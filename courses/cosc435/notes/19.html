A New Kind of Conflict

  • In reduction and scan, the addresses written each round are known in advance and never overlap: no two threads write the same slot in one round
  • A histogram breaks that: each thread looks at one value, decides its bin, and adds 1 to that bin’s count. Which bin depends on the data, not on the thread’s index
  • Two threads can easily hit the same bin at the same time: both need to increment counts[5]
  • So collisions are unpredictable and data-dependent, not the clean tree of reduction or scan

~3 min. Frame this explicitly as “the third pattern” completing the module — students should leave recognizing reduction (combine to one), scan (propagate to all), and atomics (handle unpredictable collisions) as three distinct answers to “how do threads cooperate,” not one topic that happens to have three examples.

The Race Condition, Concretely

@cuda.jit
def histogram_broken(bins, counts):
    i = cuda.grid(1)
    if i < bins.shape[0]:
        b = bins[i]             # this value's bin (already an integer here)
        counts[b] += 1          # BROKEN: see next slide
  • counts[b] += 1 looks like one operation, but the hardware runs it as three: read counts[b], add 1, write it back
  • Two threads with the same b can both read before either writes. What happens then?

~3 min across both sub-slides. Let students answer the question before advancing. This is the same read-modify-write race idea as Module 4’s shared-memory races — here in global memory, and caused by data-dependent collisions rather than a missing syncthreads().

  • With many threads and many collisions, the histogram undercounts, and by a different amount each run, because the interleaving isn’t deterministic

Atomic Operations: The Fix

@cuda.jit
def histogram_atomic(bins, counts):
    i = cuda.grid(1)
    if i < bins.shape[0]:
        b = bins[i]
        cuda.atomic.add(counts, b, 1)   # read-modify-write as ONE indivisible step
  • cuda.atomic.add(array, index, value) does the whole read-modify-write as one indivisible hardware operation: no other thread can see or interfere with it halfway
  • Two threads adding to the same address at the same moment are serialized: one finishes completely, then the other. No lost updates
  • The rule: whenever several threads might write the same address, replace += with the atomic version

~3 min. Emphasize “indivisible,” not “fast” — atomics fix correctness, they don’t make the operation cheap (The Cost of Atomics, below). The syntax is simple; the concept (why it’s needed, what “indivisible” guarantees) is the real content.

A Complete Histogram Kernel

Values in [0, 1), counted into 10 equal-width bins:

NUM_BINS = 10

@cuda.jit
def histogram(values, counts):
    i = cuda.grid(1)
    if i < values.shape[0]:
        b = int(values[i] * NUM_BINS)          # 0.37 → bin 3
        b = max(0, min(b, NUM_BINS - 1))       # clamp into [0, NUM_BINS - 1]
        cuda.atomic.add(counts, b, 1)
  • Each thread computes its own bin, then atomically adds 1. No other coordination is needed
  • The clamp keeps an out-of-range value (exactly 1.0, or a small negative) from writing outside counts. Same habit as Module 3’s stencil boundaries

~3 min across both sub-slides. Worth a live demo if time allows.

rng    = np.random.default_rng(0)
values = rng.random(10_000).astype(np.float32)

threads = 256
blocks  = (values.size + threads - 1) // threads
counts_gpu = cuda.to_device(np.zeros(NUM_BINS, dtype=np.int32))   # must start at 0
histogram[blocks, threads](cuda.to_device(values), counts_gpu)
cuda.synchronize()

print(counts_gpu.copy_to_host())
print(np.histogram(values, bins=NUM_BINS, range=(0, 1))[0])
[1033 1016  959  988  994 1029  980  980 1041  980]
[1033 1016  959  988  994 1029  980  980 1041  980]
  • An exact match with NumPy, every run. The plain += version would come out lower, and differently each time
  • counts_gpu must be zero-initialized: atomics add to whatever is already there, they never reset it

Atomics Beyond Addition

Numba has other atomics with the same indivisible read-modify-write guarantee:

  • cuda.atomic.max(array, index, value) / cuda.atomic.min(...): for many threads updating a shared “best so far”
  • cuda.atomic.cas(array, index, old, new) (compare-and-swap): “write new only if the value still equals old”. Most other atomics, and lock-free algorithms in general, are built from it
  • Whenever several threads might write the same, data-dependent location, you need an atomic, or a redesign that avoids the collision

~2 min. Keep this at the level of “these exist and follow the same pattern as atomic.add” — no worked example for each; the histogram already carries the core idea. Avoid the older cuda.atomic.compare_and_swap(array, old, new) — it only operates on array[0].

The Cost of Atomics

  • Atomics stay correct by serializing conflicting updates. Many threads hitting the same address at once wait in line, much like Module 4’s bank conflicts
  • Few bins, many threads (10 bins, a million threads): heavy contention, most threads waiting on a handful of addresses
  • Many bins relative to threads: collisions are rare, little waiting
  • The trade-off: plain += was fast and wrong; atomics are always right, and how fast depends on how much contention your data causes

~2 min. This is the last of three techniques (bounds guards, syncthreads, atomics) that all trade a little overhead for correctness — worth naming that pattern explicitly as something students have now seen three times.

Reducing Contention: Private Histograms

Give each block its own shared-memory histogram, then merge it into the global one:

@cuda.jit
def histogram_private(values, counts):
    local = cuda.shared.array(NUM_BINS, numba.int32)   # this block's histogram
    ti = cuda.threadIdx.x
    if ti < NUM_BINS:
        local[ti] = 0
    cuda.syncthreads()

    i = cuda.grid(1)
    if i < values.shape[0]:
        b = max(0, min(int(values[i] * NUM_BINS), NUM_BINS - 1))
        cuda.atomic.add(local, b, 1)          # contention only within this block
    cuda.syncthreads()

    if ti < NUM_BINS:
        cuda.atomic.add(counts, ti, local[ti])   # one global atomic per bin per block

~3 min across both sub-slides. Awareness-level, not in a lab or checkpoint — but it ties Module 4 (shared memory + barriers) to today, and it’s the standard real-world fix. Verified in the CUDA simulator: same output as histogram on the previous example. It assumes threads per block ≥ NUM_BINS.

  • Atomics on shared memory are much cheaper than on global memory, and only this block’s 256 threads compete for each bin
  • Global atomics drop from one per value (10,000) to one per bin per block (40 blocks × 10 = 400)
  • Both barriers matter: the first so nobody counts into an uncleared bin, the second so the merge doesn’t read a half-finished local histogram
  • This is the pattern again: privatize, combine locally, merge once, the same idea as a reduction’s per-block partial sums
