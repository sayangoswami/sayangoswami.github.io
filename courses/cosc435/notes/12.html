The Wrong Way to Time a GPU Kernel

import time

my_kernel[blocks, threads](arr_gpu)    # warm-up: the first call JIT-compiles
cuda.synchronize()

start = time.perf_counter()
my_kernel[blocks, threads](arr_gpu)
end = time.perf_counter()

print(f"{(end - start)*1000:.2f} ms")  # WRONG
  • A GPU kernel launch is asynchronous — the CPU issues the launch and immediately continues to the next line, without waiting for the GPU to finish
  • time.perf_counter() here measures how long it took to launch the kernel, not how long the kernel took to run
  • The result: a suspiciously, impossibly fast number — this is the bug, not a real measurement

~3 min. This is Lab 06’s critical demo. Let the wrong number sit for a moment before revealing why it’s wrong — the surprise is the point, it makes the fix memorable. Mention the warm-up line in passing here; the next slide explains it.

The Right Way: cuda.synchronize()

import time
from numba import cuda

my_kernel[blocks, threads](arr_gpu)    # warm-up: the first call JIT-compiles
cuda.synchronize()

start = time.perf_counter()
my_kernel[blocks, threads](arr_gpu)
cuda.synchronize()              # wait for the GPU to actually finish
end = time.perf_counter()

print(f"{(end - start)*1000:.2f} ms")  # CORRECT
  • cuda.synchronize() blocks the CPU until every previously-launched GPU operation has completed
  • The warm-up call matters too: the first launch of a @cuda.jit kernel compiles it, which can take hundreds of ms — never time that call
  • In Lab 6 the wrong timing typically comes out 10–100× smaller than the correct one
  • Without cuda.synchronize(), you are timing a function call that returns almost instantly, not a computation
  • This is not a beginner mistake to be embarrassed about — the same bug appears in published papers and shipped industry code. Professional GPU code-review checklists explicitly call it out

~2 min across both sub-slides. Reiterate: the fact that the wrong code runs, produces a plausible-looking (if suspiciously small) number, and never raises an error is exactly what makes this trap dangerous. There is no crash to alert you.

Timing Across Problem Sizes

sizes = [10_000, 100_000, 1_000_000, 10_000_000]
THREADS = 256

for N in sizes:
    arr = np.ones(N, dtype=np.float32)
    arr_gpu = cuda.to_device(arr)            # transfer happens before the timer
    BLOCKS = (N + THREADS - 1) // THREADS

    scale[BLOCKS, THREADS](arr_gpu, 2.0)     # warm-up (first call compiles)
    cuda.synchronize()

    start = time.perf_counter()
    scale[BLOCKS, THREADS](arr_gpu, 2.0)     # the scale kernel from Oct 5
    cuda.synchronize()
    gpu_ms = (time.perf_counter() - start) * 1000

    start = time.perf_counter()
    arr *= 2.0                               # the same work in NumPy, on the CPU
    cpu_ms = (time.perf_counter() - start) * 1000

    print(f"N={N:>10,}  GPU={gpu_ms:.3f} ms  NumPy={cpu_ms:.3f} ms")

What the output shows:

  • At small N the GPU time barely changes as N grows — a fixed launch overhead dominates, and NumPy often wins
  • At large N the GPU time grows roughly in proportion to N — the overhead is amortized, and the GPU pulls ahead as NumPy’s time keeps climbing
  • The crossover is the N where the two lines cross — a concrete answer to Module 1’s “when does the GPU actually win?”
  • cuda.to_device runs before the timer, so this measures the kernel alone. Move it inside the timed region and transfer cost joins the fixed overhead (Module 2’s host↔︎device boundary) — the crossover moves to a much larger N
  • Lab 6 Part 2 makes the same kind of GPU-vs-NumPy comparison at a single N; this loop extends it across sizes

Reading a Profiler-Style Table

     Block |  Time (ms) | Threads/block
------------------------------------------
       8x8 |      14.82 |             64

     32x32 |       8.94 |           1024
  • Reading this table is itself a skill: scan the “Time” column for the minimum, then ask why that configuration won — this is what CK-06 tests
  • Here, 16×16 is fastest — not the smallest block and not the largest. Why? The next slides work it out
  • A profiler-style table is a compressed record of an experiment — reading it well means reconstructing the “why,” not just picking out the smallest number
  • These numbers are representative — your Lab 6 results will vary with Colab’s GPU and its current load. The shape is what to look for

~3 min across both sub-slides. Numbers shown are representative, not guaranteed — actual Lab 6 results vary by Colab’s assigned T4 and current load. The shape (middle value wins) is the teachable pattern, not these exact milliseconds.

Why 16×16 Won Here

  • Sep 30’s occupancy idea doesn’t explain this table on a T4. One T4 SM holds at most 1024 threads and 16 blocks:
Block Blocks per SM Threads per SM
8×8 (64 threads) 16 (the block limit) 1024
16×16 (256 threads) 4 1024
32×32 (1024 threads) 1 1024
  • All three fill the SM — and this kernel uses few registers, so registers don’t cap it either
  • What does differ is how each warp touches memory

cuda.grid(2) puts threadIdx.x on row, so a warp’s 32 threads fill down the rows first.

Two forces pull in opposite directions:

  • Scattered reads (favors small blocks): at each k, a warp reads A[row, k] for every row it covers. Each row of A lives in a different place in memory — 8, 16, or 32 separate fetches. B[k, col] comes from adjacent columns: one fetch
  • Shared data (favors big blocks): every thread in a block needs the same few rows of A and columns of B. 8×8 needs 8 + 8 = 16 of them for 64 outputs; 32×32 needs 64 for 1,024 outputs — 16× the outputs from 4× the data, reuse the cache can catch
  • 16×16 sits between the two. Which force wins depends on the GPU and the matrix size — a heuristic, not a law. The only way to know is to measure, as Lab 6 does
  • Module 4 makes both forces deliberate: coalescing (Oct 21) tackles the first, shared-memory tiling (Lab 9) the second

~4 min across the three sub-slides. REWRITTEN 2026-10-07: this slide used to explain the table by occupancy (8x8 = too few warps, 32x32 = too few blocks). That holds on some GPUs (e.g. compute capability 8.6: 16 blocks x 64 = 1024 of 1536 threads, 67%), but not on Colab’s T4 (CC 7.5: 1024 threads / 16 blocks per SM), where all three configs reach 100% theoretical occupancy. Compute-Bound or Memory-Bound?

  • The naive matmul kernel reads a full row of A and a full column of B from global memory for every single output element — no programmed reuse: each thread fetches its own copies, even though neighboring threads need the same data
  • That’s a lot of memory traffic relative to the arithmetic done per byte fetched — low arithmetic intensity (Module 1’s preview of this idea)
  • Diagnosis: this kernel is memory-bound, not compute-bound — its ALUs are very often waiting on data
  • This diagnosis is exactly why Module 4’s tiled matmul (reusing data via shared memory) gets such a large speedup — it directly attacks the memory bottleneck identified here

~3 min. Plant the reasoning pattern here (describe the access pattern → count reuse → conclude bound type). The caches (L1/L2) do catch some of the neighbor reuse by accident, which is why Lab 06 Ex 2’s “implied traffic” exceeds DRAM peak — tiling makes that reuse deliberate. The next slides turn this qualitative diagnosis into the numbers CK-06 asks for.

Putting Numbers on It: Achieved Bandwidth

Worked example: SAXPY, y[i] = a * x[i] + y[i], on N = 10,000,000 float32 elements, timed at 0.45 ms on a T4

  • Bytes moved per element: read x[i] (4) + read y[i] (4) + write y[i] (4) = 12 bytes
  • Total bytes: 10,000,000 × 12 = 120,000,000 bytes

\[\text{Bandwidth} = \frac{120{,}000{,}000\ \text{bytes}}{0.45 \times 10^{-3}\ \text{s}} = 2.67 \times 10^{11}\ \text{B/s} = 266.7\ \text{GB/s}\]

  • The units trap: convert ms → s (÷ 1000) and bytes → GB (÷ 10⁹, the convention in this course) before comparing to the T4’s 320 GB/s peak
  • 266.7 ÷ 320 = 83% of peak bandwidth

Arithmetic Intensity and the Ridge Point

  • Arithmetic intensity = FLOPs ÷ bytes moved. SAXPY: 2 FLOPs (one multiply, one add) per 12 bytes = 0.167 FLOP/byte
  • Ridge point = peak FLOP/s ÷ peak bandwidth. T4: 8,100 GFLOP/s ÷ 320 GB/s = 25.3 FLOP/byte
  • Intensity below the ridge point → memory-bound: bandwidth runs out before arithmetic does
  • Intensity above the ridge point → compute-bound
  • SAXPY: 0.167 ≪ 25.3, so it’s memory-bound — and the relevant peak to report is bandwidth (83%), not FLOP/s
  • For a compute-bound kernel, report achieved GFLOP/s ÷ 8,100 instead (Module 4 draws all of this as the roofline)

~4 min across both sub-slides. CK-06 is exactly this sequence on a seeded table: GB/s per row, memory vs. compute, % of the relevant peak. Lab 06 Exercise 2 does it on the naive matmul (deliberately not used as the worked example here, so the lab isn’t pre-answered). The ridge point is formalized as the roofline in Module 4.

Choosing a Robust Configuration

Threads/Block |  Time (ms)
--------------------------
           64 |      0.61
          128 |      0.48
          256 |      0.46
          512 |      0.45   ← fastest
         1024 |      0.52
  • Timings within ~5% of each other are effectively a tie — run-to-run noise on a shared Colab GPU is about that large
  • Rule used in CK-06: pick the smallest block size within 5% of the best time
  • Here: 5% above 0.45 ms is 0.4725 ms → 256 (0.46) qualifies, 128 (0.48) doesn’t → robust choice: 256
  • Why smallest: it gives the scheduler more, smaller blocks to spread across the 40 SMs, and less per-block resource demand if the kernel later grows

~2 min. The point is that “fastest in one run” is not the same as “best choice” — a config that wins by 2% may lose next run. Same 5% rule as CK-06’s Gap 4.

Amdahl’s Law: The Serial Fraction Problem

Every program has two parts:

  • Parallel part (fraction \(p\)): can run on all GPU cores simultaneously
  • Serial part (fraction \(1-p\)): must run sequentially — no amount of parallel hardware helps

\[\text{Speedup}(n) = \frac{1}{(1-p) + \frac{p}{n}}\]

where \(n\) is the number of parallel processors applied to the parallel part.

  • Why: if the original run takes 1 unit of time, the serial part still takes \((1-p)\), and the parallel part shrinks to \(p/n\). Speedup is 1 divided by the new total

~4 min. Derive from first principles on the board, then reveal the “Why” bullet so the derivation is on the slide for students reviewing later. This is the formal version of Module 1’s informal preview.

The Ceiling

As \(n \to \infty\) (infinitely many processors):

\[\text{Speedup} \to \frac{1}{1-p}\]

  • A 5% serial fraction caps total speedup at 20× — forever, no matter how many GPU cores you add
  • A 1% serial fraction caps it at 100×. Even a tiny serial fraction becomes the binding constraint once \(n\) is large enough

Every curve rises, then hits a wall at \(1/(1-p)\) — more processors stop helping long before you run out of them.

~2 min across both sub-slides. The chart is the “aha” — a static formula is less convincing than watching four curves all hit a wall at different heights. EL-03 has students apply this exact ceiling to the capstone’s estimated 5% serial fraction. Chart source: diags/make_amdahl_chart.py.

The Uncomfortable Implication

  • Your GPU kernel is 50× faster than the CPU version. The serial part of your program is completely unchanged.
  • If the serial fraction is 5%, the end-to-end speedup of your whole program is still capped at 20×, no matter how fast that kernel gets
  • Cutting the serial fraction from 5% to 2.5% buys more end-to-end speedup than doubling the GPU kernel’s raw performance (numbers on the next slide)
  • Practical consequence: sometimes the highest-value optimization isn’t the kernel at all — it’s the data loading, the preprocessing step, or a serial aggregation on the host

Check the claim with the formula, starting from a 50× kernel and 5% serial:

Change Speedup
Start: \(p = 0.95\), \(n = 50\) \(1 / (0.05 + 0.95/50) =\) 14.5×
Double the kernel: \(p = 0.95\), \(n = 100\) \(1 / (0.05 + 0.95/100) =\) 16.8×
Halve the serial part: \(p = 0.975\), \(n = 50\) \(1 / (0.025 + 0.975/50) =\) 22.5×

Doubling the kernel adds 2.3 to the end-to-end speedup; halving the serial part adds 8.0.

~3 min across both sub-slides. This is the punchline students should carry into the capstone: profiling (this session’s first half) tells you where time goes; Amdahl tells you the ceiling on how much any one piece of optimization can help. Have students compute the middle row themselves before revealing it.
