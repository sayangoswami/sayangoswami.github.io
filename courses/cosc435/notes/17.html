Beyond Embarrassingly Parallel

So far, every kernel has had the same shape: thread i computes output i, from input i (or a small fixed neighbourhood, for stencils). No thread ever needs another thread’s result.

Some problems don’t fit that shape:

  • Sum all elements: the answer needs every input. No single thread can know the total
  • Find the maximum: same problem, a different combining operation
  • Running total (prefix sum): each output depends on all earlier inputs (Nov 9)

These need threads to communicate and combine partial results: a new kind of parallel pattern.

~3 min. These two patterns (reduction, and Nov 9’s prefix scan) appear constantly outside this course too — databases, compression, sorting, and nearly every non-trivial GPU algorithm use one or both. The capstone’s cp.argpartition internally relies on a reduction-like operation.

The Serial Approach, for Contrast

def serial_sum(arr):
    total = 0.0
    for x in arr:       # N steps, strictly sequential
        total += x
    return total
  • O(N) time, O(1) memory. Step 2 can’t start until step 1’s result is known
  • Porting this loop to the GPU as-is doesn’t help: one thread does all N additions while thousands sit idle
  • The question for today: can we restructure the computation so the work happens in parallel rounds?

~2 min. Emphasize “restructure,” not “parallelize as-is” — a common early misconception is that any serial loop can just run on more threads. This one specifically can’t, without changing the algorithm’s shape.

Tree Reduction: The Idea

~4 min across both sub-slides. Walk the three rounds out loud, stride by stride. Lab 10 Part 1 runs the same tree on [1, 2, …, 8] (total 36) — ask students to predict its rounds before Friday. This array is the one Lab 11 uses on Nov 13.

  • Pair values up and add all the pairs at once: one round of parallel work replaces many sequential additions
  • Each round halves the number of values still in play, so N values reduce to one in log₂(N) rounds
  • For N = 1,000,000: a serial sum takes 1,000,000 sequential steps; a tree takes about 20 rounds

The Stride-Halving Kernel

@cuda.jit
def block_sum(arr, out):
    s  = cuda.shared.array(shape=256, dtype=numba.float32)
    ti = cuda.threadIdx.x
    i  = cuda.grid(1)

    s[ti] = arr[i] if i < arr.shape[0] else numba.float32(0.0)
    cuda.syncthreads()

    stride = 128                 # blockDim.x // 2
    while stride > 0:
        if ti < stride:
            s[ti] += s[ti + stride]
        cuda.syncthreads()
        stride //= 2             # halve each round

    if ti == 0:
        out[cuda.blockIdx.x] = s[0]   # this block's sum

~3 min for the step-through, ~2 min for the next sub-slide. This is the kernel Lab 10 Part 2 runs (the lab version takes n as a third argument). Click through the highlights in order: load, the loop, the active threads, the barrier, the single write. Before the barrier highlight, ask “is this barrier legal?” — it’s outside the if, so yes (Module 4’s divergent-barrier trap).

  • Line 7: each thread loads one element into shared memory. Threads past the end load 0.0, the identity for addition, so they can’t change the sum
  • Lines 10–15: the diagram’s rounds: stride 128, 64, …, 1. That’s 8 rounds for 256 threads
  • Lines 12–13: only threads with ti < stride work: half as many each round
  • Line 14: a barrier every round: the next round reads values other threads just wrote. It sits outside the if, so every thread reaches it (Oct 26)
  • Lines 17–18: after the last round s[0] holds the block’s total, and one thread writes it out

Multi-Level Reduction

  • One launch gives one sum per block, not one for the whole array: out[blockIdx.x] is that block’s partial sum
  • For N = 1,000,000 with 256-thread blocks: (1,000,000 + 255) // 256 = 3,907 blocks, so 3,907 partial sums are left
  • Finishing needs a second pass: run the reduction again on the partial sums, or, since 3,907 values is small, copy them to the host and let NumPy finish

~3 min across both sub-slides. This two-pass (or GPU-then-CPU) pattern is ubiquitous in real GPU reduction code — it’s what cp.sum() (Module 6) does internally, optimized further than a hand-written version. That’s why the capstone uses CuPy’s built-in reductions rather than a hand-rolled kernel: this pattern, done well, is genuinely fiddly to get optimal.

One million ones, so every answer is easy to check:

N, BLOCK = 1_000_000, 256
n_blocks = (N + BLOCK - 1) // BLOCK                  # 3,907

arr_gpu        = cuda.to_device(np.ones(N, dtype=np.float32))
block_sums_gpu = cuda.device_array(n_blocks, dtype=np.float32)
block_sum[n_blocks, BLOCK](arr_gpu, block_sums_gpu)
cuda.synchronize()

block_sums_cpu = block_sums_gpu.copy_to_host()
total = block_sums_cpu.sum()          # finish the last, small reduction on the CPU
print(block_sums_cpu[:3], block_sums_cpu[-1])
print(int(total))
[256. 256. 256.] 64.0
1000000
  • Every full block sums to 256. The last block holds only 1,000,000 − 3,906 × 256 = 64 real values; its zero padding adds nothing

Work and Step Complexity

Algorithm Total work (operations) Steps (sequential rounds)
Serial sum O(N) O(N)
Tree reduction O(N) O(log N)
  • Both do the same total work: a tree doesn’t do fewer additions, it arranges the same N − 1 additions so many happen at once
  • The speedup comes entirely from parallelism, not from a “smarter” computation
  • A recurring theme: some parallel algorithms even do more total work than the serial version, and still win, because they need far fewer sequential steps. Wall-clock time is what matters

~2 min. Worth stating explicitly since it cuts against a common intuition: “parallel” doesn’t automatically mean “does less work” — it means “does the same (or more) work in fewer sequential rounds, using more processors at once.”

Different Combiners: Max and Dot Product

The tree’s shape doesn’t care how two values are combined. Swap += for another operation and the same stride-halving loop still works.

  • Maximum: s[ti] = max(s[ti], s[ti + stride]), and pad out-of-range threads with -math.inf, which can never win. Padding with 0.0 would win whenever every real value is negative. This is Lab 10 Exercise 3
  • Dot product: each thread first computes a[i] * b[i], then the products are reduced with += exactly as in block_sum. The capstone’s similarity scores are this same multiply-then-reduce shape

~3 min across both sub-slides. The identity value is the most common Lab 10 bug (0 instead of a very negative number) and is also what CK-10 checks: its data is all ≥ 100, so a 0.0 identity for min visibly wins.

Which operations work?

  • The tree combines values in a different order and grouping than a left-to-right loop: round 1 pairs s[0] with s[128]
  • So the operation must be associative, (a ⊕ b) ⊕ c == a ⊕ (b ⊕ c), and commutative, a ⊕ b == b ⊕ a. Sum, max and min are both
  • Would subtraction work?
  • No: (8 − 3) − 2 = 3, but 8 − (3 − 2) = 7. Changing the grouping changes the answer
  • Fine print: float32 addition is only almost associative (each step rounds). A GPU sum can differ from NumPy’s in the last few digits, which is why Lab 10 compares with a tolerance, not ==

~2 min. Ask the subtraction question and let them reason it out before the reveal. The float32 point pays off in Lab 10 Part 2, whose check is abs(gpu - cpu) < 1.0 on a million values.

Warp-Level Tricks

  • Once the stride drops to 32 or below, every thread still working is in warp 0 (warps from Sep 30)
  • Warp shuffle instructions (cuda.shfl_down_sync in Numba) let threads in one warp swap values register-to-register, without shared memory
  • Using shuffles for those last rounds skips the shared-memory traffic and the syncthreads() calls for the tail of the reduction: a real, measurable speedup

~3 min across both sub-slides. Intentionally awareness-level, not a skill the labs or checkpoints require — Lab 10’s block_sum uses syncthreads() every round, which is always correct, just not maximally fast. It’s here so students recognize the pattern in production CUDA code, not because it’s needed for CK-10.

A word of caution: you’ll see an older trick online that keeps using shared memory but drops syncthreads() once stride ≤ 32, because “the warp runs in lock-step anyway.”

  • That was true on older GPUs. Since Volta (2017), threads in a warp are scheduled independently, so the trick can silently give wrong sums
  • The shuffle instructions are the correct, current way to get this speedup
  • In this course, keep the barrier every round. It’s always correct
