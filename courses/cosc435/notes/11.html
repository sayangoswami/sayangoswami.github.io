From “Does It Run” to “Does It Run Well”

  • Every kernel you’ve written so far (Labs 4-5) follows one pattern: one thread computes one output element, checked by one bounds guard
  • That pattern is correct, and it’s the right default — but it’s not the only shape a kernel can take, and getting it running is only the first bar to clear
  • The rest of this module is about two things: designing kernels deliberately rather than by habit, and measuring whether they’re actually fast

~2 min. Framing slide — sets up why “design patterns” and “debugging” belong in the same session as a matched pair: patterns are how you write a kernel well the first time, debugging is what you do when it isn’t.

Pattern: One Thread, One Output Element

@cuda.jit
def scale(arr, factor):
    i = cuda.grid(1)
    if i < arr.shape[0]:
        arr[i] = arr[i] * factor
  • Launch (at least) as many threads as there are outputs; each thread computes exactly one
  • Maps directly onto the hardware’s SIMT model (Sep 30)
  • Right whenever the number of outputs is known ahead of time and reasonably launch-able — millions of threads is fine; billions can hit practical limits
  • This is the default pattern — reach for it first

~2 min. Deliberately named and framed as “the pattern” — students have been using it since Lab 4 without necessarily thinking of it as a reusable, nameable design choice. Naming it is the point of this slide.

Pattern: The Grid-Stride Loop

@cuda.jit
def scale_grid_stride(arr, factor):
    start  = cuda.grid(1)
    stride = cuda.gridsize(1)   # total threads launched
    for i in range(start, arr.shape[0], stride):
        arr[i] = arr[i] * factor
  • Launch a fixed, modest number of threads; each one loops over several elements, striding by the total thread count
  • Useful when N is unknown at launch time or too large for one thread per element, or to run one launch config across a wide range of N

~2 min. Explicitly flag this as awareness-level, not tested — students should not walk away thinking they need to memorize cuda.gridsize() syntax for a checkpoint. The goal is purely “don’t be confused when you see this shape later in your career.” The trace on the next sub-slide is the fastest way to make the loop click.

Trace: N = 10 elements, but only 4 threads launched (stride = 4)

Thread (start) Handles indices
0 0, 4, 8
1 1, 5, 9
2 2, 6
3 3, 7
  • Every index is covered exactly once, and the loop’s own range stops at N — no separate bounds guard needed
  • You won’t be asked to write this pattern in a lab or checkpoint this semester — it’s here so you recognize it in real-world CUDA code, which uses it constantly

Choosing a Launch Configuration

  • So far, launch configuration (THREADS, computed BLOCKS) has mostly been handed to you or fixed at a round number like 256
  • In practice there is rarely one obviously-correct block size — it depends on the kernel’s resource usage (registers, shared memory) and the GPU’s occupancy limits (Sep 30)

A few reliable heuristics:

  • Prefer multiples of 32 — whole warps, no wasted lanes (Sep 30)
  • Common starting points: 128, 256, or 512 threads per block
  • Extremes (very small or very large blocks) are rarely optimal

Beyond those heuristics, the honest answer is: measure it.

  • Lab 6 (this Friday) has you sweep several block sizes on a real kernel and find the fastest empirically — that’s Oct 7’s subject in full

~3 min across both sub-slides. Resist the temptation to give a definitive “always use 256” rule — the entire point of Oct 7’s profiling session is that this has to be measured per-kernel. This slide should leave students slightly unsatisfied with “it depends,” which Oct 7 then resolves with a concrete method.

Debugging Numba CUDA Kernels

  • GPU kernels run outside the normal Python debugger — you can’t drop a breakpoint inside a @cuda.jit function the way you would in ordinary Python

Common failure modes you’ll hit this semester:

  • Silent wrong answers — almost always a missing or incorrect bounds guard (Module 2)
  • TypingError at compile time — Numba compiles only a restricted subset of Python/NumPy; Python lists, string formatting, and most NumPy functions inside a kernel fail with a (sometimes cryptic) type error
  • Shape mismatches — passing an array of the wrong shape or dtype to a kernel that assumes a specific layout

~3 min. Ask the room if anyone has already hit a TypingError in Lab 4 or 5 — normalize it as a routine part of the workflow, not a sign something has gone deeply wrong.

Debugging Technique: Shrink N and Verify by Hand

N_DEBUG = 8   # instead of 1,000,000 — small enough to eyeball
arr = np.arange(N_DEBUG, dtype=np.float32)
arr_gpu = cuda.to_device(arr)

my_kernel[1, N_DEBUG](arr_gpu)     # one block, exactly enough threads
cuda.synchronize()

print(arr_gpu.copy_to_host())      # small enough to read directly

If my_kernel doubles every element, you should see:

[ 0.  2.  4.  6.  8. 10. 12. 14.]

If you see [ 0. 2. 4. 6. 4. 5. 6. 7.] instead, half the threads did nothing — an indexing or launch bug, visible at a glance.

  • Before trusting a kernel at N = 1,000,000, run it at N = 8 and check every value by hand or against a tiny NumPy reference
  • Launching one block with exactly N threads (no ceiling division needed) removes launch-configuration bugs from the picture while you debug the kernel body itself
  • Every lab’s Completion cell checks your results at full scale — this technique is how you get there with confidence, one step earlier

~2 min across both sub-slides. This is the single most useful habit to instill this session — most kernel bugs are far easier to spot in 8 printed numbers than in a checksum computed over a million.

Debugging Technique: The CUDA Simulator

import os
os.environ["NUMBA_ENABLE_CUDASIM"] = "1"   # set BEFORE importing numba

import numpy as np
from numba import cuda

@cuda.jit
def my_kernel(arr):
    i = cuda.grid(1)
    if i < arr.shape[0]:
        print("thread", i, "sees", arr[i])
        arr[i] = arr[i] * 2.0

my_kernel[1, 4](np.arange(4, dtype=np.float32))

Output (thread order may vary):

thread 0 sees 0.0
thread 1 sees 1.0
thread 2 sees 2.0
thread 3 sees 3.0
  • NUMBA_ENABLE_CUDASIM=1 runs your @cuda.jit kernel in pure Python, on the CPU, with every GPU thread simulated — no GPU required
  • In the simulator you can inspect any variable with print() and even set pdb breakpoints — and an out-of-bounds read raises a normal Python IndexError instead of silently corrupting memory
  • On a real GPU, print() works only for simple values (numbers, string constants), the output is unordered across threads, and pdb doesn’t work at all
  • Trade-off: the simulator is much slower and doesn’t reflect real GPU timing — use it to debug logic, then switch back to a real GPU to measure performance

~2 min. This is a genuinely useful Numba feature many students won’t discover on their own — worth a live demo if time allows: move the print() above the bounds guard and launch 5 threads on 4 elements; the simulator raises IndexError on the spot, while real hardware would read garbage silently. Note the env var must be set before numba is imported at all — in Colab that means restarting the runtime if numba is already loaded.
