What a Kernel Is

  • A kernel is a function that runs on the GPU — you write it once, and the GPU runs that same code for every thread, simultaneously
  • Each thread automatically knows its own position in the grid of threads — that position is how a thread figures out which piece of data it’s responsible for
  • Marked with the @cuda.jit decorator, which compiles ordinary-looking Python into GPU machine code
from numba import cuda

@cuda.jit
def my_kernel(arr):
    i = cuda.grid(1)          # this thread's global index
    if i < arr.shape[0]:      # bounds guard — always required (next slide)
        arr[i] = arr[i] * 2.0
  • Three parts every kernel has: the decorator, a position calculation, and a bounds guard

~3 min. Students will forget the bounds guard constantly in early labs — flag it now as “always required” so it’s not a surprise two slides from now.

The Thread Grid

  • blockIdx.x — which block is this thread in?
  • threadIdx.x — where is this thread within its block?
  • blockDim.x — how many threads are in each block?
  • Global index = blockIdx.x * blockDim.x + threadIdx.x — cuda.grid(1) computes exactly this in one call
  • This global index is what a thread uses to know which array element is “its” element

~4 min. This is the single mental model students need for the rest of the course — worth having them compute the global index for 2-3 different (blockIdx, threadIdx, blockDim) combinations out loud before moving on.

Launching a Kernel

import numpy as np
from numba import cuda

N = 1_000_000
arr = np.ones(N, dtype=np.float32)
arr_gpu = cuda.to_device(arr)          # host → device transfer

THREADS = 256
BLOCKS  = (N + THREADS - 1) // THREADS   # ceiling division — see below

my_kernel[BLOCKS, THREADS](arr_gpu)    # launch: BLOCKS × THREADS total threads
cuda.synchronize()                     # wait for the GPU to finish

result = arr_gpu.copy_to_host()        # device → host transfer
  • (N + THREADS - 1) // THREADS is ceiling division — the standard way to compute “enough blocks to cover N, rounding up” using only integer arithmetic
  • You will write this exact five-line pattern (transfer, configure, launch, synchronize, transfer back) in nearly every lab this semester

~3 min. Walk through each line out loud. Ceiling division specifically is worth a plain-integer example: N=1000, THREADS=256 → (1000+255)//256 = 4 blocks = 1024 threads launched, 24 wasted (caught by the bounds guard).

The Bounds Guard

@cuda.jit
def my_kernel(arr):
    i = cuda.grid(1)
    # Without this line: threads with i >= arr.shape[0] write out of bounds
    if i < arr.shape[0]:
        arr[i] = arr[i] * 2.0
  • BLOCKS × THREADS is a ceiling, computed by rounding up — so there are almost always a few extra threads beyond the last real array element
  • Those extra threads still run the kernel body — without the guard, they read/write memory past the end of the array
  • Consequence: undefined behavior — sometimes a crash, sometimes silent data corruption that produces a wrong answer with no error message at all

~2 min. Silent corruption is the scarier failure mode to emphasize — a crash at least tells you something’s wrong. Lab 04 Exercise 4 has students remove the guard intentionally on a small array so they can see the effect directly.

Worked Example: Scalar Multiply

@cuda.jit
def multiply_scalar(arr, scalar):
    i = cuda.grid(1)
    if i < arr.shape[0]:
        arr[i] = arr[i] * scalar
  • One thread per array element — for N = 500,000 elements, the GPU launches 500,000 threads
  • No thread needs any other thread’s result — this is the “embarrassingly parallel” shape from Module 1
  • This is Lab 04 Exercise 1’s pattern; you’ll write the launch configuration yourself in lab

~2 min. Deliberately simple — the goal here is the launch pattern sinking in, not the arithmetic.

Worked Example: Add Two Arrays

@cuda.jit
def add_arrays(a, b, out):
    i = cuda.grid(1)
    if i < out.shape[0]:
        out[i] = a[i] + b[i]
  • Three arrays now live on the device: two inputs, one output
  • Still no dependencies between elements — output[i] only ever needs input[i], never any other index
  • Ask yourself: if N doubles, what (if anything) changes in the launch configuration? (Answer: BLOCKS recomputes via the same ceiling-division formula — THREADS usually stays fixed)

~2 min. Lab 04 Exercise 2’s pattern. The “what changes when N doubles” question is worth pausing on — it’s testing whether students actually understand ceiling division rather than having memorized a specific number.

From 1D to 2D

  • Images, matrices, and (soon) the capstone’s similarity table are inherently two-dimensional
  • Same idea as 1D, doubled: one thread per (row, col) pair instead of one thread per index
  • cuda.grid(2) returns a (row, col) tuple directly — you don’t need to compute it by hand from blockIdx/threadIdx (though you still can, next slide shows the underlying formula)
@cuda.jit
def add_matrices(A, B, C):
    row, col = cuda.grid(2)
    if row < C.shape[0] and col < C.shape[1]:
        C[row, col] = A[row, col] + B[row, col]
  • The bounds guard is now two conditions ANDed together — a thread must be in-bounds on both axes to do useful work

~3 min. cuda.grid(2) returning (row, col) directly is the convention used in every 2D checkpoint and lab this semester (CK-05, Lab 05) — always unpack it as row, col = cuda.grid(2), never reorder it.

2D Launch Configuration

M, N = 300, 400     # matrix shape

THREADS = (16, 16)  # 256 threads per block — a 16×16 tile
BLOCKS  = (
    (M + THREADS[0] - 1) // THREADS[0],   # ceiling in the row dimension
    (N + THREADS[1] - 1) // THREADS[1],   # ceiling in the col dimension
)

add_matrices[BLOCKS, THREADS](A_gpu, B_gpu, C_gpu)

16×16 = 256 threads per block is a common convention — a power-of-two total that divides evenly into full warps (32 threads each, from Sep 30’s content)

300 is not a multiple of 16 → the last block in each row/column has extra threads; the bounds guard filters them exactly as in 1D

~3 min. Point out the 256 = 8 warps connection explicitly if Sep 30 has already happened when this is taught in a future offering — for this semester’s ordering it’s a forward reference, mention it as “you’ll see exactly why 256 is a friendly number in a week and a half.”

Thread Index in 2D

  • This is the formula cuda.grid(2) computes internally — same ceiling-division logic as 1D, just applied on both axes independently
  • A thread that can correctly compute its own (row, col) here has mastered 2D kernels — everything else (2D bounds checks, 2D array indexing) follows directly
global_row = blockIdx.x * blockDim.x + threadIdx.x
global_col = blockIdx.y * blockDim.y + threadIdx.y

~3 min. Have students label the global index for a thread you point to at random in the diagram — this is the practical skill CK-05 tests directly.

Preview: The Capstone’s Kernel

@cuda.jit
def similarity_naive(Q, D, sim):
    row, col = cuda.grid(2)          # row = query index, col = database index
    if row < Q.shape[0] and col < D.shape[0]:
        acc = 0.0
        for k in range(Q.shape[1]):  # over the embedding dimension (64)
            acc += Q[row, k] * D[col, k]
        sim[row, col] = acc
  • This is the heart of the semester-long capstone, in outline form — one thread per (query, database-item) pair
  • At capstone scale (1,000 queries × 100,000 database items) that’s 100 million threads, each running this exact loop independently
  • You’ll fill in a version of this kernel’s gaps at CK-13; Module 4 will later replace the inner loop with tiled shared-memory access for a major speedup

~2 min. This is purely a preview — students are not expected to write this today. The point is recognition: “oh, that’s just a 2D kernel with an extra loop inside,” which is exactly true.
