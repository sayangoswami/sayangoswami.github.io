What Is a Prefix Sum?

Input:              [2, 5, 1, 8, 3, 7, 4, 6]
Exclusive scan:     [0, 2, 7, 8, 16, 19, 26, 30]
  • Exclusive: output[i] = the sum of every input strictly before i. output[0] is always 0: nothing comes before it
  • Inclusive: output[i] = the sum of input[0..i], i included. What is it for this input?
Inclusive scan:     [2, 7, 8, 16, 19, 26, 30, 36]
  • Inclusive is exclusive shifted left by one, with the total (36) on the end
  • Exclusive is usually the useful one: it gives each element a ready-made offset to write at (next slide)

~3 min. Have students verify the first few exclusive outputs by hand from the input, then predict the inclusive row before revealing it — this cements “strictly before” vs. “up to and including” far better than the definition alone. This is the array students scan in Lab 11 Exercises 2–3.

Why Prefix Scan Matters

Stream compaction: keep only the values > 5 from [7, 2, 9, 4, 8], with no gaps.

values:           [7, 2, 9, 4, 8]
keep mask:        [1, 0, 1, 0, 1]
exclusive scan:   [0, 1, 1, 2, 2]     ← "how many kept values came before me"
  • Each kept value writes to out[scan[i]]: 7 → out[0], 9 → out[1], 8 → out[2]. Result: [7, 9, 8]
  • Every thread knows its own slot without talking to the others. You’ll do this in Lab 11’s bonus (Nov 13)

~3 min across both sub-slides. Stream compaction is the one application students actually build (Lab 11’s bonus) — the others on the next sub-slide are there so the pattern is recognizable by name later, not because they’re separately assessed.

Scan shows up inside many other algorithms:

  • Histograms: turning per-bin counts into starting offsets in one combined output array
  • Sorting: radix sort, a fast non-comparison sort, runs a scan on every digit pass
  • Dynamic allocation: threads that each need a variable-size chunk of one output buffer scan their sizes to get non-overlapping start offsets
  • You won’t implement all of these. The point: scan is a primitive, one algorithm that turns up, often invisibly, inside many others

The Serial Algorithm

def exclusive_scan_seq(arr):
    out = [0] * len(arr)
    running = 0
    for i in range(len(arr)):
        out[i] = running
        running += arr[i]
    return out
  • O(N) and strictly sequential: each output needs the running total of everything before it, which is why this looks impossible to parallelize
  • Lab 11 Exercise 1 has you write this function. Knowing it well is what makes the parallel version readable rather than magic
  • The rest of today answers one question: how can this run in O(log N) parallel rounds?

~2 min. Deliberately start here rather than jumping straight to Blelloch — the serial version being trivial is what makes the parallel version’s cleverness visible by contrast.

Blelloch Scan: Two Phases

The Blelloch exclusive scan works in two phases, each O(log N) rounds:

  1. Up-sweep (reduce): build partial sums bottom-up, with the same tree as Nov 2’s reduction
  2. Down-sweep: push those partial sums back down, turning them into prefix values

Total: O(N) work, O(log N) steps. The same as tree reduction, for a harder problem.

~2 min. Point out explicitly: up-sweep is the reduction algorithm from Nov 2, run for its side effects (the partial sums left behind at each level) rather than just its final total. Students who understood Nov 2 already understand half of this algorithm.

Up-Sweep on [2, 5, 1, 8]

~4 min across both sub-slides. Lab 11 Exercise 2 has students run this on the full 8-element array from “What Is a Prefix Sum?”. Walk through this 4-element version first to establish the index pattern. Contrast with Nov 2: reduction pairs s[t] with s[t + stride] and works toward s[0]; the up-sweep pairs s[t] with s[t − stride] and works toward the last slot. Same tree, mirrored.

Initial:  [2, 5, 1, 8]
stride=1: s[1] += s[0] → [2, 7, 1, 8]
          s[3] += s[2] → [2, 7, 1, 9]
stride=2: s[3] += s[1] → [2, 7, 1, 16]
Result:   [2, 7, 1, 16]   ← s[3] = total sum
  • The active slots are the ones where (t + 1) is a multiple of 2 × stride: slots 1 and 3, then slot 3
  • Each active slot adds the value stride places to its left
  • Unlike Nov 2’s reduction, the intermediate sums stay in place: s[1] = 2 + 5 is exactly what the down-sweep needs

Down-Sweep

~5 min across the three sub-slides. This is the module’s hardest diagram — budget the full five minutes, don’t compress it. The pattern to emphasize: at each step, the left slot’s old value moves right and gets added there; the left slot receives whatever the right slot used to hold. Students who trace both phases by hand in Lab 11 report this is what finally makes the GPU kernel legible.

Set s[3] = 0:              [2, 7, 1, 0]

stride=2:
  tmp = s[1] = 7
  s[1] = s[3] = 0
  s[3] = tmp + s[3] = 7+0 = 7    → [2, 0, 1, 7]

stride=1:
  tmp=s[0]=2; s[0]=s[1]=0; s[1]=0+2=2   → [0, 2, 1, 7]
  tmp=s[2]=1; s[2]=s[3]=7; s[3]=7+1=8   → [0, 2, 7, 8]

Final: [0, 2, 7, 8]  ✓ matches the exclusive scan definition
  • The same active slots as the up-sweep, visited in reverse order (stride 2, then 1)
  • Each step is a swap-and-add: tmp = s[left], s[left] = s[right], s[right] += tmp

Why clear the root to 0?

  • The value flowing down into each slot means “the sum of everything to my left”
  • The root covers the whole array, and nothing is to the left of it, so it starts at 0, the identity for +
  • Going down, a left child inherits its parent’s “everything to my left”; a right child also adds its left sibling’s subtotal, which the up-sweep saved
  • Forgetting this step is the most common Blelloch bug: the output comes out offset by the total

~1 min. Verify the last bullet with the class: skipping the clear on [2, 5, 1, 8] gives [16, 18, 23, 24] — every value 16 too big. For CK-11’s max-scan, 0 is no longer the identity: ask what it should be (−∞), but don’t dwell — that’s the checkpoint.

The GPU Version

You port your Lab 11 CPU code to a kernel. The structure maps over directly:

CPU version (Lab 11 Exercise 3) GPU version
for tid in range(BLOCK): every thread runs the body once, with its own tid
a NumPy array shared, a shared-memory array
level d finishes before level 2d starts (automatic) you must make threads wait at the right points

The last row is the whole difficulty: a thread that races ahead to the next level can read a value a slower thread hasn’t written yet.

The up-sweep, as GPU code: the Nov 2 pattern, mirrored.

    d = 1
    while d < BLOCK:
        if tid % (2 * d) == 2 * d - 1:       # this level's active slots
            shared[tid] += shared[tid - d]
        cuda.syncthreads()                   # whole level done before the next
        d *= 2
  • The if is exactly the CPU condition. The for tid loop disappears: each thread is one tid
  • The barrier sits outside the if and runs every level, as in block_sum
  • Then, in Lab 11 Part 4, you write: the root clear (exactly one thread does it, then everyone waits), and the down-sweep, with the same one-level-at-a-time rule
