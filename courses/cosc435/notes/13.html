Beyond Element-wise: What Is a Stencil?

Element-wise (every kernel so far): output i depends only on input i. No thread ever looks at its neighbors.

Stencil: output i depends on a small neighborhood of inputs around i. The neighborhood’s half-width is the radius.

  • Classic examples: a moving average (each output = average of nearby inputs), image blur (each output pixel = weighted average of nearby pixels), numerical derivatives (a weighted combination of neighboring values)
  • The “one thread, one output” launch pattern (Oct 5) still applies. What changes is what each thread reads, not how many threads you launch
  • Neighborhoods overlap: in the figure, in[3] also feeds out[2] and out[4]. That’s harmless for correctness (threads only read shared inputs, and each writes its own output) — but it matters for speed, as we’ll see at the end

~3 min across both sub-slides. Frame this explicitly as “the launch pattern you already know, applied to a kernel body that reads more than one input” — students shouldn’t feel like they’re learning an entirely new launch mechanic, just a new kernel-body shape. The overlap bullet plants the Radius vs. Cost slide.

The Boundary Problem

Every interior cell has real neighbors on both sides. Cells near the edges do not.

  • A stencil reads a neighborhood around each position — but positions near the edge have neighbors that fall outside the array entirely
  • A kernel won’t warn you: arr[-1] silently becomes the last element (Python-style negative indexing — an accidental wrap), and arr[n] reads past the end with no error, because Numba CUDA does no bounds checking
  • Every stencil kernel needs an explicit boundary policy — there is no “correct” default, only different reasonable choices with different tradeoffs
Policy Out-of-range neighbor becomes… Array of 10: neighbor index −1 reads
Clamp the nearest valid edge value arr[0]
Zero-pad zero 0
Wrap the value from the other side (circular) arr[9]

Clamp: edges repeat themselves. No fake values enter the average, so a flat edge stays flat. The usual choice for images.

Zero-pad: missing neighbors add nothing. Simple, but averages near the edge get pulled toward 0 (an image blurred this way gets a dark border).

Wrap: the array is treated as a circle. Right for periodic data (angles, a ring of sensors, a tiling texture); wrong for a photo, where the left edge has nothing to do with the right.

~4 min across the three sub-slides. Don’t rush past “there is no correct default” — this is a genuine design decision, not a fact to memorize. Different applications legitimately prefer different policies (image processing usually clamps or wraps; some signal-processing contexts zero-pad). The no-bounds-checking bullet is why “just read arr[i-1]” isn’t an option: a negative index quietly wraps to the end of the array, and an index >= n reads whatever memory follows (garbage, or a later crash) instead of raising IndexError.

Our Policy: Clamping

def clamp(x, lo, hi):
    return min(max(x, lo), hi)

clamp(-1, 0, 9)   # → 0  (snapped up)
clamp(5, 0, 9)    # → 5  (unchanged)
clamp(15, 0, 9)   # → 9  (snapped down)

This course uses clamping (also called edge-replication) throughout. Any neighbor index outside [lo, hi] is snapped to the nearest valid edge.

Read it inside-out: max(x, lo) fixes indices that are too small (−1 → 0); then min(…, hi) fixes ones that are too large (15 → 9). An index already in range passes through both unchanged.

Edge values get their “missing” neighbors filled with a repeat of the nearest real value — not a fabricated zero or a wraparound.

A kernel can’t call an ordinary Python function like clamp() above. Two ways around it:

# Option 1: write the logic inline, right where the index is used
j = min(max(i + d, 0), n - 1)

# Option 2: compile the helper for the GPU as a *device function*
@cuda.jit(device=True)
def clamp(x, lo, hi):
    return min(max(x, lo), hi)
  • A device function runs on the GPU and is called from a kernel (it can’t be launched with [blocks, threads]), and it can return a value — a kernel can’t
  • Lab 7 writes the clamp inline, which is what the kernels on the next slides do

The other two policies, inside the same neighbor loop:

# zero-pad: only add neighbors that exist (missing ones count as 0)
j = i + d
if 0 <= j < n:
    total += arr[j]

# wrap: Python's % is never negative for positive n  (-1 % 10 == 9)
j = (i + d) % n
total += arr[j]

Zero-pad skips the read entirely when j is out of range. Skipping a tap is the same as adding 0 — and the guard keeps us from ever touching arr[-1].

Wrap uses % to fold the index back into 0 … n−1: -1 % 10 == 9 and 10 % 10 == 0. (C’s % can return negatives; Python’s — and Numba’s — can’t.)

CK-07 deliberately switches to zero-padding, so make sure you understand the policies themselves, not just one line of code.

~4 min across the three sub-slides. Numba CUDA kernels can only call other GPU-compiled code — a plain Python def fails with a TypingError, but a @cuda.jit(device=True) function works fine. Inlining is just the simplest option for a one-liner like clamp, and it’s what Lab 7 does. Wrap via % assumes radius < n (true in every lab/checkpoint here).

A 1D Warm-up: Moving Average

@cuda.jit
def moving_average_1d(arr, out, n, radius):
    i = cuda.grid(1)
    if i < n:
        total = numba.float32(0.0)
        for d in range(-radius, radius + 1):
            j = min(max(i + d, 0), n - 1)   # clamp
            total += arr[j]
        out[i] = total / (2 * radius + 1)
  • Lines 3–4: one thread, one output — the same global index and bounds guard as every 1D kernel since Oct 5
  • Line 5: a float32 accumulator — a plain 0.0 would make it float64, the slow-on-a-T4 trap from Lab 05
  • Line 6: d runs from -radius to +radius inclusive (range stops one short, hence radius + 1): 2*radius + 1 taps. Radius 2 → a 5-wide window
  • Line 7: the clamp, applied once per neighbor read, before the index is used
  • Line 8: accumulate the neighbor’s value
  • Line 9: divide by the full window size. Clamping always supplies 2*radius + 1 real values, so even the edges are a true average

Launching it on [10, 20, …, 100] with radius = 2:

arr = np.arange(10, 101, 10, dtype=np.float32)   # [10, 20, ..., 100]
n = arr.size
d_arr = cuda.to_device(arr)
d_out = cuda.device_array_like(d_arr)            # GPU array, same shape/dtype, no copy

threads = 32
blocks = (n + threads - 1) // threads            # ceiling division: 1 block here
moving_average_1d[blocks, threads](d_arr, d_out, n, 2)
print(d_out.copy_to_host())
[16. 22. 30. 40. 50. 60. 70. 80. 88. 94.]
  • The middle is a steady +10 (the input is a straight line, and averaging a straight line leaves it alone)
  • The ends are pulled toward the edge value: 16 instead of 30, 94 instead of 80. That’s clamping — the next slides trace exactly why

Trace i = 0, radius = 2:

The same trace as a table:

d −2 −1 0 1 2
i + d −2 −1 0 1 2
j (clamped) 0 0 0 1 2
arr[j] 10 10 10 20 30

out[0] = (10 + 10 + 10 + 20 + 30) / 5 = 16.0 — the first value printed above

  • Three of the five taps are the same repeated edge value — that’s the clamping policy visibly at work, not a bug
  • Try i = 9 yourself: j = 7, 8, 9, 9, 9 → (80 + 90 + 100 + 100 + 100) / 5 = 94.0

From 1D to 2D: Box Blur

@cuda.jit
def box_blur_2d(img, out, H, W, radius):
    row, col = cuda.grid(2)
    if row < H and col < W:
        total = numba.float32(0.0)
        for dr in range(-radius, radius + 1):
            for dc in range(-radius, radius + 1):
                r = min(max(row + dr, 0), H - 1)   # clamp row
                c = min(max(col + dc, 0), W - 1)   # clamp col
                total += img[r, c]
        out[row, col] = total / ((2 * radius + 1) ** 2)

What changed from the 1D version:

Lines 3–4: cuda.grid(2) gives each thread a (row, col) pair; the guard now checks both dimensions (Module 2’s 2D launch)

Lines 6–7: two nested loops: dr walks the rows of the window, dc its columns — a (2·radius+1) × (2·radius+1) square

Lines 8–9: the row and column are clamped independently: a pixel on the top edge clamps only r; a corner pixel clamps both

Line 11: divide by the number of taps, now the square of the window width

This is image convolution. A box blur is the simplest one: every neighbor weighted equally. (A Gaussian blur — Lab 7’s bonus — just multiplies each tap by a weight)

An interior pixel needs no clamping: all 9 taps are real pixels.

At the corner, 5 of the 9 taps fall off the image. Clamping turns them into reads of img[0,0] (×4 total), img[0,1] (×2) and img[1,0] (×2), plus the one real img[1,1].

A tiny test you can check by hand — a 4×4 image, radius = 1:

img = np.arange(16, dtype=np.float32).reshape(4, 4)   # rows: 0-3, 4-7, 8-11, 12-15
H, W = img.shape
d_img = cuda.to_device(img)
d_out = cuda.device_array_like(d_img)

threads = (16, 16)                                     # 256 threads per block
blocks = ((H + 15) // 16, (W + 15) // 16)              # (rows of blocks, cols of blocks)
box_blur_2d[blocks, threads](d_img, d_out, H, W, 1)
print(d_out.copy_to_host().round(2))
[[ 1.67  2.33  3.33  4.  ]
 [ 4.33  5.    6.    6.67]
 [ 8.33  9.   10.   10.67]
 [11.   11.67 12.67 13.33]]
  • Corner out[0,0] matches the figure: (4·img[0,0] + 2·img[0,1] + 2·img[1,0] + img[1,1]) / 9 = (0 + 2 + 8 + 5) / 9 ≈ 1.67
  • Interior out[1,1] = 5.0 — the plain average of the 3×3 block around it, no clamping

Radius vs. Cost

Radius Window size Taps per output pixel
1 3×3 9
2 5×5 25
4 9×9 81
8 17×17 289
  • Taps per pixel = \((2r+1)^2\): it grows with the square of the radius — doubling the radius roughly quadruples the memory reads and arithmetic per output
  • Lab 7 has you compare blur strength across a few radii and connect the visual result back to this table

Neighboring windows overlap: every input is read by 2r+1 threads in 1D, and (2r+1)² threads in 2D.

In the naive kernel each of those is a separate global-memory read of the same value. Loading a neighborhood once into fast on-chip memory is exactly what Module 4’s shared-memory tiling does.

~3 min across both sub-slides. Worth an explicit callback: “this naive stencil re-reads overlapping neighborhoods from global memory constantly, with heavy reuse between adjacent output pixels — sound familiar?” — it’s the same reuse-without-caching problem Oct 7’s naive-matmul diagnosis identified, just in a different kernel shape. (L1/L2 catch some of this reuse in practice, as they did for matmul; shared memory makes it explicit.)
