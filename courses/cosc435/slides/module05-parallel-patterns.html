Beyond Embarrassingly Parallel

So far, every kernel has had the same shape: thread i computes output i, from input i (or a small fixed neighbourhood, for stencils). No thread ever needs another thread’s result.

Some problems don’t fit that shape:

  • Sum all elements: the answer needs every input. No single thread can know the total
  • Find the maximum: same problem, a different combining operation
  • Running total (prefix sum): each output depends on all earlier inputs (Nov 9)

These need threads to communicate and combine partial results: a new kind of parallel pattern.

~3 min. These two patterns (reduction, and Nov 9’s prefix scan) appear constantly outside this course too — databases, compression, sorting, and nearly every non-trivial GPU algorithm use one or both. The capstone’s cp.argpartition internally relies on a reduction-like operation.

The Serial Approach, for Contrast

def serial_sum(arr):
    total = 0.0
    for x in arr:       # N steps, strictly sequential
        total += x
    return total
  • O(N) time, O(1) memory. Step 2 can’t start until step 1’s result is known
  • Porting this loop to the GPU as-is doesn’t help: one thread does all N additions while thousands sit idle
  • The question for today: can we restructure the computation so the work happens in parallel rounds?

~2 min. Emphasize “restructure,” not “parallelize as-is” — a common early misconception is that any serial loop can just run on more threads. This one specifically can’t, without changing the algorithm’s shape.

Tree Reduction: The Idea

~4 min across both sub-slides. Walk the three rounds out loud, stride by stride. Lab 10 Part 1 runs the same tree on [1, 2, …, 8] (total 36) — ask students to predict its rounds before Friday. This array is the one Lab 11 uses on Nov 13.

  • Pair values up and add all the pairs at once: one round of parallel work replaces many sequential additions
  • Each round halves the number of values still in play, so N values reduce to one in log₂(N) rounds
  • For N = 1,000,000: a serial sum takes 1,000,000 sequential steps; a tree takes about 20 rounds

The Stride-Halving Kernel

@cuda.jit
def block_sum(arr, out):
    s  = cuda.shared.array(shape=256, dtype=numba.float32)
    ti = cuda.threadIdx.x
    i  = cuda.grid(1)

    s[ti] = arr[i] if i < arr.shape[0] else numba.float32(0.0)
    cuda.syncthreads()

    stride = 128                 # blockDim.x // 2
    while stride > 0:
        if ti < stride:
            s[ti] += s[ti + stride]
        cuda.syncthreads()
        stride //= 2             # halve each round

    if ti == 0:
        out[cuda.blockIdx.x] = s[0]   # this block's sum

~3 min for the step-through, ~2 min for the next sub-slide. This is the kernel Lab 10 Part 2 runs (the lab version takes n as a third argument). Click through the highlights in order: load, the loop, the active threads, the barrier, the single write. Before the barrier highlight, ask “is this barrier legal?” — it’s outside the if, so yes (Module 4’s divergent-barrier trap).

  • Line 7: each thread loads one element into shared memory. Threads past the end load 0.0, the identity for addition, so they can’t change the sum
  • Lines 10–15: the diagram’s rounds: stride 128, 64, …, 1. That’s 8 rounds for 256 threads
  • Lines 12–13: only threads with ti < stride work: half as many each round
  • Line 14: a barrier every round: the next round reads values other threads just wrote. It sits outside the if, so every thread reaches it (Oct 26)
  • Lines 17–18: after the last round s[0] holds the block’s total, and one thread writes it out

Multi-Level Reduction

  • One launch gives one sum per block, not one for the whole array: out[blockIdx.x] is that block’s partial sum
  • For N = 1,000,000 with 256-thread blocks: (1,000,000 + 255) // 256 = 3,907 blocks, so 3,907 partial sums are left
  • Finishing needs a second pass: run the reduction again on the partial sums, or, since 3,907 values is small, copy them to the host and let NumPy finish

~3 min across both sub-slides. This two-pass (or GPU-then-CPU) pattern is ubiquitous in real GPU reduction code — it’s what cp.sum() (Module 6) does internally, optimized further than a hand-written version. That’s why the capstone uses CuPy’s built-in reductions rather than a hand-rolled kernel: this pattern, done well, is genuinely fiddly to get optimal.

One million ones, so every answer is easy to check:

N, BLOCK = 1_000_000, 256
n_blocks = (N + BLOCK - 1) // BLOCK                  # 3,907

arr_gpu        = cuda.to_device(np.ones(N, dtype=np.float32))
block_sums_gpu = cuda.device_array(n_blocks, dtype=np.float32)
block_sum[n_blocks, BLOCK](arr_gpu, block_sums_gpu)
cuda.synchronize()

block_sums_cpu = block_sums_gpu.copy_to_host()
total = block_sums_cpu.sum()          # finish the last, small reduction on the CPU
print(block_sums_cpu[:3], block_sums_cpu[-1])
print(int(total))
[256. 256. 256.] 64.0
1000000
  • Every full block sums to 256. The last block holds only 1,000,000 − 3,906 × 256 = 64 real values; its zero padding adds nothing

Work and Step Complexity

Algorithm Total work (operations) Steps (sequential rounds)
Serial sum O(N) O(N)
Tree reduction O(N) O(log N)
  • Both do the same total work: a tree doesn’t do fewer additions, it arranges the same N − 1 additions so many happen at once
  • The speedup comes entirely from parallelism, not from a “smarter” computation
  • A recurring theme: some parallel algorithms even do more total work than the serial version, and still win, because they need far fewer sequential steps. Wall-clock time is what matters

~2 min. Worth stating explicitly since it cuts against a common intuition: “parallel” doesn’t automatically mean “does less work” — it means “does the same (or more) work in fewer sequential rounds, using more processors at once.”

Different Combiners: Max and Dot Product

The tree’s shape doesn’t care how two values are combined. Swap += for another operation and the same stride-halving loop still works.

  • Maximum: s[ti] = max(s[ti], s[ti + stride]), and pad out-of-range threads with -math.inf, which can never win. Padding with 0.0 would win whenever every real value is negative. This is Lab 10 Exercise 3
  • Dot product: each thread first computes a[i] * b[i], then the products are reduced with += exactly as in block_sum. The capstone’s similarity scores are this same multiply-then-reduce shape

~3 min across both sub-slides. The identity value is the most common Lab 10 bug (0 instead of a very negative number) and is also what CK-10 checks: its data is all ≥ 100, so a 0.0 identity for min visibly wins.

Which operations work?

  • The tree combines values in a different order and grouping than a left-to-right loop: round 1 pairs s[0] with s[128]
  • So the operation must be associative, (a ⊕ b) ⊕ c == a ⊕ (b ⊕ c), and commutative, a ⊕ b == b ⊕ a. Sum, max and min are both
  • Would subtraction work?
  • No: (8 − 3) − 2 = 3, but 8 − (3 − 2) = 7. Changing the grouping changes the answer
  • Fine print: float32 addition is only almost associative (each step rounds). A GPU sum can differ from NumPy’s in the last few digits, which is why Lab 10 compares with a tolerance, not ==

~2 min. Ask the subtraction question and let them reason it out before the reveal. The float32 point pays off in Lab 10 Part 2, whose check is abs(gpu - cpu) < 1.0 on a million values.

Warp-Level Tricks

  • Once the stride drops to 32 or below, every thread still working is in warp 0 (warps from Sep 30)
  • Warp shuffle instructions (cuda.shfl_down_sync in Numba) let threads in one warp swap values register-to-register, without shared memory
  • Using shuffles for those last rounds skips the shared-memory traffic and the syncthreads() calls for the tail of the reduction: a real, measurable speedup

~3 min across both sub-slides. Intentionally awareness-level, not a skill the labs or checkpoints require — Lab 10’s block_sum uses syncthreads() every round, which is always correct, just not maximally fast. It’s here so students recognize the pattern in production CUDA code, not because it’s needed for CK-10.

A word of caution: you’ll see an older trick online that keeps using shared memory but drops syncthreads() once stride ≤ 32, because “the warp runs in lock-step anyway.”

  • That was true on older GPUs. Since Volta (2017), threads in a warp are scheduled independently, so the trick can silently give wrong sums
  • The shuffle instructions are the correct, current way to get this speedup
  • In this course, keep the barrier every round. It’s always correct

Session 2 · Nov 9 · Prefix Scan

Today’s Plan

  • A second cooperative pattern: every output depends on all earlier inputs, not just a combined total
  • Inclusive vs. exclusive scan, and why exclusive is usually more useful
  • The Blelloch algorithm: up-sweep and down-sweep, traced by hand before any code
  • Applications: stream compaction, histograms, sorting

~1 min. Full 50-min session, no quiz. This is a genuinely harder algorithm than reduction — budget extra time for the two hand-traced diagrams, don’t rush them.

What Is a Prefix Sum?

Input:              [2, 5, 1, 8, 3, 7, 4, 6]
Exclusive scan:     [0, 2, 7, 8, 16, 19, 26, 30]
  • Exclusive: output[i] = the sum of every input strictly before i. output[0] is always 0: nothing comes before it
  • Inclusive: output[i] = the sum of input[0..i], i included. What is it for this input?
Inclusive scan:     [2, 7, 8, 16, 19, 26, 30, 36]
  • Inclusive is exclusive shifted left by one, with the total (36) on the end
  • Exclusive is usually the useful one: it gives each element a ready-made offset to write at (next slide)

~3 min. Have students verify the first few exclusive outputs by hand from the input, then predict the inclusive row before revealing it — this cements “strictly before” vs. “up to and including” far better than the definition alone. This is the array students scan in Lab 11 Exercises 2–3.

Why Prefix Scan Matters

Stream compaction: keep only the values > 5 from [7, 2, 9, 4, 8], with no gaps.

values:           [7, 2, 9, 4, 8]
keep mask:        [1, 0, 1, 0, 1]
exclusive scan:   [0, 1, 1, 2, 2]     ← "how many kept values came before me"
  • Each kept value writes to out[scan[i]]: 7 → out[0], 9 → out[1], 8 → out[2]. Result: [7, 9, 8]
  • Every thread knows its own slot without talking to the others. You’ll do this in Lab 11’s bonus (Nov 13)

~3 min across both sub-slides. Stream compaction is the one application students actually build (Lab 11’s bonus) — the others on the next sub-slide are there so the pattern is recognizable by name later, not because they’re separately assessed.

Scan shows up inside many other algorithms:

  • Histograms: turning per-bin counts into starting offsets in one combined output array
  • Sorting: radix sort, a fast non-comparison sort, runs a scan on every digit pass
  • Dynamic allocation: threads that each need a variable-size chunk of one output buffer scan their sizes to get non-overlapping start offsets
  • You won’t implement all of these. The point: scan is a primitive, one algorithm that turns up, often invisibly, inside many others

The Serial Algorithm

def exclusive_scan_seq(arr):
    out = [0] * len(arr)
    running = 0
    for i in range(len(arr)):
        out[i] = running
        running += arr[i]
    return out
  • O(N) and strictly sequential: each output needs the running total of everything before it, which is why this looks impossible to parallelize
  • Lab 11 Exercise 1 has you write this function. Knowing it well is what makes the parallel version readable rather than magic
  • The rest of today answers one question: how can this run in O(log N) parallel rounds?

~2 min. Deliberately start here rather than jumping straight to Blelloch — the serial version being trivial is what makes the parallel version’s cleverness visible by contrast.

Blelloch Scan: Two Phases

The Blelloch exclusive scan works in two phases, each O(log N) rounds:

  1. Up-sweep (reduce): build partial sums bottom-up, with the same tree as Nov 2’s reduction
  2. Down-sweep: push those partial sums back down, turning them into prefix values

Total: O(N) work, O(log N) steps. The same as tree reduction, for a harder problem.

~2 min. Point out explicitly: up-sweep is the reduction algorithm from Nov 2, run for its side effects (the partial sums left behind at each level) rather than just its final total. Students who understood Nov 2 already understand half of this algorithm.

Up-Sweep on [2, 5, 1, 8]

~4 min across both sub-slides. Lab 11 Exercise 2 has students run this on the full 8-element array from “What Is a Prefix Sum?”. Walk through this 4-element version first to establish the index pattern. Contrast with Nov 2: reduction pairs s[t] with s[t + stride] and works toward s[0]; the up-sweep pairs s[t] with s[t − stride] and works toward the last slot. Same tree, mirrored.

Initial:  [2, 5, 1, 8]
stride=1: s[1] += s[0] → [2, 7, 1, 8]
          s[3] += s[2] → [2, 7, 1, 9]
stride=2: s[3] += s[1] → [2, 7, 1, 16]
Result:   [2, 7, 1, 16]   ← s[3] = total sum
  • The active slots are the ones where (t + 1) is a multiple of 2 × stride: slots 1 and 3, then slot 3
  • Each active slot adds the value stride places to its left
  • Unlike Nov 2’s reduction, the intermediate sums stay in place: s[1] = 2 + 5 is exactly what the down-sweep needs

Down-Sweep

~5 min across the three sub-slides. This is the module’s hardest diagram — budget the full five minutes, don’t compress it. The pattern to emphasize: at each step, the left slot’s old value moves right and gets added there; the left slot receives whatever the right slot used to hold. Students who trace both phases by hand in Lab 11 report this is what finally makes the GPU kernel legible.

Set s[3] = 0:              [2, 7, 1, 0]

stride=2:
  tmp = s[1] = 7
  s[1] = s[3] = 0
  s[3] = tmp + s[3] = 7+0 = 7    → [2, 0, 1, 7]

stride=1:
  tmp=s[0]=2; s[0]=s[1]=0; s[1]=0+2=2   → [0, 2, 1, 7]
  tmp=s[2]=1; s[2]=s[3]=7; s[3]=7+1=8   → [0, 2, 7, 8]

Final: [0, 2, 7, 8]  ✓ matches the exclusive scan definition
  • The same active slots as the up-sweep, visited in reverse order (stride 2, then 1)
  • Each step is a swap-and-add: tmp = s[left], s[left] = s[right], s[right] += tmp

Why clear the root to 0?

  • The value flowing down into each slot means “the sum of everything to my left”
  • The root covers the whole array, and nothing is to the left of it, so it starts at 0, the identity for +
  • Going down, a left child inherits its parent’s “everything to my left”; a right child also adds its left sibling’s subtotal, which the up-sweep saved
  • Forgetting this step is the most common Blelloch bug: the output comes out offset by the total

~1 min. Verify the last bullet with the class: skipping the clear on [2, 5, 1, 8] gives [16, 18, 23, 24] — every value 16 too big. For CK-11’s max-scan, 0 is no longer the identity: ask what it should be (−∞), but don’t dwell — that’s the checkpoint.

The GPU Version

You port your Lab 11 CPU code to a kernel. The structure maps over directly:

CPU version (Lab 11 Exercise 3) GPU version
for tid in range(BLOCK): every thread runs the body once, with its own tid
a NumPy array shared, a shared-memory array
level d finishes before level 2d starts (automatic) you must make threads wait at the right points

The last row is the whole difficulty: a thread that races ahead to the next level can read a value a slower thread hasn’t written yet.

    d = 1
    while d < BLOCK:

Session 3 · Nov 11 · Histograms & Atomic Operations

Today’s Plan

  • A third cooperative pattern: many threads that may update the same memory location, chosen at runtime
  • Why the naive version is a race condition, and why reduction and scan never had one
  • Atomic operations: the hardware-guaranteed fix
  • A worked example: a histogram, and how to make it fast

~1 min. Full 50-min session, no quiz. This closes out Module 5’s three cooperative patterns: combine-to-one (reduction), propagate-outward (scan), and now many-to-one-of-several (atomics/histograms).

A New Kind of Conflict

  • In reduction and scan, the addresses written each round are known in advance and never overlap: no two threads write the same slot in one round
  • A histogram breaks that: each thread looks at one value, decides its bin, and adds 1 to that bin’s count. Which bin depends on the data, not on the thread’s index
  • Two threads can easily hit the same bin at the same time: both need to increment counts[5]
  • So collisions are unpredictable and data-dependent, not the clean tree of reduction or scan

~3 min. Frame this explicitly as “the third pattern” completing the module — students should leave recognizing reduction (combine to one), scan (propagate to all), and atomics (handle unpredictable collisions) as three distinct answers to “how do threads cooperate,” not one topic that happens to have three examples.

The Race Condition, Concretely

@cuda.jit
def histogram_broken(bins, counts):
    i = cuda.grid(1)
    if i < bins.shape[0]:
        b = bins[i]             # this value's bin (already an integer here)
        counts[b] += 1          # BROKEN: see next slide
  • counts[b] += 1 looks like one operation, but the hardware runs it as three: read counts[b], add 1, write it back
  • Two threads with the same b can both read before either writes. What happens then?

~3 min across both sub-slides. Let students answer the question before advancing. This is the same read-modify-write race idea as Module 4’s shared-memory races — here in global memory, and caused by data-dependent collisions rather than a missing syncthreads().

  • With many threads and many collisions, the histogram undercounts, and by a different amount each run, because the interleaving isn’t deterministic

Atomic Operations: The Fix

@cuda.jit
def histogram_atomic(bins, counts):
    i = cuda.grid(1)
    if i < bins.shape[0]:
        b = bins[i]
        cuda.atomic.add(counts, b, 1)   # read-modify-write as ONE indivisible step
  • cuda.atomic.add(array, index, value) does the whole read-modify-write as one indivisible hardware operation: no other thread can see or interfere with it halfway
  • Two threads adding to the same address at the same moment are serialized: one finishes completely, then the other. No lost updates
  • The rule: whenever several threads might write the same address, replace += with the atomic version

~3 min. Emphasize “indivisible,” not “fast” — atomics fix correctness, they don’t make the operation cheap (The Cost of Atomics, below). The syntax is simple; the concept (why it’s needed, what “indivisible” guarantees) is the real content.

A Complete Histogram Kernel

Values in [0, 1), counted into 10 equal-width bins:

NUM_BINS = 10

@cuda.jit
def histogram(values, counts):
    i = cuda.grid(1)
    if i < values.shape[0]:
        b = int(values[i] * NUM_BINS)          # 0.37 → bin 3
        b = max(0, min(b, NUM_BINS - 1))       # clamp into [0, NUM_BINS - 1]
        cuda.atomic.add(counts, b, 1)
  • Each thread computes its own bin, then atomically adds 1. No other coordination is needed
  • The clamp keeps an out-of-range value (exactly 1.0, or a small negative) from writing outside counts. Same habit as Module 3’s stencil boundaries

~3 min across both sub-slides. Worth a live demo if time allows.

rng    = np.random.default_rng(0)
values = rng.random(10_000).astype(np.float32)

threads = 256
blocks  = (values.size + threads - 1) // threads
counts_gpu = cuda.to_device(np.zeros(NUM_BINS, dtype=np.int32))   # must start at 0
histogram[blocks, threads](cuda.to_device(values), counts_gpu)
cuda.synchronize()

print(counts_gpu.copy_to_host())
print(np.histogram(values, bins=NUM_BINS, range=(0, 1))[0])
[1033 1016  959  988  994 1029  980  980 1041  980]
[1033 1016  959  988  994 1029  980  980 1041  980]
  • An exact match with NumPy, every run. The plain += version would come out lower, and differently each time
  • counts_gpu must be zero-initialized: atomics add to whatever is already there, they never reset it

Atomics Beyond Addition

Numba has other atomics with the same indivisible read-modify-write guarantee:

  • cuda.atomic.max(array, index, value) / cuda.atomic.min(...): for many threads updating a shared “best so far”
  • cuda.atomic.cas(array, index, old, new) (compare-and-swap): “write new only if the value still equals old”. Most other atomics, and lock-free algorithms in general, are built from it
  • Whenever several threads might write the same, data-dependent location, you need an atomic, or a redesign that avoids the collision

~2 min. Keep this at the level of “these exist and follow the same pattern as atomic.add” — no worked example for each; the histogram already carries the core idea. Avoid the older cuda.atomic.compare_and_swap(array, old, new) — it only operates on array[0].

The Cost of Atomics

  • Atomics stay correct by serializing conflicting updates. Many threads hitting the same address at once wait in line, much like Module 4’s bank conflicts
  • Few bins, many threads (10 bins, a million threads): heavy contention, most threads waiting on a handful of addresses
  • Many bins relative to threads: collisions are rare, little waiting
  • The trade-off: plain += was fast and wrong; atomics are always right, and how fast depends on how much contention your data causes

~2 min. This is the last of three techniques (bounds guards, syncthreads, atomics) that all trade a little overhead for correctness — worth naming that pattern explicitly as something students have now seen three times.

Reducing Contention: Private Histograms

Give each block its own shared-memory histogram, then merge it into the global one:

@cuda.jit
def histogram_private(values, counts):
    local = cuda.shared.array(NUM_BINS, numba.int32)   # this block's histogram
    ti = cuda.threadIdx.x
    if ti < NUM_BINS:
        local[ti] = 0
    cuda.syncthreads()

    i = cuda.grid(1)
    if i < values.shape[0]:
        b = max(0, min(int(values[i] * NUM_BINS), NUM_BINS - 1))
        cuda.atomic.add(local, b, 1)          # contention only within this block
    cuda.syncthreads()

    if ti < NUM_BINS:
        cuda.atomic.add(counts, ti, local[ti])   # one global atomic per bin per block

~3 min across both sub-slides. Awareness-level, not in a lab or checkpoint — but it ties Module 4 (shared memory + barriers) to today, and it’s the standard real-world fix. Verified in the CUDA simulator: same output as histogram on the previous example. It assumes threads per block ≥ NUM_BINS.

  • Atomics on shared memory are much cheaper than on global memory, and only this block’s 256 threads compete for each bin
  • Global atomics drop from one per value (10,000) to one per bin per block (40 blocks × 10 = 400)
  • Both barriers matter: the first so nobody counts into an uncleared bin, the second so the merge doesn’t read a half-finished local histogram
  • This is the pattern again: privatize, combine locally, merge once, the same idea as a reduction’s per-block partial sums
