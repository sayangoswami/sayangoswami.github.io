Session 1 · Nov 2 · Parallel Reduction

Today’s Plan

  • Why some problems can’t use the “every thread independent” pattern from Modules 2-4
  • Tree reduction: combining N values down to one, in log(N) parallel rounds instead of N sequential steps
  • The reduction kernel, applied to sum, max, and (conceptually) dot product
  • A warp-level optimization for the final few rounds

~1 min. Full 50-min session — no quiz today (Quiz 5 opens at the start of Lab 10, Nov 6, not this lecture). This session is the conceptual pivot of the module: everything since Module 2 has been “one thread, one independent output” — today breaks that assumption for the first time.

Beyond Embarrassingly Parallel

  • So far, every kernel has followed the same shape: thread i computes output i, using only input i (or a small fixed neighborhood, for stencils) — no thread needs any other thread’s result
  • Some problems don’t fit that shape at all:
    • Sum all elements → the answer requires combining every input; no single thread can know the total on its own
    • Find the maximum → same problem, different combining operation
    • Running total (prefix sum) → each output depends on all prior inputs (Nov 9)
  • These problems need threads to communicate and combine partial results — a genuinely different kind of parallel pattern from anything so far this semester

~3 min. These two patterns (reduction, and Nov 9’s prefix scan) appear constantly outside this course too — databases, compression, sorting, and nearly every non-trivial GPU algorithm use one or both. The capstone’s cp.argpartition internally relies on a reduction-like operation.

The Serial Approach, for Contrast

def serial_sum(arr):
    total = 0.0
    for x in arr:       # N steps, strictly sequential
        total += x
    return total
  • O(N) time, O(1) memory — simple, and completely sequential: step 2 can’t start until step 1’s result is known
  • Naively porting this to the GPU doesn’t help: one thread would do all N additions while thousands of others sit idle
  • The question this session answers: can we restructure the computation itself — not just throw more threads at the same sequential recipe — so that work happens in parallel rounds?

~2 min. Emphasize “restructure,” not “parallelize as-is” — a common early misconception is that any serial loop can just run on more threads. This one specifically can’t, without changing the algorithm’s shape.

Tree Reduction: The Idea

[DIAGRAM] — 8 elements in a row: [3, 1, 4, 1, 5, 9, 2, 6]. Three rounds drawn as successive rows beneath, each with arrows connecting pairs from the row above into a single combined value below. Round 1 (stride 4): arrows connect position 0↔︎4, 1↔︎5, 2↔︎6, 3↔︎7, producing [8, 10, 6, 7]. Round 2 (stride 2): arrows connect position 0↔︎2, 1↔︎3 of that new row, producing [14, 17]. Round 3 (stride 1): one arrow connects the remaining pair, producing [31]. Caption: “3 rounds for 8 elements = log₂(8).”

  • Instead of adding elements one at a time, pair them up and add all pairs simultaneously — one round of parallel work replaces many sequential additions
  • Each round halves the number of “active” values remaining, so N elements reduce to one in log₂(N) rounds, not N
  • For N = 1,000,000: a serial sum takes 1,000,000 sequential steps; tree reduction takes about 20 parallel rounds

~4 min. Walk the diagram’s three rounds out loud, stride value by stride value — students trace this exact 8-element example by hand in Lab 10 before writing any code.

The Stride-Halving Kernel

@cuda.jit
def block_sum(arr, out):
    s = cuda.shared.array(shape=256, dtype=numba.float32)
    ti = cuda.threadIdx.x
    i  = cuda.grid(1)

    s[ti] = arr[i] if i < arr.shape[0] else 0.0
    cuda.syncthreads()

    stride = 128         # blockDim.x // 2
    while stride > 0:
        if ti < stride:
            s[ti] += s[ti + stride]
        cuda.syncthreads()
        stride //= 2      # halve each round
    if ti == 0:
        out[cuda.blockIdx.x] = s[0]   # this block's sum, in one element
  • Each thread loads one element into shared memory (Module 4), padding out-of-range threads with the additive identity (0.0) so they don’t corrupt the sum
  • Every round, only the threads with ti < stride do work — that’s exactly half as many active threads as the previous round, matching the diagram above
  • syncthreads() after every round is required: a thread reading s[ti + stride] must wait until whichever thread wrote it in the previous round has finished (Module 4’s shared-memory rules apply here directly)

~3 min. This is the exact kernel Lab 10 has students build up piece by piece. Walk through it in the same order as the code: load-to-shared, the stride loop, the single-thread final write. Emphasize only thread 0 writes the result — every other thread in the block does useful work during the loop but writes nothing at the end.

Multi-Level Reduction

  • One kernel launch gives you one sum per block, not one sum for the whole array — out[blockIdx.x] holds that block’s partial result
  • For N = 1,000,000 with 256-thread blocks: (1,000,000 + 255) // 256 = 3,907 blocks, so 3,907 partial sums remain after one kernel launch, not the single total you actually want
  • Getting the final answer needs a second pass: either launch the same reduction kernel again on the array of partial sums (repeating until one value remains), or — since 3,907 values is small — just copy them to the host and let NumPy finish the job
block_sums_gpu = cuda.device_array(n_blocks, dtype=np.float32)
block_sum[n_blocks, BLOCK](arr_gpu, block_sums_gpu)
cuda.synchronize()

block_sums_cpu = block_sums_gpu.copy_to_host()
total = block_sums_cpu.sum()   # finish the last, small reduction on the CPU

~3 min. This two-pass (or GPU-then-CPU) pattern is ubiquitous in real GPU reduction code — it’s exactly what cp.sum() (Module 6) does internally, optimized further than a hand-written version. That’s why the capstone uses CuPy’s built-in reductions rather than a hand-rolled kernel: this pattern, done well, is genuinely fiddly to get optimal.

Work and Step Complexity

Algorithm Total work (operations) Steps (sequential rounds)
Serial sum O(N) O(N)
Tree reduction O(N) O(log N)
  • Both algorithms do the same total amount of work — tree reduction doesn’t do fewer additions overall, it does the same additions arranged so many happen simultaneously
  • The speedup comes entirely from parallelism (many operations at once), not from an algorithmically “smarter” computation
  • This is a recurring theme in parallel algorithms: sometimes the total work even goes up compared to the serial version, and that’s still a win if it converts into far fewer sequential steps — wall-clock time is what matters, not operation count

~2 min. Worth stating explicitly since it cuts against a common intuition: “parallel” doesn’t automatically mean “does less work” — it means “does the same (or more) work in fewer sequential rounds, using more processors at once.”

Different Combiners: Max and Dot Product

  • The tree-reduction shape doesn’t care what operation combines two values — swap += for a different associative operation and the exact same stride-halving pattern still works
  • Maximum: replace s[ti] += s[ti + stride] with s[ti] = max(s[ti], s[ti + stride]), and pad out-of-range threads with a very negative identity value (-1e9) instead of 0.0 — this is Lab 10 Exercise 3
  • Dot product: compute a[i] * b[i] per thread first, then reduce those products with += exactly as in block_sum — this is the same “multiply then reduce” shape as the capstone’s similarity computation, just done with a hand-written kernel instead of CuPy’s Q @ D.T
  • The requirement is associativity: (a ⊕ b) ⊕ c == a ⊕ (b ⊕ c), so it doesn’t matter which order pairs get combined in — addition, max, and min all qualify; subtraction does not

~3 min. The associativity requirement is worth naming explicitly and briefly testing student intuition on — ask “would this trick work for subtraction?” and let them reason out why not (order-dependence breaks the tree’s freedom to combine pairs in any order).

Warp-Level Tricks

  • Once a reduction’s stride drops to 32 or below, every remaining active thread belongs to a single warp (Sep 30) — and a warp already executes in lock-step, one instruction at a time, across all its lanes
  • Modern CUDA offers warp shuffle instructions (cuda.shfl_down_sync in Numba) that let threads within one warp exchange values directly, register-to-register, without ever touching shared memory at all
  • Using shuffle for a reduction’s final few rounds skips the shared-memory read/write and the syncthreads() call entirely for that portion — a real, measurable speedup on the “small stride” tail of the reduction
  • A word of caution: an older, informal trick claims you can also just skip syncthreads() once stride ≤ 32 while still using shared memory, reasoning that “the warp is lock-step anyway.” This is no longer reliably safe on modern GPU architectures (Volta and later independently schedule threads within a warp) — the shuffle-instruction approach above is the correct, current way to get this optimization

~3 min. This slide is intentionally awareness-level, not a skill this course’s labs or checkpoints require — Lab 10’s block_sum uses syncthreads() for every round, which is always correct, just not maximally fast. Flag explicitly that this is here so students recognize the pattern in production CUDA code, not because it’s required for CK-10.

Session 2 · Nov 9 · Prefix Scan

Today’s Plan

  • A second cooperative pattern: every output depends on all prior inputs, not just a combined total
  • Inclusive vs. exclusive scan, and why the exclusive version is usually more useful
  • The Blelloch algorithm: up-sweep and down-sweep, traced by hand before any code
  • Real applications: stream compaction, histograms, sorting

~1 min. Full 50-min session, no quiz. This is a genuinely harder algorithm than reduction — budget extra time for the two hand-traced diagrams, don’t rush them.

What Is a Prefix Sum?

Input:              [2, 5, 1, 8, 3, 7, 4, 6]
Exclusive scan out: [0, 2, 7, 8, 16, 19, 26, 30]
  • output[i] = the sum of every input strictly before index i — output[0] is always 0 (nothing comes before the first element)
  • Contrast with inclusive scan, where output[i] = sum of input[0..i] (index i included): [2, 7, 8, 16, 19, 26, 30, 36] for the same input
  • The exclusive version is usually the more directly useful one in parallel algorithms — it gives each element a ready-made “slot” or “offset” to write into, which is exactly what stream compaction (below) needs

~3 min. Have students verify the first few outputs by hand from the input list before revealing the diagram — this cements “strictly before” (exclusive) vs. “up to and including” (inclusive) far better than the definition alone.

Why Prefix Scan Matters

  • Stream compaction: given a boolean mask of which elements survive, exclusive scan of the mask gives each surviving element its exact output position — you built and used exactly this in Lab 11’s bonus exercise
  • Histogram computation: converting per-bin counts into cumulative offsets (where does each bin’s data start, in a combined output array) is a prefix scan
  • Sorting: radix sort — a fast, non-comparison-based sorting algorithm — uses prefix scan internally at every digit pass
  • Dynamic allocation: when many threads each need a variable-size chunk of a shared output buffer, exclusive scan of the requested sizes gives every thread its own non-overlapping starting offset
  • You are not expected to implement all of these applications — the point is that prefix scan is a primitive: one algorithm that shows up, often invisibly, inside many others

~2 min. Stream compaction is the one application students actually build (Lab 11’s bonus) — the others are here so the pattern is recognizable by name later, not because they’re separately assessed.

The Serial Algorithm

def exclusive_scan_seq(arr):
    out = [0] * len(arr)
    running = 0
    for i in range(len(arr)):
        out[i] = running
        running += arr[i]
    return out
  • Straightforward and O(N) sequential — each output depends on the running total built up from everything before it, which is exactly what makes this look hard to parallelize at first glance
  • Lab 11 Exercise 1 has you write this exact function — understanding this version thoroughly is what makes the parallel version (next) legible, rather than a magic trick
  • The whole rest of this session is answering one question: how do you compute something that looks inherently sequential using O(log N) parallel rounds instead?

~2 min. Deliberately start here rather than jumping straight to Blelloch — the serial version being trivial is what makes the parallel version’s cleverness visible by contrast.

Blelloch Scan: Two Phases

The Blelloch exclusive scan solves this in two phases, both O(log N) rounds:

  1. Up-sweep (reduce): build partial sums bottom-up — the exact same tree shape as Nov 2’s reduction
  2. Down-sweep: propagate those partial sums back down top-to-bottom, converting them into prefix values

Total: O(N) work, O(log N) steps — same complexity class as tree reduction, for a harder problem.

~2 min. Point out explicitly: up-sweep is literally the reduction algorithm from Nov 2, run for its side effects (the partial sums left behind at each level) rather than just its final total. Students who understood Nov 2 already understand half of this algorithm.

Up-Sweep on [2, 5, 1, 8]

[DIAGRAM] — Four boxes in a row holding 2, 5, 1, 8, with two rounds drawn beneath as tree-reduction-style arrows. Round 1 (stride 1): an arrow from box 0 into box 1 (box 1 becomes 2+5=7), and an arrow from box 2 into box 3 (box 3 becomes 1+8=9) — boxes now read 2, 7, 1, 9. Round 2 (stride 2): an arrow from box 1 into box 3 (box 3 becomes 7+9=16) — boxes now read 2, 7, 1, 16. Caption: “s[3] = 16 = the total sum of all four elements — same result the Nov 2 reduction tree would produce, but the intermediate partial sums (7, 9) are kept, not discarded.”

Initial:  [2, 5, 1, 8]
stride=1: s[1] += s[0] → [2, 7, 1, 8]
          s[3] += s[2] → [2, 7, 1, 9]
stride=2: s[3] += s[1] → [2, 7, 1, 16]
Result:   [2, 7, 1, 16]   ← s[3] = total sum

~4 min. Lab 11 Exercise 2 has students trace this on the full 8-element array from the “What Is a Prefix Sum” slide. Walk through this simpler 4-element version here first to establish the index pattern before scaling up.

Down-Sweep

[DIAGRAM] — The same four boxes, starting from the up-sweep’s final state [2, 7, 1, 16], with the last box first reset to 0: [2, 7, 1, 0]. Round 1 (stride 2): an arrow shows box 1’s value (7) moving into box 3, while box 1 simultaneously receives box 3’s old value (0) — resulting in box 3 = 7 + 0 = 7, box 1 = 0: state becomes [2, 0, 1, 7]. Round 2 (stride 1): two simultaneous swap-and-add operations, box 0↔︎1 and box 2↔︎3, following the same swap pattern — final state [0, 2, 1, 7] then combined to [0, 2, 7, 8]. Caption: “Each step: the left partner’s old value moves right and gets added; the left partner receives the right partner’s old value.”

Set s[3] = 0:              [2, 7, 1, 0]

stride=2:
  tmp = s[1] = 7
  s[1] = s[3] = 0
  s[3] = tmp + s[3] = 7+0 = 7    → [2, 0, 1, 7]

stride=1:
  tmp=s[0]=2; s[0]=s[1]=0; s[1]=0+2=2   → [0, 2, 1, 7]
  tmp=s[2]=1; s[2]=s[3]=7; s[3]=7+1=8   → [0, 2, 7, 8]

Final: [0, 2, 7, 8]  ✓ matches the exclusive scan definition

~5 min. This is the module’s hardest diagram — budget the full five minutes, don’t compress it. The pattern to emphasize: at each swap-and-add step, the left position’s old value is what moves to the right (and gets added there); the left position then receives whatever the right position used to hold. Students who trace both phases by hand in Lab 11 report this is what finally makes the GPU kernel (next slide) legible.

The GPU Version

BLOCK = 16

@cuda.jit
def exclusive_scan_gpu(arr, out):
    s   = cuda.shared.array(shape=BLOCK, dtype=numba.float32)
    ti  = cuda.threadIdx.x
    i   = cuda.grid(1)

    s[ti] = arr[i] if i < arr.shape[0] else 0.0
    cuda.syncthreads()

    # Up-sweep
    stride = 1
    while stride < BLOCK:
        if (ti + 1) % (stride * 2) == 0:
            s[ti] += s[ti - stride]
        cuda.syncthreads()
        stride *= 2

    # Clear root — this is the single most-forgotten step
    if ti == BLOCK - 1:
        s[ti] = 0.0
    cuda.syncthreads()

    # Down-sweep
    stride = BLOCK // 2
    while stride > 0:
        if (ti + 1) % (stride * 2) == 0:
            tmp            = s[ti - stride]
            s[ti - stride] = s[ti]
            s[ti]          = tmp + s[ti]
        cuda.syncthreads()
        stride //= 2

    if i < out.shape[0]:
        out[i] = s[ti]
  • Every line here is one of the two hand-traced diagrams above, translated directly into indexing arithmetic — the (ti + 1) % (stride * 2) == 0 condition is just “which positions are active at this stride,” the same positions the diagrams marked with arrows
  • Lab 11 Part 4 gives you this kernel pre-written and asks you to verify it against your own hand trace — the goal is confirming understanding, not re-deriving the indexing from scratch under time pressure

~3 min. Point at the “clear root” line specifically — Lab 11’s own instructor notes flag this as the single most-forgotten step by students attempting this from memory. It’s the one line that has no analogue in the up-sweep and is easy to skip if you’re pattern-matching rather than reasoning through the algorithm.

Session 3 · Nov 11 · Histograms & Atomic Operations

Today’s Plan

  • A third cooperative pattern: many threads that might all want to update the same memory location, at a location not known until runtime
  • Why the naive version of this is a race condition — reduction and scan don’t have this problem, and this pattern shows why they were special cases
  • Atomic operations: the hardware-guaranteed fix
  • A worked example: computing a histogram

~1 min. Full 50-min session, no quiz. This closes out Module 5’s three cooperative patterns: combine-to-one (reduction), propagate-outward (scan), and now many-to-one-of-several (atomics/histograms).

A New Kind of Conflict

  • Reduction and scan both have a property that made them tractable: at every step, the set of memory locations being written is known in advance and non-overlapping — no two threads in the same round ever write the same address
  • A histogram breaks that property: given a stream of values, each thread looks at one value, decides which “bin” it belongs to, and increments that bin’s counter — but which bin depends on the data itself, not on the thread’s index
  • Two different threads can easily land on the same bin at the same time — say, two threads both processing a value that falls in bin 5 — and both need to increment counts[5]
  • This is a fundamentally different problem: unpredictable, data-dependent collisions, not the clean tree structure of reduction or scan

~3 min. Frame this explicitly as “the third pattern” completing the module — students should leave recognizing reduction (combine to one), scan (propagate to all), and atomics (handle unpredictable collisions) as three distinct answers to “how do threads cooperate,” not one topic that happens to have three examples.

The Race Condition, Concretely

@cuda.jit
def histogram_broken(values, counts):
    i = cuda.grid(1)
    if i < values.shape[0]:
        bin_idx = values[i]           # which bin does this value belong to?
        counts[bin_idx] += 1          # BROKEN — see below
  • counts[bin_idx] += 1 looks like one operation, but the hardware executes it as three: read counts[bin_idx], add 1 to that value, write the result back
  • If two threads both target the same bin_idx at nearly the same time, both can read the same starting value before either has written their update back — both then write back old_value + 1, and one of the two increments is silently lost
  • With enough threads and enough collisions, a histogram built this way undercounts — every run potentially giving a slightly different (wrong) answer, since the exact interleaving of threads is not deterministic

~3 min. This is the same read-modify-write race condition idea introduced very briefly for shared memory in Module 4 — here it’s global memory, and the collision is data-dependent rather than a missing syncthreads(). Worth drawing the two-thread interleaving out explicitly: Thread A reads 5, Thread B reads 5 (before A writes), A writes 6, B writes 6 — the count should be 7, but ends at 6.

Atomic Operations: The Fix

from numba import cuda

@cuda.jit
def histogram_correct(values, counts):
    i = cuda.grid(1)
    if i < values.shape[0]:
        bin_idx = values[i]
        cuda.atomic.add(counts, bin_idx, 1)   # read-modify-write, guaranteed indivisible
  • cuda.atomic.add(array, index, value) performs the entire read-modify-write as one indivisible hardware operation — no other thread can observe or interfere with it partway through
  • If two threads call atomic.add on the same address at the same moment, the hardware serializes them: one fully completes, then the other — never an interleaved, lost update
  • This is the general fix for exactly the race condition on the previous slide — replace the naive += with the atomic version whenever multiple threads might write the same address

~3 min. Emphasize “indivisible,” not “fast” — atomics fix correctness, they don’t inherently make the operation cheap (next-to-last slide covers the cost). The syntax itself is simple; the concept (why it’s needed, what “indivisible” guarantees) is the real content here.

A Complete Histogram Kernel

NUM_BINS = 10

@cuda.jit
def histogram(values, counts):
    i = cuda.grid(1)
    if i < values.shape[0]:
        bin_idx = min(int(values[i] * NUM_BINS), NUM_BINS - 1)   # clamp to valid range
        cuda.atomic.add(counts, bin_idx, 1)

# Launch
counts_gpu = cuda.to_device(np.zeros(NUM_BINS, dtype=np.int32))
histogram[blocks, threads](values_gpu, counts_gpu)
cuda.synchronize()
  • Each of potentially millions of threads independently computes which bin its value belongs to, then atomically increments that bin — no coordination between threads needed beyond the atomic operation itself
  • counts_gpu must be zero-initialized before the kernel runs — atomics increment whatever is already there, they don’t reset it
  • Notice the bin-index computation clamps into [0, NUM_BINS-1] — same “handle the edge case explicitly” habit as Module 3’s stencil boundary conditions, just for a different kind of edge case

~2 min. This is a complete, runnable pattern — worth a live demo if time allows, generating random data and confirming the GPU histogram matches np.histogram on the same data.

Atomics Beyond Addition

  • cuda.atomic.add is the most common atomic, but Numba provides others for the same indivisible-read-modify-write guarantee with different combining operations:
    • cuda.atomic.max(array, index, value) / cuda.atomic.min(...) — atomic maximum/minimum, useful whenever many threads might all want to update a shared “best so far” value
    • cuda.atomic.compare_and_swap(array, old, new) — the building block many other atomics (and lock-free algorithms generally) are built from: “update this value only if it still equals what I expect”
  • Anywhere multiple threads might write to the same, data-dependent location — not a fixed, thread-indexed location like every kernel before this session — an atomic operation (or a redesign to avoid the collision entirely) is required for correctness

~2 min. Keep this at the level of “these exist and follow the same pattern as atomic.add” — no worked example needed for each; the histogram example already carries the core idea.

The Cost of Atomics

  • Atomics guarantee correctness by serializing conflicting operations — which means heavy contention (many threads atomically writing the same address at the same time) can become a real bottleneck, similar in spirit to Module 4’s bank conflicts
  • A histogram with very few bins and a huge number of threads (e.g. 10 bins, a million threads) will see enormous contention — most threads end up waiting in line for the same handful of addresses
  • A histogram with many bins relative to thread count sees far less contention, since collisions become statistically rare
  • This is a genuine performance/correctness tradeoff: atomics are always correct, but not always fast — the naive version from two slides ago was fast (no serialization) and wrong; the atomic version is always right, and its speed depends on how much actual contention your specific data causes

~2 min. Good closing thought for the module: this is the last of three techniques (bounds guards, syncthreads, atomics) that all trade a small amount of overhead for correctness — worth naming that pattern explicitly as something students have now seen three times.
