The Full Pipeline, End to End

Disk (JPEG/PNG file)
   │  decode — turn compressed bytes into a raw pixel array
   ▼
Host (NumPy array, shape (H, W, 3), uint8)
   │  cuda.to_device() / cp.asarray()          ← Module 2 / Module 6
   ▼
Device (GPU memory)
   │  process — one or more GPU kernels or CuPy ops
   ▼
Device (GPU memory, transformed)
   │  copy_to_host() / cp.asnumpy()            ← Module 2 / Module 6
   ▼
Host (NumPy array)
   │  encode — turn the array back into a file format
   ▼
Disk (result image) or display
  • Every arrow in this diagram is something you’ve already written this semester — a decode/encode step (ordinary Python, not GPU-specific) bookending a host↔︎device transfer and a GPU compute stage
  • The “process” stage is where your semester’s kernel-writing skills (Modules 2-5) or library calls (Module 6) actually do the work

~3 min. This diagram is worth drawing on the board from memory — it’s the same “three-step cycle” from Module 6’s CuPy lecture (transfer, compute, transfer back), just with real disk I/O bookending it this time.

Stage 1: Load and Decode

from PIL import Image
import numpy as np

img = Image.open("photo.jpg")            # decode — ordinary CPU work, not GPU
arr = np.array(img, dtype=np.uint8)      # shape (H, W, 3) — a NumPy array
print(arr.shape, arr.dtype)
  • Decoding a compressed image format (JPEG, PNG) into a raw pixel array happens on the CPU — this step has nothing to do with the GPU, and there’s no reason to change that
  • The result is an ordinary NumPy array — a 3D array of (height, width, channels) — exactly the kind of array-shaped data every GPU technique this semester has assumed
  • This is also where a real pipeline decides on a batch: loading and processing many images together, rather than one at a time, to better amortize GPU overhead (Module 3’s fixed-overhead-vs-problem-size lesson, applied directly)

~2 min. Worth naming explicitly: decoding is not a GPU task — some pipelines do move decoding to the GPU (NVIDIA’s nvJPEG library exists for exactly this), but that’s beyond this course’s scope. The point here is recognizing which stages are naturally CPU work and which are naturally GPU work.

Stage 2: Transfer and Process

import cupy as cp

arr_gpu = cp.asarray(arr)                       # host → device (Module 6)

# Grayscale: a weighted sum across the color channels — an element-wise op
gray_gpu = (0.299 * arr_gpu[:, :, 0]
          + 0.587 * arr_gpu[:, :, 1]
          + 0.114 * arr_gpu[:, :, 2])

# Box blur: a 2D stencil, exactly Module 3's box-blur kernel — could be
# written as a @cuda.jit kernel instead of a CuPy call, same underlying idea
blurred_gpu = box_blur_2d_kernel(gray_gpu, radius=2)
  • Grayscale conversion is a straightforward element-wise operation — the same “one thread/one CuPy op, one output” shape used everywhere since Module 2
  • Blurring is a stencil (Module 3) — each output pixel depends on a neighborhood of inputs, with a boundary condition needed at the image edges
  • A real pipeline mixes both styles freely: CuPy for standard operations, a hand-written Numba kernel for anything with no library equivalent — exactly Module 6’s CuPy-vs-Numba decision, applied to image processing specifically

~4 min. This slide’s whole point is recognition: grayscale = Module 2’s element-wise pattern, blur = Module 3’s stencil pattern, applied to real pixel data instead of a synthetic array. Nothing here is new syntax.

Stage 3: Transfer Back and Save

result_cpu = cp.asnumpy(blurred_gpu)             # device → host (Module 6)
result_img = Image.fromarray(result_cpu.astype(np.uint8))
result_img.save("blurred_photo.jpg")             # encode — CPU work again
  • The device→host transfer is the same call from Module 6’s three-step cycle — and, per Module 4’s PCIe-bottleneck lesson, this is the most expensive single step in the whole pipeline per byte moved
  • Saving (encoding back to a compressed format) is CPU work again, mirroring the load stage
  • The pipeline-design lesson: minimize the number of host↔︎device round trips. If you had five processing steps to apply, you’d transfer once, run all five GPU operations back-to-back, and transfer back once — not transfer, process, transfer back, transfer again, process, transfer back (Module 2’s “minimize transfers” rule, applied to a realistic multi-step pipeline)

~2 min. This is the practical payoff of the whole session — the diagram’s five stages exist to set up this one design principle, which transfers directly to the capstone’s own pipeline (next session’s framing, and Dec 4’s spec walkthrough).

How PyTorch Really Moves Data

  • Real inference systems don’t call .to('cuda') on one batch and stop — they continuously load new data, moving it to the GPU while the previous batch is still being processed
  • PyTorch’s DataLoader with pin_memory=True allocates host memory in a way that makes the host→device transfer (Module 2’s PCIe bottleneck, again) faster and lets it overlap with GPU computation, instead of the CPU and GPU strictly taking turns
  • This is the same idea as Module 2’s “minimize and overlap transfers” lesson, implemented for you by a library rather than hand-written — recognizing the underlying problem is more valuable than memorizing this specific API

~3 min. Keep this at the concept level — pin_memory and overlapped transfer are real PyTorch features, but this course doesn’t require students to write this code. The goal is recognizing “oh, this is Module 2’s transfer-minimization lesson, industrialized.”

What cuDNN Does

  • cuDNN (mentioned in Module 6’s library-ecosystem slide) is NVIDIA’s library of hand-tuned neural-network building blocks — convolutions, pooling, activation functions, normalization layers
  • A convolution (the core operation in image-processing neural networks) can be computed several genuinely different ways on a GPU — as a direct sliding-window stencil (Module 3’s territory), or by reformulating it as a matrix multiply (Module 6’s @/cuBLAS territory), among others — and the fastest choice depends on the exact layer shape
  • cuDNN automatically benchmarks several implementations for your specific layer sizes and picks the fastest one at runtime — the same “which tool for this job” judgment call from Module 6 (CuPy vs. Numba), except cuDNN makes the call for you, per operation, automatically
  • PyTorch calls into cuDNN under the hood every time you run a convolutional layer — you never see cuDNN directly, but it’s doing real work every forward pass

~3 min. This directly connects Module 3’s stencil framing and Module 6’s library-selection framing to a single real example: a convolution genuinely is a stencil, computed by a library that’s smart enough to also compute it as a matmul when that’s faster.

Batching Strategy

[DIAGRAM] — Two small bar charts side by side, sharing a y-axis labeled “time.” Left, “batch size = 1”: many thin, short bars in a row, each representing one input processed alone, with a large gray “launch overhead” segment at the base of every single bar (the overhead repeats every time). Right, “batch size = 32”: one much taller bar representing 32 inputs processed together, with a single “launch overhead” segment at its base — proportionally tiny compared to the much larger “useful compute” segment above it. Caption under both: “Same total work, very different overhead-to-work ratio.”

  • Running inference one input at a time badly underuses a GPU — the same “problem too small to fill the device” failure mode from Module 1’s “when does the GPU lose” slide
  • Batching: group many inputs together into one larger tensor, and run the forward pass once on the whole batch — turning many small, overhead-dominated launches into one large, throughput-dominated one
  • Larger batches generally mean better GPU utilization and higher throughput (more total inferences per second) — but also higher latency for any single input (it has to wait for the rest of its batch to arrive) and more GPU memory used at once
  • This is a direct, concrete instance of Module 1’s latency-vs-throughput tradeoff: a production system tunes batch size deliberately, trading a little per-request latency for much better aggregate throughput

~3 min. Tie explicitly back to Module 1’s very first architectural framing — latency-optimized vs. throughput-optimized wasn’t just about comparing CPU to GPU, it’s a design knob within GPU workloads too, and batch size is exactly that knob for inference.

The LLM Connection

  • Large language models (the kind behind chatbots and code assistants) are, at their computational core, an enormous, repeated sequence of matrix multiplies — the same @ operator from Module 6, just at a scale of billions of parameters
  • Generating text one token at a time (autoregressive generation) means running a forward pass repeatedly, once per output token — each pass is itself a batch-and-inference problem exactly like this session’s content, just chained many times in a row
  • LLM inference is famously memory-bandwidth-bound, not compute-bound (Module 1’s arithmetic-intensity preview, Module 4’s roofline model) — moving the model’s billions of parameters from GPU memory to the compute units, over and over, is often the actual bottleneck, not the arithmetic itself
  • This is why LLM-serving hardware emphasizes memory bandwidth and capacity as much as raw FLOPS — a direct, large-scale echo of Module 1’s memory-wall lesson from week 3

~3 min. This is the “why does everyone care about GPUs right now” payoff, made concrete with the actual dominant workload — tie it back explicitly to arithmetic intensity (Module 1/4) so it reads as an application of a concept already taught, not a new fact to memorize.

The Day-1 Teaser, Revisited

Every song is described by 64 numbers. A user is also described by 64 numbers. We measure how well a song matches a user by multiplying those 64 pairs of numbers together and adding them up. We need to find the 10 best matches for 1,000 users, from a library of 100,000 songs, in under a second.

You now know everything you need to do this.

~2 min. Pause here. This slide should feel different today than it did on the first day. Students heard this in week 1 and could not have written a single line of GPU code. Now they can implement it in its entirety.

What You Are Building

A k-nearest-neighbor recommendation engine: - Database: 100,000 items (songs, movies, products), each a 64-dimensional embedding - Query: 1,000 users, each a 64-dimensional embedding - Task: for each user, find their top-K most similar items - Metric: cosine similarity — but since every vector is pre-normalized (length 1), cosine similarity reduces to a plain dot product, no separate distance formula needed

~2 min. This is the one conceptual thing to land before the math slide: “cosine similarity” sounds like it needs a scary formula, but with pre-normalized vectors it’s just a dot product — the setup cell handles normalization, students never derive it themselves.

The Mathematics (The Friendly Version)

Pre-normalized vectors: each ||v||₂ = 1.0

\[\text{similarity}(u, v) = u \cdot v = \sum_{k=0}^{63} u_k \cdot v_k\]

All 1,000 × 100,000 similarities at once:

sim = Q_mat @ D_mat.T    # shape (1000, 100_000)

Top-K per user:

top_k = cp.argpartition(-sim, K, axis=1)[:, :K]
  • The entire mathematical core of the capstone is these two lines — the capstone’s actual difficulty is building and optimizing the GPU kernel that computes the first line efficiently, and understanding every design decision along the way, not the math itself

~2 min. Reassurance slide: if a team is intimidated by “cosine similarity” and “k-nearest-neighbor,” this is the moment to show them it’s two lines of code they already know how to write.

The capstone is a simplified version of: - Spotify’s audio embedding search - Netflix’s collaborative filtering inference - Amazon’s “customers who bought” engine - Any vector database retrieval system

Session 4 · Dec 7 · GPU Computing in Industry

Today’s Plan

  • Four brief case studies: how GPU computing shows up in ML training, rendering, genomics, and finance
  • What each one has in common with something you’ve already built this semester

~1 min. Full 50-min session, no quiz. Keep each case study brisk (roughly 8-10 min) — the goal is breadth and recognition, not depth in any one field.

Case Study: ML Training

  • Training a large model means repeatedly running the forward pass (Dec 2’s territory) and computing gradients (autograd, briefly introduced Module 6) across enormous datasets, for many GPUs, for days or weeks
  • The core operation, repeated billions of times, is still the matrix multiply — Module 6’s @/cuBLAS, at a scale where even small per-operation inefficiencies compound into real time and cost
  • Multi-GPU training adds a new problem this course hasn’t covered: GPUs must periodically synchronize their results with each other over a network — a much slower and more complex version of Module 2’s host↔︎device transfer, now between multiple devices instead of one

~2 min. This connects directly to Module 1’s “a single training run can use thousands of GPUs for weeks” slide and Dec 2’s LLM content — training is the other half of that picture, generation (inference) being the half already covered.

Case Study: Rendering

  • Real-time ray tracing and path tracing (how modern game and film rendering works) is fundamentally a massively parallel, per-pixel or per-ray computation — the same “one thread, one independent unit of work” shape from Module 2, applied to light rays instead of array elements
  • Rendering workloads are often extremely divergent (Module 2’s Sep 30 content): different rays can bounce very different numbers of times before terminating, meaning different threads in the same warp frequently disagree on how much work remains
  • This is precisely why divergence-handling (predication, the cost of mismatched branches) matters so much in graphics-focused GPU work — it’s not just an exam topic, it’s the daily reality of writing a renderer

~2 min. Good moment to note that this course’s CUDA-focused, compute-only framing deliberately skipped graphics-specific GPU features (rasterization, texture units) — rendering workloads use the same underlying hardware and many of the same programming concepts, just with a different problem shape and additional graphics-specific hardware in play.

Case Study: Genomics

  • DNA/protein sequence alignment — finding where a short sequence matches within a much longer reference — has the same shape as Module 5’s parallel patterns: many independent comparisons that can run simultaneously, sometimes combined via a reduction to find the best-scoring match
  • Protein structure prediction (the class of problem AlphaFold addresses) relies heavily on large matrix operations and neural-network inference — Module 6’s @ and PyTorch content, at a much larger and more specialized scale
  • Genomics datasets are enormous (a single human genome is billions of base pairs) — exactly the kind of scale where Module 1’s “GPU wins when there’s enough work to amortize overhead” reasoning applies cleanly

~2 min. If time allows, ask whether anyone has used or heard of AlphaFold — it’s a widely-known example that makes “neural network inference, GPU-accelerated, at genomics scale” concrete rather than abstract.

Case Study: Finance

  • Monte Carlo simulation (running a random model millions of times to estimate a risk or a price) is embarrassingly parallel in the exact sense Module 1 defined it — each simulated trial is fully independent of every other one
  • Module 5’s random-number generation and reduction patterns (CuPy’s GPU-side RNG, tree reduction to aggregate results) map directly onto this: generate millions of random scenarios on the GPU, then reduce them down to a summary statistic (an average price, a risk estimate)
  • High-frequency trading systems care intensely about latency, not just throughput — a reminder that Module 1’s latency-vs-throughput framing isn’t just “GPU vs. CPU,” it’s a real design axis within GPU-accelerated systems too, echoing Dec 2’s batching-strategy discussion

~2 min. Nice closing case study for the module — it reuses nearly every major concept from the semester (embarrassingly parallel, RNG, reduction, latency-vs-throughput) in one recognizable real-world context.
