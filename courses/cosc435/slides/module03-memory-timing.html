From “Does It Run” to “Does It Run Well”

  • Every kernel you’ve written so far (Labs 4-5) follows one pattern: one thread computes one output element, checked by one bounds guard
  • That pattern is correct, and it’s the right default — but it’s not the only shape a kernel can take, and getting it running is only the first bar to clear
  • The rest of this module is about two things: designing kernels deliberately rather than by habit, and measuring whether they’re actually fast

~2 min. Framing slide — sets up why “design patterns” and “debugging” belong in the same session as a matched pair: patterns are how you write a kernel well the first time, debugging is what you do when it isn’t.

Pattern: One Thread, One Output Element

@cuda.jit
def scale(arr, factor):
    i = cuda.grid(1)
    if i < arr.shape[0]:
        arr[i] = arr[i] * factor
  • The pattern every kernel this semester has used so far: launch (at least) as many threads as there are outputs, each thread computes exactly one
  • Simple to reason about, maps directly onto the hardware’s SIMT model (Sep 30), and is the right choice whenever the number of outputs is known ahead of time and reasonably launch-able (millions of threads is fine; billions can hit practical limits)
  • This is the default pattern — reach for it first, and only reach for something else when it doesn’t fit

~2 min. Deliberately named and framed as “the pattern” — students have been using it since Lab 4 without necessarily thinking of it as a reusable, nameable design choice. Naming it is the point of this slide.

Pattern: The Grid-Stride Loop

@cuda.jit
def scale_grid_stride(arr, factor):
    start  = cuda.grid(1)
    stride = cuda.gridsize(1)          # total threads launched
    for i in range(start, arr.shape[0], stride):
        arr[i] = arr[i] * factor
  • A different shape: launch a fixed, modest number of threads, and have each one loop over multiple elements, striding by the total thread count
  • Useful when N is unknown at launch time, or so large that launching one thread per element isn’t practical, or when you want the same kernel to run efficiently across a wide range of N without recomputing launch config each time
  • You won’t be asked to write this pattern in a lab or checkpoint this semester — it’s here so you recognize it when you see it in real-world CUDA code, which uses it constantly

~2 min. Explicitly flag this as awareness-level, not tested — students should not walk away thinking they need to memorize cuda.gridsize() syntax for a checkpoint. The goal is purely “don’t be confused when you see this shape later in your career.”

Choosing a Launch Configuration

  • So far, launch configuration (THREADS, computed BLOCKS) has mostly been handed to you or fixed at a round number like 256
  • In practice, there is rarely one obviously-correct block size — it depends on the kernel’s resource usage (registers, shared memory) and the GPU’s occupancy limits (Sep 30)
  • A few reliable heuristics: prefer multiples of 32 (whole warps, no wasted lanes — Sep 30); common starting points are 128, 256, or 512 threads per block; extremes (very small or very large blocks) are rarely optimal
  • Beyond those heuristics, the honest answer is: measure it. Lab 6 (this Friday) has you sweep several block sizes on a real kernel and find the fastest empirically — that’s Oct 7’s subject in full

~3 min. Resist the temptation to give a definitive “always use 256” rule — the entire point of Oct 7’s profiling session is that this has to be measured per-kernel. This slide should leave students slightly unsatisfied with “it depends,” which Oct 7 then resolves with a concrete method.

Debugging Numba CUDA Kernels

  • GPU kernels run outside the normal Python debugger — you can’t drop a breakpoint inside a @cuda.jit function the way you would in ordinary Python
  • Common failure modes you’ll hit this semester:
    • Silent wrong answers — almost always a missing or incorrect bounds guard (Module 2)
    • TypingError at compile time — Numba’s CUDA compiler only supports a restricted subset of Python/NumPy; an unsupported operation (e.g. Python lists, string formatting, most NumPy functions) inside a kernel fails to compile with a (sometimes cryptic) type error
    • Shape mismatches — passing an array of the wrong shape or dtype to a kernel that assumes a specific layout

~3 min. Ask the room if anyone has already hit a TypingError in Lab 4 or 5 — normalize it as a routine part of the workflow, not a sign something has gone deeply wrong.

Debugging Technique: Shrink N and Verify by Hand

N_DEBUG = 8   # instead of 1,000,000 — small enough to eyeball
arr = np.arange(N_DEBUG, dtype=np.float32)
arr_gpu = cuda.to_device(arr)

my_kernel[1, N_DEBUG](arr_gpu)     # one block, exactly enough threads
cuda.synchronize()

print(arr_gpu.copy_to_host())      # small enough to read directly
  • Before trusting a kernel at N = 1,000,000, run it at N = 8 (or similar) and check every value by hand or against a tiny NumPy reference
  • Launching one block with exactly N threads (no ceiling division needed) removes launch-configuration bugs from the picture while you debug the kernel body itself
  • Every lab’s Completion cell does a version of this at full scale — this technique is how you get there with confidence, one step earlier

~2 min. This is the single most useful habit to instill this session — most kernel bugs are far easier to spot in 8 printed numbers than in a checksum computed over a million.

Debugging Technique: The CUDA Simulator

import os
os.environ["NUMBA_ENABLE_CUDASIM"] = "1"   # set BEFORE importing numba.cuda

from numba import cuda

@cuda.jit
def my_kernel(arr):
    i = cuda.grid(1)
    print("thread", i, "sees", arr[i])   # print() now actually works!
    if i < arr.shape[0]:
        arr[i] = arr[i] * 2.0
  • Setting NUMBA_ENABLE_CUDASIM=1 runs your @cuda.jit kernel in pure Python, on the CPU, one simulated thread at a time — no GPU required
  • Inside the simulator, ordinary Python print() and even pdb breakpoints work exactly as they would in any Python function — neither works reliably in a real GPU kernel
  • Trade-off: the simulator is much slower and doesn’t reflect real GPU timing — use it to debug logic, then switch back to a real GPU to debug and measure performance

~2 min. This is a genuinely useful Numba feature many students won’t discover on their own — worth a live demo if time allows, showing a kernel with a deliberate bug caught via a print() that would be silent (or crash unhelpfully) on real hardware.

The Wrong Way to Time a GPU Kernel

import time

start = time.perf_counter()
my_kernel[blocks, threads](arr_gpu)
end = time.perf_counter()

print(f"{(end - start)*1000:.2f} ms")  # WRONG
  • A GPU kernel launch is asynchronous — the CPU issues the launch and immediately continues to the next line, without waiting for the GPU to actually finish
  • time.perf_counter() here measures how long it took to launch the kernel, not how long the kernel took to run
  • The result: a suspiciously, impossibly fast number — this is the bug, not a real measurement

~3 min. This is Lab 06’s critical demo. Let the wrong number sit for a moment before revealing why it’s wrong — the surprise is the point, it makes the fix memorable.

The Right Way: cuda.synchronize()

import time
from numba import cuda

start = time.perf_counter()
my_kernel[blocks, threads](arr_gpu)
cuda.synchronize()              # wait for the GPU to actually finish
end = time.perf_counter()

print(f"{(end - start)*1000:.2f} ms")  # CORRECT
  • cuda.synchronize() blocks the CPU until every previously-launched GPU operation has completed
  • Without it, you are timing a function call that returns almost instantly, not a computation
  • This is not a beginner mistake to be embarrassed about — the same bug appears in published papers and shipped industry code. Professional GPU code-review checklists explicitly call it out

~2 min. Reiterate: the fact that the wrong code runs, produces a plausible-looking (if suspiciously small) number, and never raises an error is exactly what makes this trap dangerous. There is no crash to alert you.

Timing Across Problem Sizes

sizes = [10_000, 100_000, 1_000_000, 5_000_000, 20_000_000]

for N in sizes:
    arr = cp.random.randn(N, dtype=cp.float32)

    start = time.perf_counter()
    result = cp.sum(arr ** 2)
    cp.cuda.Stream.null.synchronize()   # CuPy's equivalent of cuda.synchronize()
    elapsed = time.perf_counter() - start

    print(f"N={N:>10,}  time={elapsed*1000:.2f} ms")
  • Running the same computation across a range of N reveals whether GPU overhead (kernel launch, PCIe transfer — Module 2) is dominating small problems
  • At small N, expect the GPU to look slow — fixed overhead dominates. At large N, that overhead is amortized and the GPU’s raw throughput wins
  • Lab 6 has you find this crossover point directly — it’s a concrete answer to Module 1’s “when does the GPU actually win?” question

~2 min. Tie explicitly back to Module 1’s “when does the GPU win/lose” slide — this timing sweep is that question, answered empirically instead of just in principle.

Reading a Profiler-Style Table

Lab 6 has you sweep the naive matmul kernel across three block sizes and record the results:

     Block |  Time (ms) | Threads/block
------------------------------------------
       8x8 |      14.82 |             64
     16x16 |       6.31 |            256
     32x32 |       8.94 |           1024
  • Reading this table is itself a skill: scan the “Time” column for the minimum, then ask why that configuration won — this is exactly what CK-06 tests
  • Here, 16×16 is fastest — not the smallest block (8×8, too few threads to keep the SM busy) and not the largest (32×32, resource limits reduce how many blocks can be resident at once — Sep 30’s occupancy content)
  • A profiler-style table like this is a compressed record of an experiment — reading it well means reconstructing the “why,” not just picking out the smallest number

~3 min. Numbers shown are representative, not guaranteed — actual Lab 6 results vary by Colab’s assigned T4 and current load. The shape (middle value wins) is the teachable pattern, not these exact milliseconds.

Compute-Bound or Memory-Bound?

  • The naive matmul kernel reads a full row of A and a full column of B from global memory for every single output element it computes — with zero reuse between threads
  • That’s a lot of global-memory traffic relative to the arithmetic done per byte fetched (low arithmetic intensity — Module 1’s preview of this idea)
  • Diagnosis: this kernel is memory-bound, not compute-bound — its ALUs are very often waiting on data, not the limiting factor
  • This diagnosis is exactly why Module 4’s tiled matmul (reusing data via shared memory) gets such a large speedup over this naive version — it directly attacks the memory-bound bottleneck identified here

~3 min. This is CK-06’s Q1 in worked-example form — plant the reasoning pattern here (describe the access pattern → count reuse → conclude bound type) so students can reproduce it on a different kernel in the checkpoint.

Why a Middle Block Size Often Wins

  • Very small blocks (8×8 = 64 threads = 2 warps): too few resident warps for the scheduler to hide memory latency well (Sep 30) — the SM often has nothing else ready to run while one warp waits
  • Very large blocks (32×32 = 1024 threads): each block claims a large share of the SM’s fixed register/thread budget, so fewer blocks fit resident at once — occupancy can drop even though each individual block is “big”
  • The middle ground (16×16 = 256 threads = 8 warps) is often the sweet spot: enough warps to hide latency, without claiming so much of the SM’s budget that fewer blocks fit
  • “Often” is doing real work in that sentence — this is a heuristic, not a law. The only way to know for a specific kernel is to measure, exactly as Lab 6 does

~2 min. This is CK-06’s Q2 in worked-example form. Emphasize this is reasoning from the occupancy concept (Sep 30), not a new independent rule to memorize.

Amdahl’s Law: The Serial Fraction Problem

Every program has two parts:

  • Parallel part (fraction \(p\)): can run on all GPU cores simultaneously
  • Serial part (fraction \(1-p\)): must run sequentially — no amount of parallel hardware helps

\[\text{Speedup}(n) = \frac{1}{(1-p) + \frac{p}{n}}\]

where \(n\) is the number of parallel processors applied to the parallel part.

~4 min. Derive from first principles: if total serial-equivalent work is 1 unit, the serial part takes time \((1-p)\) regardless of \(n\), and the parallel part takes time \(p/n\). Total time is the sum; speedup is 1 divided by that. This is the formal version of Module 1’s informal preview.

The Ceiling

As \(n \to \infty\) (infinitely many processors):

\[\text{Speedup} \to \frac{1}{1-p}\]

  • A 5% serial fraction caps total speedup at 20× — forever, no matter how many GPU cores you add
  • A 1% serial fraction caps it at 100×. Even a tiny serial fraction becomes the binding constraint once \(n\) is large enough

[DIAGRAM] — Line chart, x-axis “number of processors n” (log scale, 1 to 10,000), y-axis “speedup.” Four curves for p = 0.5, 0.9, 0.95, 0.99. All four curves rise initially, then flatten into a horizontal asymptote — the p=0.5 curve flattens near speedup=2 almost immediately, while the p=0.99 curve keeps climbing much further before flattening near speedup=100. Dashed horizontal lines mark each curve’s ceiling value.

~2 min. The diagram is the “aha” — a static formula is less convincing than watching four curves all hit a wall at different heights. EL-03 has students apply this exact ceiling to the capstone’s estimated 5% serial fraction.

The Uncomfortable Implication

  • Your GPU kernel is 50× faster than the CPU version. The serial part of your program is completely unchanged.
  • If the serial fraction is 5%, the end-to-end speedup of your whole program is still capped at 20×, no matter how fast that kernel gets
  • Cutting the serial fraction from 5% to 2.5% buys more end-to-end speedup than doubling the GPU kernel’s raw performance
  • Practical consequence: sometimes the highest-value optimization isn’t the kernel at all — it’s the data loading, the preprocessing step, or a serial aggregation on the host

~3 min. This is the punchline students should carry into the capstone: profiling (this session’s first half) tells you where time goes; Amdahl tells you the ceiling on how much any one piece of optimization can help.

Applying Amdahl to the Capstone

In the capstone’s similarity-search pipeline:

  • Serial: data loading, host↔︎device PCIe transfer, cp.argpartition for top-K — estimated at roughly 5% of total time
  • Parallel: the Q @ D.T similarity computation itself — roughly 95%

\[\text{Max possible speedup} = \frac{1}{0.05} = 20\times\]

  • EL-03 (due Sun, Oct 18 — the day before the midterm) has you read Herb Sutter’s “The Free Lunch Is Over” essay and apply this exact calculation to the capstone yourself

Beyond Element-wise: What Is a Stencil?

  • Every kernel so far has been element-wise: output i depends only on input i (or input (row, col)) — no thread needs to look at its neighbors
  • A stencil breaks that pattern: output i depends on a small neighborhood of nearby inputs, not just the one at the same position
  • Classic examples: a moving average (each output = average of nearby inputs), image blur (each output pixel = weighted average of nearby pixels), numerical derivatives (each output = a weighted combination of neighboring values)
  • The “one thread, one output” launch pattern (Oct 5) still applies — what changes is what each thread reads, not how many threads you launch

~3 min. Frame this explicitly as “the launch pattern you already know, applied to a kernel body that reads more than one input” — students shouldn’t feel like they’re learning an entirely new launch mechanic, just a new kernel-body shape.

The Boundary Problem

[DIAGRAM] — A 1D array of 10 cells, indices 0-9, drawn in a row. Above index 0, dashed “ghost” cells at positions -2 and -1 are shown with question marks, labeled “neighbors that don’t exist.” Above index 9, the same for positions 10 and 11 on the right. A caption: “Every interior cell has real neighbors on both sides. Cells near the edges do not.”

  • A stencil reads a neighborhood around each position — but positions near the edge of the array have neighbors that fall outside the array entirely
  • Every stencil kernel needs an explicit policy for what to do at the boundary — there is no “correct” default, only different reasonable choices with different tradeoffs
  • Three common policies: clamp (reuse the nearest valid edge value), zero-pad (treat out-of-range neighbors as zero), wrap (treat the array as circular, wrapping around to the other side)

~3 min. Don’t rush past “there is no correct default” — this is a genuine design decision, not a fact to memorize. Different applications legitimately prefer different policies (image processing usually clamps or wraps; some signal-processing contexts zero-pad).

Our Policy: Clamping

def clamp(x, lo, hi):
    return min(max(x, lo), hi)

clamp(-1, 0, 9)   # -1 is out of range  → snaps to 0
clamp(5, 0, 9)    #  5 is in range     → unchanged
clamp(15, 0, 9)   # 15 is out of range → snaps to 9
  • This course uses clamping (also called edge-replication) throughout: any neighbor index that falls outside the valid range is snapped to the nearest valid edge index instead
  • Effect: edge pixels/values get their “missing” neighbors filled in with a repeat of the nearest real value, rather than a fabricated zero or a wraparound from the opposite edge
  • Every stencil kernel this semester (Lab 7, CK-07) uses this exact clamp() helper — implemented inline inside the kernel, since Numba CUDA kernels can’t call arbitrary Python helper functions

~2 min. Flag the “can’t call arbitrary helper functions” constraint explicitly — students will need to inline the clamp logic (min(max(idx, 0), n-1)) directly in the kernel body rather than calling a separate clamp() function, which is a real Numba CUDA limitation worth knowing about before Lab 7.

A 1D Warm-up: Moving Average

@cuda.jit
def moving_average_1d(arr, out, n, radius):
    i = cuda.grid(1)
    if i < n:
        total = 0.0
        for d in range(-radius, radius + 1):
            j = min(max(i + d, 0), n - 1)   # clamp inline
            total += arr[j]
        out[i] = total / (2 * radius + 1)
  • Each output i averages 2*radius + 1 neighboring inputs — radius 2 means a 5-wide window (2 before, the center, 2 after)
  • The min(max(...)) clamp appears inside the loop, once per neighbor read — this is CK-07’s exact pattern
  • Near the edges, clamping means some neighbor positions repeat (e.g. near index 0, j clamps to 0 for every out-of-range neighbor) — that’s the clamping policy visibly at work, not a bug

~3 min. This is Lab 07 Part 3’s warm-up, shown here as a worked example before the lab. Have students trace through i=0, radius=2 by hand: d ranges over -2,-1,0,1,2; j clamps to 0,0,0,1,2 — three of the five taps are the same repeated value.

From 1D to 2D: Box Blur

@cuda.jit
def box_blur_2d(img, out, H, W, radius):
    row, col = cuda.grid(2)
    if row < H and col < W:
        total = 0.0
        for dr in range(-radius, radius + 1):
            for dc in range(-radius, radius + 1):
                r = min(max(row + dr, 0), H - 1)   # clamp row
                c = min(max(col + dc, 0), W - 1)   # clamp col
                total += img[r, c]
        out[row, col] = total / ((2 * radius + 1) ** 2)
  • Same idea as the 1D case, doubled: a (2·radius+1) × (2·radius+1) square neighborhood, clamped independently on both row and column
  • This is image convolution — the motivating example for this whole session. A box blur is the simplest possible convolution: every neighbor weighted equally
  • Radius 1 → 3×3 window (9 taps). Radius 2 → 5×5 window (25 taps). Bigger radius means more blur, but also a lot more memory reads per output pixel

~3 min. This is Lab 07’s Exercise 1 pattern, shown as a worked example. The nested loop (row neighborhood × col neighborhood) is the main new syntactic idea versus the 1D case — walk through it explicitly.

Radius vs. Cost

Radius Window size Taps per output pixel
1 3×3 9
2 5×5 25
4 9×9 81
8 17×17 289
  • Taps per pixel grows with the square of the radius — doubling the radius roughly quadruples the memory reads and arithmetic per output element
  • Every one of those taps is a separate global-memory read in the naive version above — this is exactly the kind of memory traffic Module 4’s shared-memory tiling (a stencil-shaped problem too, in spirit) is built to reduce
  • Lab 7 has you compare blur strength across a few radii directly and connect the visual result back to this table

~2 min. Worth an explicit callback: “this naive stencil re-reads overlapping neighborhoods from global memory constantly, with heavy reuse between adjacent output pixels — sound familiar?” — it’s the same reuse-without-caching problem Oct 7’s naive-matmul diagnosis identified, just in a different kernel shape.
