  • Every kernel you’ve written so far (Labs 4-5) follows one pattern: one thread computes one output element, checked by one bounds guard
  • That pattern is correct, and it’s the right default — but it’s not the only shape a kernel can take, and getting it running is only the first bar to clear
  • The rest of this module is about two things: designing kernels deliberately rather than by habit, and measuring whether they’re actually fast

Pattern: One Thread, One Output Element

@cuda.jit
def scale(arr, factor):
    i = cuda.grid(1)
    if i < arr.shape[0]:
        arr[i] = arr[i] * factor
  • Launch (at least) as many threads as there are outputs; each thread computes exactly one
  • Maps directly onto the hardware’s SIMT model (Sep 30)
  • Right whenever the number of outputs is known ahead of time and reasonably launch-able — millions of threads is fine; billions can hit practical limits
  • This is the default pattern — reach for it first

~2 min. Deliberately named and framed as “the pattern” — students have been using it since Lab 4 without necessarily thinking of it as a reusable, nameable design choice. Naming it is the point of this slide.

Pattern: The Grid-Stride Loop

@cuda.jit
def scale_grid_stride(arr, factor):
    start  = cuda.grid(1)
    stride = cuda.gridsize(1)   # total threads launched
    for i in range(start, arr.shape[0], stride):
        arr[i] = arr[i] * factor
  • Launch a fixed, modest number of threads; each one loops over several elements, striding by the total thread count
  • Useful when N is unknown at launch time or too large for one thread per element, or to run one launch config across a wide range of N

~2 min. Explicitly flag this as awareness-level, not tested — students should not walk away thinking they need to memorize cuda.gridsize() syntax for a checkpoint. The goal is purely “don’t be confused when you see this shape later in your career.” The trace on the next sub-slide is the fastest way to make the loop click.

Trace: N = 10 elements, but only 4 threads launched (stride = 4)

Thread (start) Handles indices
0 0, 4, 8
1 1, 5, 9
2 2, 6
3 3, 7
  • Every index is covered exactly once, and the loop’s own range stops at N — no separate bounds guard needed
  • You won’t be asked to write this pattern in a lab or checkpoint this semester — it’s here so you recognize it in real-world CUDA code, which uses it constantly

Choosing a Launch Configuration

  • So far, launch configuration (THREADS, computed BLOCKS) has mostly been handed to you or fixed at a round number like 256
  • In practice there is rarely one obviously-correct block size — it depends on the kernel’s resource usage (registers, shared memory) and the GPU’s occupancy limits (Sep 30)

A few reliable heuristics:

  • Prefer multiples of 32 — whole warps, no wasted lanes (Sep 30)
  • Common starting points: 128, 256, or 512 threads per block
  • Extremes (very small or very large blocks) are rarely optimal

Beyond those heuristics, the honest answer is: measure it.

  • Lab 6 (this Friday) has you sweep several block sizes on a real kernel and find the fastest empirically — that’s Oct 7’s subject in full

~3 min across both sub-slides. Resist the temptation to give a definitive “always use 256” rule — the entire point of Oct 7’s profiling session is that this has to be measured per-kernel. This slide should leave students slightly unsatisfied with “it depends,” which Oct 7 then resolves with a concrete method.

Debugging Numba CUDA Kernels

  • GPU kernels run outside the normal Python debugger — you can’t drop a breakpoint inside a @cuda.jit function the way you would in ordinary Python

Common failure modes you’ll hit this semester:

  • Silent wrong answers — almost always a missing or incorrect bounds guard (Module 2)
  • TypingError at compile time — Numba compiles only a restricted subset of Python/NumPy; Python lists, string formatting, and most NumPy functions inside a kernel fail with a (sometimes cryptic) type error
  • Shape mismatches — passing an array of the wrong shape or dtype to a kernel that assumes a specific layout

~3 min. Ask the room if anyone has already hit a TypingError in Lab 4 or 5 — normalize it as a routine part of the workflow, not a sign something has gone deeply wrong.

Debugging Technique: Shrink N and Verify by Hand

N_DEBUG = 8   # instead of 1,000,000 — small enough to eyeball
arr = np.arange(N_DEBUG, dtype=np.float32)
arr_gpu = cuda.to_device(arr)

my_kernel[1, N_DEBUG](arr_gpu)     # one block, exactly enough threads
cuda.synchronize()

print(arr_gpu.copy_to_host())      # small enough to read directly

If my_kernel doubles every element, you should see:

[ 0.  2.  4.  6.  8. 10. 12. 14.]

If you see [ 0. 2. 4. 6. 4. 5. 6. 7.] instead, half the threads did nothing — an indexing or launch bug, visible at a glance.

  • Before trusting a kernel at N = 1,000,000, run it at N = 8 and check every value by hand or against a tiny NumPy reference
  • Launching one block with exactly N threads (no ceiling division needed) removes launch-configuration bugs from the picture while you debug the kernel body itself
  • Every lab’s Completion cell checks your results at full scale — this technique is how you get there with confidence, one step earlier

~2 min across both sub-slides. This is the single most useful habit to instill this session — most kernel bugs are far easier to spot in 8 printed numbers than in a checksum computed over a million.

Debugging Technique: The CUDA Simulator

import os
os.environ["NUMBA_ENABLE_CUDASIM"] = "1"   # set BEFORE importing numba

import numpy as np
from numba import cuda

@cuda.jit
def my_kernel(arr):
    i = cuda.grid(1)
    if i < arr.shape[0]:
        print("thread", i, "sees", arr[i])
        arr[i] = arr[i] * 2.0

my_kernel[1, 4](np.arange(4, dtype=np.float32))

Output (thread order may vary):

thread 0 sees 0.0
thread 1 sees 1.0
thread 2 sees 2.0
thread 3 sees 3.0
  • NUMBA_ENABLE_CUDASIM=1 runs your @cuda.jit kernel in pure Python, on the CPU, with every GPU thread simulated — no GPU required
  • In the simulator you can inspect any variable with print() and even set pdb breakpoints — and an out-of-bounds read raises a normal Python IndexError instead of silently corrupting memory
  • On a real GPU, print() works only for simple values (numbers, string constants), the output is unordered across threads, and pdb doesn’t work at all
  • Trade-off: the simulator is much slower and doesn’t reflect real GPU timing — use it to debug logic, then switch back to a real GPU to measure performance

~2 min. This is a genuinely useful Numba feature many students won’t discover on their own — worth a live demo if time allows: move the print() above the bounds guard and launch 5 threads on 4 elements; the simulator raises IndexError on the spot, while real hardware would read garbage silently. Note the env var must be set before numba is imported at all — in Colab that means restarting the runtime if numba is already loaded.

The Wrong Way to Time a GPU Kernel

import time

my_kernel[blocks, threads](arr_gpu)    # warm-up: the first call JIT-compiles
cuda.synchronize()

start = time.perf_counter()
my_kernel[blocks, threads](arr_gpu)
end = time.perf_counter()

print(f"{(end - start)*1000:.2f} ms")  # WRONG
  • A GPU kernel launch is asynchronous — the CPU issues the launch and immediately continues to the next line, without waiting for the GPU to finish
  • time.perf_counter() here measures how long it took to launch the kernel, not how long the kernel took to run
  • The result: a suspiciously, impossibly fast number — this is the bug, not a real measurement

~3 min. This is Lab 06’s critical demo. Let the wrong number sit for a moment before revealing why it’s wrong — the surprise is the point, it makes the fix memorable. Mention the warm-up line in passing here; the next slide explains it.

The Right Way: cuda.synchronize()

import time
from numba import cuda

my_kernel[blocks, threads](arr_gpu)    # warm-up: the first call JIT-compiles
cuda.synchronize()

start = time.perf_counter()
my_kernel[blocks, threads](arr_gpu)
cuda.synchronize()              # wait for the GPU to actually finish
end = time.perf_counter()

print(f"{(end - start)*1000:.2f} ms")  # CORRECT
  • cuda.synchronize() blocks the CPU until every previously-launched GPU operation has completed
  • The warm-up call matters too: the first launch of a @cuda.jit kernel compiles it, which can take hundreds of ms — never time that call
  • In Lab 6 the wrong timing typically comes out 10–100× smaller than the correct one
  • Without cuda.synchronize(), you are timing a function call that returns almost instantly, not a computation
  • This is not a beginner mistake to be embarrassed about — the same bug appears in published papers and shipped industry code. Professional GPU code-review checklists explicitly call it out

~2 min across both sub-slides. Reiterate: the fact that the wrong code runs, produces a plausible-looking (if suspiciously small) number, and never raises an error is exactly what makes this trap dangerous. There is no crash to alert you.

Timing Across Problem Sizes

sizes = [10_000, 100_000, 1_000_000, 10_000_000]
THREADS = 256

for N in sizes:
    arr = np.ones(N, dtype=np.float32)
    arr_gpu = cuda.to_device(arr)            # transfer happens before the timer
    BLOCKS = (N + THREADS - 1) // THREADS

    scale[BLOCKS, THREADS](arr_gpu, 2.0)     # warm-up (first call compiles)
    cuda.synchronize()

    start = time.perf_counter()
    scale[BLOCKS, THREADS](arr_gpu, 2.0)     # the scale kernel from Oct 5
    cuda.synchronize()
    gpu_ms = (time.perf_counter() - start) * 1000

    start = time.perf_counter()
    arr *= 2.0                               # the same work in NumPy, on the CPU
    cpu_ms = (time.perf_counter() - start) * 1000

    print(f"N={N:>10,}  GPU={gpu_ms:.3f} ms  NumPy={cpu_ms:.3f} ms")

What the output shows:

  • At small N the GPU time barely changes as N grows — a fixed launch overhead dominates, and NumPy often wins
  • At large N the GPU time grows roughly in proportion to N — the overhead is amortized, and the GPU pulls ahead as NumPy’s time keeps climbing
  • The crossover is the N where the two lines cross — a concrete answer to Module 1’s “when does the GPU actually win?”
  • cuda.to_device runs before the timer, so this measures the kernel alone. Move it inside the timed region and transfer cost joins the fixed overhead (Module 2’s host↔︎device boundary) — the crossover moves to a much larger N
  • Lab 6 Part 2 makes the same kind of GPU-vs-NumPy comparison at a single N; this loop extends it across sizes

~2 min across both sub-slides. Tie explicitly back to Module 1’s “When Does the GPU Win?” slide — this timing sweep is that question, answered empirically instead of just in principle. Uses only Numba + NumPy (CuPy isn’t introduced until Module 6). If you run it live, show the real numbers; for a kernel this light the crossover can be surprisingly late, which is itself a good discussion point (scale does one multiply per 8 bytes moved).

Why 16×16 Won Here

  • Sep 30’s occupancy idea doesn’t explain this table on a T4. One T4 SM holds at most 1024 threads and 16 blocks:
Block Blocks per SM Threads per SM
8×8 (64 threads) 16 (the block limit) 1024
16×16 (256 threads) 4 1024
32×32 (1024 threads) 1 1024
  • All three fill the SM — and this kernel uses few registers, so registers don’t cap it either
  • What does differ is how each warp touches memory

cuda.grid(2) puts threadIdx.x on row, so a warp’s 32 threads fill down the rows first.

Two forces pull in opposite directions:

  • Scattered reads (favors small blocks): at each k, a warp reads A[row, k] for every row it covers. Each row of A lives in a different place in memory — 8, 16, or 32 separate fetches. B[k, col] comes from adjacent columns: one fetch
  • Shared data (favors big blocks): every thread in a block needs the same few rows of A and columns of B. 8×8 needs 8 + 8 = 16 of them for 64 outputs; 32×32 needs 64 for 1,024 outputs — 16× the outputs from 4× the data, reuse the cache can catch
  • 16×16 sits between the two. Which force wins depends on the GPU and the matrix size — a heuristic, not a law. The only way to know is to measure, as Lab 6 does
  • Module 4 makes both forces deliberate: coalescing (Oct 21) tackles the first, shared-memory tiling (Lab 9) the second

~4 min across the three sub-slides. REWRITTEN 2026-10-07: this slide used to explain the table by occupancy (8x8 = too few warps, 32x32 = too few blocks). That holds on some GPUs (e.g. compute capability 8.6: 16 blocks x 64 = 1024 of 1536 threads, 67%), but not on Colab’s T4 (CC 7.5: 1024 threads / 16 blocks per SM), where all three configs reach 100% theoretical occupancy. Compute-Bound or Memory-Bound?

  • The naive matmul kernel reads a full row of A and a full column of B from global memory for every single output element — no programmed reuse: each thread fetches its own copies, even though neighboring threads need the same data
  • That’s a lot of memory traffic relative to the arithmetic done per byte fetched — low arithmetic intensity (Module 1’s preview of this idea)
  • Diagnosis: this kernel is memory-bound, not compute-bound — its ALUs are very often waiting on data
  • This diagnosis is exactly why Module 4’s tiled matmul (reusing data via shared memory) gets such a large speedup — it directly attacks the memory bottleneck identified here

~3 min. Plant the reasoning pattern here (describe the access pattern → count reuse → conclude bound type). The caches (L1/L2) do catch some of the neighbor reuse by accident, which is why Lab 06 Ex 2’s “implied traffic” exceeds DRAM peak — tiling makes that reuse deliberate. The next slides turn this qualitative diagnosis into the numbers CK-06 asks for.

Putting Numbers on It: Achieved Bandwidth

Worked example: SAXPY, y[i] = a * x[i] + y[i], on N = 10,000,000 float32 elements, timed at 0.45 ms on a T4

  • Bytes moved per element: read x[i] (4) + read y[i] (4) + write y[i] (4) = 12 bytes
  • Total bytes: 10,000,000 × 12 = 120,000,000 bytes

\[\text{Bandwidth} = \frac{120{,}000{,}000\ \text{bytes}}{0.45 \times 10^{-3}\ \text{s}} = 2.67 \times 10^{11}\ \text{B/s} = 266.7\ \text{GB/s}\]

  • The units trap: convert ms → s (÷ 1000) and bytes → GB (÷ 10⁹, the convention in this course) before comparing to the T4’s 320 GB/s peak
  • 266.7 ÷ 320 = 83% of peak bandwidth

Arithmetic Intensity and the Ridge Point

  • Arithmetic intensity = FLOPs ÷ bytes moved. SAXPY: 2 FLOPs (one multiply, one add) per 12 bytes = 0.167 FLOP/byte
  • Ridge point = peak FLOP/s ÷ peak bandwidth. T4: 8,100 GFLOP/s ÷ 320 GB/s = 25.3 FLOP/byte
  • Intensity below the ridge point → memory-bound: bandwidth runs out before arithmetic does
  • Intensity above the ridge point → compute-bound
  • SAXPY: 0.167 ≪ 25.3, so it’s memory-bound — and the relevant peak to report is bandwidth (83%), not FLOP/s
  • For a compute-bound kernel, report achieved GFLOP/s ÷ 8,100 instead (Module 4 draws all of this as the roofline)

~4 min across both sub-slides. CK-06 is exactly this sequence on a seeded table: GB/s per row, memory vs. compute, % of the relevant peak. Lab 06 Exercise 2 does it on the naive matmul (deliberately not used as the worked example here, so the lab isn’t pre-answered). The ridge point is formalized as the roofline in Module 4.

Choosing a Robust Configuration

Threads/Block |  Time (ms)
--------------------------
           64 |      0.61
          128 |      0.48
          256 |      0.46
          512 |      0.45   ← fastest
         1024 |      0.52
  • Timings within ~5% of each other are effectively a tie — run-to-run noise on a shared Colab GPU is about that large
  • Rule used in CK-06: pick the smallest block size within 5% of the best time
  • Here: 5% above 0.45 ms is 0.4725 ms → 256 (0.46) qualifies, 128 (0.48) doesn’t → robust choice: 256
  • Why smallest: it gives the scheduler more, smaller blocks to spread across the 40 SMs, and less per-block resource demand if the kernel later grows

~2 min. The point is that “fastest in one run” is not the same as “best choice” — a config that wins by 2% may lose next run. Same 5% rule as CK-06’s Gap 4.

Amdahl’s Law: The Serial Fraction Problem

Every program has two parts:

  • Parallel part (fraction \(p\)): can run on all GPU cores simultaneously
  • Serial part (fraction \(1-p\)): must run sequentially — no amount of parallel hardware helps

\[\text{Speedup}(n) = \frac{1}{(1-p) + \frac{p}{n}}\]

where \(n\) is the number of parallel processors applied to the parallel part.

  • Why: if the original run takes 1 unit of time, the serial part still takes \((1-p)\), and the parallel part shrinks to \(p/n\). Speedup is 1 divided by the new total

~4 min. Derive from first principles on the board, then reveal the “Why” bullet so the derivation is on the slide for students reviewing later. This is the formal version of Module 1’s informal preview.

The Ceiling

As \(n \to \infty\) (infinitely many processors):

\[\text{Speedup} \to \frac{1}{1-p}\]

  • A 5% serial fraction caps total speedup at 20× — forever, no matter how many GPU cores you add
  • A 1% serial fraction caps it at 100×. Even a tiny serial fraction becomes the binding constraint once \(n\) is large enough

Every curve rises, then hits a wall at \(1/(1-p)\) — more processors stop helping long before you run out of them.

~2 min across both sub-slides. The chart is the “aha” — a static formula is less convincing than watching four curves all hit a wall at different heights. EL-03 has students apply this exact ceiling to the capstone’s estimated 5% serial fraction. Chart source: diags/make_amdahl_chart.py.

The Uncomfortable Implication

  • Your GPU kernel is 50× faster than the CPU version. The serial part of your program is completely unchanged.
  • If the serial fraction is 5%, the end-to-end speedup of your whole program is still capped at 20×, no matter how fast that kernel gets
  • Cutting the serial fraction from 5% to 2.5% buys more end-to-end speedup than doubling the GPU kernel’s raw performance (numbers on the next slide)
  • Practical consequence: sometimes the highest-value optimization isn’t the kernel at all — it’s the data loading, the preprocessing step, or a serial aggregation on the host

Check the claim with the formula, starting from a 50× kernel and 5% serial:

Change Speedup
Start: \(p = 0.95\), \(n = 50\) \(1 / (0.05 + 0.95/50) =\) 14.5×
Double the kernel: \(p = 0.95\), \(n = 100\) \(1 / (0.05 + 0.95/100) =\) 16.8×
Halve the serial part: \(p = 0.975\), \(n = 50\) \(1 / (0.025 + 0.975/50) =\) 22.5×

Doubling the kernel adds 2.3 to the end-to-end speedup; halving the serial part adds 8.0.

~3 min across both sub-slides. This is the punchline students should carry into the capstone: profiling (this session’s first half) tells you where time goes; Amdahl tells you the ceiling on how much any one piece of optimization can help. Have students compute the middle row themselves before revealing it.

Beyond Element-wise: What Is a Stencil?

Element-wise (every kernel so far): output i depends only on input i. No thread ever looks at its neighbors.

Stencil: output i depends on a small neighborhood of inputs around i. The neighborhood’s half-width is the radius.

  • Classic examples: a moving average (each output = average of nearby inputs), image blur (each output pixel = weighted average of nearby pixels), numerical derivatives (a weighted combination of neighboring values)
  • The “one thread, one output” launch pattern (Oct 5) still applies. What changes is what each thread reads, not how many threads you launch
  • Neighborhoods overlap: in the figure, in[3] also feeds out[2] and out[4]. That’s harmless for correctness (threads only read shared inputs, and each writes its own output) — but it matters for speed, as we’ll see at the end

~3 min across both sub-slides. Frame this explicitly as “the launch pattern you already know, applied to a kernel body that reads more than one input” — students shouldn’t feel like they’re learning an entirely new launch mechanic, just a new kernel-body shape. The overlap bullet plants the Radius vs. Cost slide.

The Boundary Problem

Every interior cell has real neighbors on both sides. Cells near the edges do not.

  • A stencil reads a neighborhood around each position — but positions near the edge have neighbors that fall outside the array entirely
  • A kernel won’t warn you: arr[-1] silently becomes the last element (Python-style negative indexing — an accidental wrap), and arr[n] reads past the end with no error, because Numba CUDA does no bounds checking
  • Every stencil kernel needs an explicit boundary policy — there is no “correct” default, only different reasonable choices with different tradeoffs
Policy Out-of-range neighbor becomes… Array of 10: neighbor index −1 reads
Clamp the nearest valid edge value arr[0]
Zero-pad zero 0
Wrap the value from the other side (circular) arr[9]

Clamp: edges repeat themselves. No fake values enter the average, so a flat edge stays flat. The usual choice for images.

Zero-pad: missing neighbors add nothing. Simple, but averages near the edge get pulled toward 0 (an image blurred this way gets a dark border).

Wrap: the array is treated as a circle. Right for periodic data (angles, a ring of sensors, a tiling texture); wrong for a photo, where the left edge has nothing to do with the right.

~4 min across the three sub-slides. Don’t rush past “there is no correct default” — this is a genuine design decision, not a fact to memorize. Different applications legitimately prefer different policies (image processing usually clamps or wraps; some signal-processing contexts zero-pad). The no-bounds-checking bullet is why “just read arr[i-1]” isn’t an option: a negative index quietly wraps to the end of the array, and an index >= n reads whatever memory follows (garbage, or a later crash) instead of raising IndexError.

Our Policy: Clamping

def clamp(x, lo, hi):
    return min(max(x, lo), hi)

clamp(-1, 0, 9)   # → 0  (snapped up)
clamp(5, 0, 9)    # → 5  (unchanged)
clamp(15, 0, 9)   # → 9  (snapped down)

This course uses clamping (also called edge-replication) throughout. Any neighbor index outside [lo, hi] is snapped to the nearest valid edge.

Read it inside-out: max(x, lo) fixes indices that are too small (−1 → 0); then min(…, hi) fixes ones that are too large (15 → 9). An index already in range passes through both unchanged.

Edge values get their “missing” neighbors filled with a repeat of the nearest real value — not a fabricated zero or a wraparound.

A kernel can’t call an ordinary Python function like clamp() above. Two ways around it:

# Option 1: write the logic inline, right where the index is used
j = min(max(i + d, 0), n - 1)

# Option 2: compile the helper for the GPU as a *device function*
@cuda.jit(device=True)
def clamp(x, lo, hi):
    return min(max(x, lo), hi)
  • A device function runs on the GPU and is called from a kernel (it can’t be launched with [blocks, threads]), and it can return a value — a kernel can’t
  • Lab 7 writes the clamp inline, which is what the kernels on the next slides do

The other two policies, inside the same neighbor loop:

# zero-pad: only add neighbors that exist (missing ones count as 0)
j = i + d
if 0 <= j < n:
    total += arr[j]

# wrap: Python's % is never negative for positive n  (-1 % 10 == 9)
j = (i + d) % n
total += arr[j]

Zero-pad skips the read entirely when j is out of range. Skipping a tap is the same as adding 0 — and the guard keeps us from ever touching arr[-1].

Wrap uses % to fold the index back into 0 … n−1: -1 % 10 == 9 and 10 % 10 == 0. (C’s % can return negatives; Python’s — and Numba’s — can’t.)

CK-07 deliberately switches to zero-padding, so make sure you understand the policies themselves, not just one line of code.

~4 min across the three sub-slides. Numba CUDA kernels can only call other GPU-compiled code — a plain Python def fails with a TypingError, but a @cuda.jit(device=True) function works fine. Inlining is just the simplest option for a one-liner like clamp, and it’s what Lab 7 does. Wrap via % assumes radius < n (true in every lab/checkpoint here).

A 1D Warm-up: Moving Average

@cuda.jit
def moving_average_1d(arr, out, n, radius):
    i = cuda.grid(1)
    if i < n:
        total = numba.float32(0.0)
        for d in range(-radius, radius + 1):
            j = min(max(i + d, 0), n - 1)   # clamp
            total += arr[j]
        out[i] = total / (2 * radius + 1)
  • Lines 3–4: one thread, one output — the same global index and bounds guard as every 1D kernel since Oct 5
  • Line 5: a float32 accumulator — a plain 0.0 would make it float64, the slow-on-a-T4 trap from Lab 05
  • Line 6: d runs from -radius to +radius inclusive (range stops one short, hence radius + 1): 2*radius + 1 taps. Radius 2 → a 5-wide window
  • Line 7: the clamp, applied once per neighbor read, before the index is used
  • Line 8: accumulate the neighbor’s value
  • Line 9: divide by the full window size. Clamping always supplies 2*radius + 1 real values, so even the edges are a true average

Launching it on [10, 20, …, 100] with radius = 2:

arr = np.arange(10, 101, 10, dtype=np.float32)   # [10, 20, ..., 100]
n = arr.size
d_arr = cuda.to_device(arr)
d_out = cuda.device_array_like(d_arr)            # GPU array, same shape/dtype, no copy

threads = 32
blocks = (n + threads - 1) // threads            # ceiling division: 1 block here
moving_average_1d[blocks, threads](d_arr, d_out, n, 2)
print(d_out.copy_to_host())

  • The ends are pulled toward the edge value: 16 instead of 30, 94 instead of 80. That’s clamping — the next slides trace exactly why

From 1D to 2D: Box Blur

@cuda.jit
def box_blur_2d(img, out, H, W, radius):
    row, col = cuda.grid(2)
    if row < H and col < W:
        total = numba.float32(0.0)
        for dr in range(-radius, radius + 1):
            for dc in range(-radius, radius + 1):
                r = min(max(row + dr, 0), H - 1)   # clamp row
                c = min(max(col + dc, 0), W - 1)   # clamp col
                total += img[r, c]
        out[row, col] = total / ((2 * radius + 1) ** 2)

What changed from the 1D version:

Lines 3–4: cuda.grid(2) gives each thread a (row, col) pair; the guard now checks both dimensions (Module 2’s 2D launch)

Lines 6–7: two nested loops: dr walks the rows of the window, dc its columns — a (2·radius+1) × (2·radius+1) square

Lines 8–9: the row and column are clamped independently: a pixel on the top edge clamps only r; a corner pixel clamps both

Line 11: divide by the number of taps, now the square of the window width

This is image convolution. A box blur is the simplest one: every neighbor weighted equally. (A Gaussian blur — Lab 7’s bonus — just multiplies each tap by a weight)

An interior pixel needs no clamping: all 9 taps are real pixels.

At the corner, 5 of the 9 taps fall off the image. Clamping turns them into reads of img[0,0] (×4 total), img[0,1] (×2) and img[1,0] (×2), plus the one real img[1,1].

A tiny test you can check by hand — a 4×4 image, radius = 1:

img = np.arange(16, dtype=np.float32).reshape(4, 4)   # rows: 0-3, 4-7, 8-11, 12-15
H, W = img.shape
d_img = cuda.to_device(img)
d_out = cuda.device_array_like(d_img)

threads = (16, 16)                                     # 256 threads per block
blocks = ((H + 15) // 16, (W + 15) // 16)              # (rows of blocks, cols of blocks)
box_blur_2d[blocks, threads](d_img, d_out, H, W, 1)
print(d_out.copy_to_host().round(2))

 [ 4.33  5.    6.    6.67]

  • Interior out[1,1] = 5.0 — the plain average of the 3×3 block around it, no clamping

Radius vs. Cost

Radius Window size Taps per output pixel
1 3×3 9
2 5×5 25
4 9×9 81
8 17×17 289
  • Taps per pixel = \((2r+1)^2\): it grows with the square of the radius — doubling the radius roughly quadruples the memory reads and arithmetic per output
  • Lab 7 has you compare blur strength across a few radii and connect the visual result back to this table

Neighboring windows overlap: every input is read by 2r+1 threads in 1D, and (2r+1)² threads in 2D.

In the naive kernel each of those is a separate global-memory read of the same value. Loading a neighborhood once into fast on-chip memory is exactly what Module 4’s shared-memory tiling does.

(L1/L2 catch some of this reuse in practice, as they did for matmul; shared memory makes it explicit.)
