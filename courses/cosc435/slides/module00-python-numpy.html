Why This Course, Why Now

  • Every app you used this morning likely touched a GPU somewhere: the phone camera’s portrait mode, a voice assistant, a recommendation feed, a video call’s background blur
  • Large AI models (the kind behind ChatGPT, image generators, etc.) are trained and run almost entirely on GPUs — not CPUs
  • Five years ago, “GPU programming” was a niche graphics/gaming skill. Today it’s one of the most in-demand skills in computing, from finance to genomics to robotics
  • This course teaches you to think and program in the style that makes GPUs fast — not just to call a library

The Question This Course Answers

You are given a problem and a chip with thousands of tiny processors. How do you split the problem into thousands of pieces that can all run at the same time, and keep those processors from sitting idle?

  • Every module this semester answers one piece of this question
  • By the end, you’ll write code that runs on real GPU hardware — not simulate it, not read about it, actually run it

~2 min. This is the organizing question of the whole course — plant it early, return to it at the start of every module going forward (module01 already references “the question for this course”).

The Capstone Teaser: Songs as Numbers

  • Imagine a music app with 100,000 songs. Each song is described by 64 numbers (a “fingerprint” capturing its tempo, mood, instrumentation, etc.)
  • To find songs similar to one you like, the app multiplies your song’s 64 numbers against every other song’s 64 numbers, and adds up the results — a dot product
  • Do that 100,000 times, for every user, in real time: that’s 100,000 × 64 multiply-and-add operations, repeated continuously — a textbook GPU workload
  • This exact computation is your semester-long capstone project

~3 min. Don’t explain the math of dot products yet — that’s Session 3 and EL-01 (3Blue1Brown). Here the point is purely motivational: a concrete, relatable, real system that needs exactly the kind of massive repeated arithmetic a GPU is built for.

One Cashier vs. Twenty Lanes

From Graphics Card to Compute Engine

  • GPUs were originally built for one job: color millions of screen pixels, many times per second, for video games
  • Coloring a pixel is simple arithmetic, and every pixel’s color is independent of its neighbors — the same simple job, repeated millions of times, with no coordination needed
  • Around 2007, NVIDIA released tools (CUDA) letting programmers repurpose that pixel-coloring hardware for any problem shaped like “the same simple job, repeated millions of times” — not just pixels
  • Scientific simulation, finance, and eventually AI all turned out to be full of exactly that shape of problem

Session 2 · Sep 2 · Python for Java Developers

Same Logic, Different Grammar

  • You already know how to program: variables, loops, conditionals, functions — that thinking transfers completely
  • What’s different is syntax — the words and punctuation Python expects instead of Java’s
  • Today is a translation exercise, not a “learn programming from scratch” lecture
  • Goal by the end of class: read any short Python snippet and know what it does, even before you’ve memorized every keyword

~2 min. Reassure the room explicitly — many students hearing “new language” panic unnecessarily. Frame this as vocabulary, not new concepts.

No More Type Declarations

Java

int count = 5;
double price = 9.99;
String name = "Ada";
boolean done = false;

Python

count = 5
price = 9.99
name = "Ada"
done = False
  • Python infers the type from the value — you never write int, double, or String before a variable
  • The variable can even change type later (usually a bad idea, but Python allows it — Java does not)
  • Capitalization matters: Python’s True/False/None, not Java’s true/false/null

~3 min. Live-type this in a Colab cell rather than just showing it — run type(count), then reassign count = "five" and run type(count) again to make the “types are not fixed” point concrete.

Dynamic Typing: The Grammar-Teacher Analogy

  • Java is a strict grammar teacher: before you say a sentence, you must announce what part of speech every word is going to be — noun, verb, adjective — and the teacher checks you announced correctly before you’re allowed to speak
  • Python assumes you know what you mean, and figures out the parts of speech from context as you go
  • Trade-off: Java catches certain mistakes before the program ever runs (compile-time). Python only discovers a mismatch when that line actually executes (run-time) — so Python programs can fail later and more unexpectedly than Java ones
  • This is why Python code tends to look shorter — but it also means you need to test what you write more carefully

~3 min. This analogy is worth landing well — it explains why Python looks so sparse compared to Java without requiring any compiler-theory vocabulary the students don’t have.

Indentation Is the Syntax

Java

if (score >= 60) {
    System.out.println("Pass");
} else {
    System.out.println("Fail");
}

Python

if score >= 60:
    print("Pass")
else:
    print("Fail")
  • No { } braces, no ; semicolons — a colon : opens a block, and indentation (consistent spaces) marks what’s inside it
  • Mixing tabs and spaces, or indenting inconsistently, is a real error in Python — it isn’t just a style preference like in Java
  • Colab auto-indents for you after a colon — trust it, don’t fight it

~3 min. This trips up Java developers hard in Week 1 — an accidentally-misaligned line is a silent bug, not a compiler error shouting at you. Emphasize it strongly.

For Loops, Side by Side

Java

for (int i = 0; i < 5; i++) {
    System.out.println(i);
}

Python

for i in range(5):
    print(i)
  • Java’s for-loop spells out three separate things: start, condition, increment
  • Python’s range(5) bundles all three into one call: produces 0, 1, 2, 3, 4 — five values, not including 5
  • range(start, stop) and range(start, stop, step) both work, same off-by-one convention: stop is never included

~3 min. The “stop is excluded” rule is the single most common off-by-one bug source this semester — call it out explicitly and have students predict range(2, 8)’s output before revealing it.

Looping Over Data Directly

Java

int[] scores = {88, 92, 75};
for (int s : scores) {
    System.out.println(s);
}

Python

scores = [88, 92, 75]
for s in scores:
    print(s)
  • Java’s enhanced for-loop and Python’s for x in list do the same thing: hand you each element in turn, no index needed
  • Need the index too? for i, s in enumerate(scores): gives you both — closest Python equivalent to a classic indexed loop

~2 min. Students will reach for for i in range(len(scores)): print(scores[i]) out of habit — show it works, then show for s in scores: is the idiomatic version and gets used almost everywhere in this course.

While Loops and Conditionals

Java

int n = 10;
while (n > 0) {
    n--;
}
if (n == 0 && ready) {
    n = 1;
}

Python

n = 10
while n > 0:
    n -= 1

if n == 0 and ready:
    n = 1
  • &&, ||, ! in Java become the words and, or, not in Python
  • No n-- or n++ shorthand in Python — write n -= 1 / n += 1
  • == still means “equals” in both languages — that one didn’t change

~2 min. Quick slide, mostly a reference table students will return to — don’t over-explain, just point out the word-vs-symbol swap.

Functions, Side by Side

Java

static double average(
        int a, int b) {
    return (a + b) / 2.0;
}

Python

def average(a, b):
    return (a + b) / 2
  • def replaces the return-type-plus-name pattern — Python functions don’t declare a return type
  • No static, no access modifiers (public/private) — Python’s simplicity here is deliberate, not something being hidden
  • Python allows default arguments: def average(a, b=0): lets a caller omit b entirely — Java requires overloading a whole separate method for that

~3 min. Default arguments are new territory for a Java-only background — worth a concrete second example (greet(name, greeting="Hello"), called both with and without greeting).

Lists: Java’s ArrayList, Python’s list

Java

ArrayList<Integer> nums =
    new ArrayList<>();
nums.add(10);
nums.add(20);
nums.get(0);
nums.size();

Python

nums = [10, 20]
nums.append(30)
nums[0]
len(nums)
  • Python’s list is built into the language — no import, no <Integer> type parameter
  • A single Python list can hold mixed types ([1, "two", 3.0]) — Java’s ArrayList<Integer> cannot
  • len(nums) is a function call, not a method — this is a common early typo (nums.len() does not exist)

~3 min. The “mixed types allowed” point is worth a live demo — it looks alarming to a Java developer at first. Note explicitly that NumPy arrays (Session 3) are not like this — they go back to Java’s “one type only” discipline, for reasons we’ll cover then.

List Slicing

nums = [10, 20, 30, 40, 50]

nums[1:3]     # [20, 30]   — index 1 up to (not including) index 3
nums[:2]      # [10, 20]   — from the start up to index 2
nums[3:]      # [40, 50]   — from index 3 to the end
nums[-1]      # 50         — negative index counts from the end
nums[::2]     # [10, 30, 50] — every 2nd element
  • Slicing has no Java equivalent — closest is manually looping and copying into a new array
  • The pattern [start:stop:step] — memorize this now, because NumPy array slicing (Session 3) uses exactly the same syntax

~3 min. Emphasize the last bullet strongly — this slide is deliberately positioned as direct setup for Session 3. Have students predict nums[1:-1] before revealing the answer.

None vs. null, and Truthiness

result = None          # Python's "no value" — like Java's null

if result:              # careful: 0, "", [], and None are all "falsy"
    print("has a value")
else:
    print("nothing here")
  • None is Python’s null — same idea, different capitalization and spelling
  • Java only treats null itself as special in an if. Python additionally treats 0, 0.0, "" (empty string), and [] (empty list) as “falsy” in an if — this has no Java parallel and causes real bugs
  • Rule of thumb: if you mean “is this specifically None,” write if result is None:, not just if result:

~2 min. This is a genuine gotcha, not a style note — an empty list silently behaving like “false” surprises every Java developer at least once. Worth a quick live example: if []: print("shown"); else: print("not shown").

List Comprehensions: Thinking in Expressions

The loop way

squares = []
for x in range(10):
    squares.append(x ** 2)

The Pythonic way

squares = [x ** 2 for x in range(10)]
  • Both produce the exact same list — the second is Python’s idiomatic shorthand for “build a new list from a rule”
  • Read it right-to-left: “for x in range(10),” “compute x squared,” “collect into a list”
  • You’ll see this pattern constantly in other people’s Python code this semester — recognize it even if you don’t write it yet

~3 min. Don’t require fluency writing these yet — just reading comprehension. This slide is also a deliberate bridge: next session, NumPy will replace both versions above with x ** 2 on a whole array, no loop or comprehension at all.

Why This Matters for GPU Programming

  • Python’s flexibility (no type declarations, quick to write) is exactly why we prototype in it
  • But that same flexibility has a cost: a Python for loop is checking and re-checking types on every single iteration — work a compiled Java loop never has to do
  • Next session, we’ll measure that cost, and meet the tool (NumPy) that removes it — which is also the first step toward the GPU way of thinking

Session 3 · Sep 9 · NumPy Foundations

The Goal of This Module

  • Everything we do for the rest of the semester operates on arrays — NumPy is the mental model, CUDA (Module 2 onward) is the execution engine that runs that same model on a GPU
  • If you can write fast, loop-free NumPy code today, you already think the way GPU programming requires
  • Today’s dot product example reappears, unchanged, on the very last day of this course

~2 min. Same framing as before but now delivered after students have Python fundamentals under their belt — reference Session 2’s “why loops are secretly expensive” teaser directly.

The Array as the Unit of Work

  • A Python list can hold anything, in any mix — flexible, but that flexibility is exactly what makes it slow at scale (Session 2’s “checking types every iteration” cost)
  • A NumPy array gives up that flexibility on purpose: one fixed type, laid out as one contiguous block of memory
  • In exchange, operations apply to the entire block at once — not element by element in a Python loop
import numpy as np
x = np.array([1.0, 2.0, 3.0], dtype=np.float32)
y = x * 2          # not a loop — one operation over the whole array

~3 min. Live-demo: type([1, "two", 3.0]) works fine, then np.array([1, "two", 3.0]) — show it silently converts everything to strings. This makes “one fixed type” concrete rather than abstract.

dtypes Matter

dtype bytes use case
float64 8 NumPy’s default, high precision
float32 4 GPU default, half the memory of float64
int32 4 indices, counts
  • Every element in an array shares one dtype — that’s the “give up flexibility” trade from the previous slide, made concrete
  • GPUs are built to move and compute on float32 efficiently; using float64 on a GPU can be noticeably slower and always uses twice the memory
  • We use float32 throughout this course, starting today — get in the habit now

~3 min. Ask: “if float32 uses half the memory, and a GPU’s speed is often limited by how fast it can move data (not compute), what does halving the memory do to speed?” Let students reason toward “roughly doubles throughput” themselves — this is a light preview of Module 3’s memory-bandwidth material, don’t over-formalize it now.

Shape, Reshape, Indexing

a = np.arange(24, dtype=np.float32)   # [0, 1, 2, ..., 23]  — shape (24,)
b = a.reshape(4, 6)                   # same 24 numbers, viewed as 4 rows × 6 cols
c = b[2, :]                           # row 2, all columns
d = b[:, 3]                           # all rows, column 3
  • reshape doesn’t move or copy any numbers — it just changes how the same block of memory is interpreted
  • Shape is always (rows, cols): b.shape == (4, 6)
  • Indexing syntax [row, col] and slicing [start:stop] are the exact patterns from Session 2’s list-slicing slide, now extended to two dimensions

~3 min. Callback explicitly to the list-slicing slide from Session 2 — “you already learned this syntax, we’re just adding a second dimension.”

Memory Layout — Why Shape Isn’t Free

[DIAGRAM] — A single row of 24 numbered memory cells (addresses 0–23) drawn as a horizontal strip. Below it, the same 24 cells regrouped into a 4×6 grid, with color-coded bands showing that grid row 0 = memory addresses 0–5, row 1 = addresses 6–11, row 2 = addresses 12–17, row 3 = addresses 18–23. An arrow labeled “reshape — same memory, new labels” connects the strip to the grid.

  • A 2D array’s rows are contiguous in memory — row 0’s six numbers sit right next to each other, then row 1’s six numbers, and so on (“row-major” order)
  • This means walking across a row is a straight walk through memory; walking down a column jumps around
  • File this away — it becomes the whole story behind memory coalescing, one of the most important GPU performance topics, in Module 3

~3 min. Don’t derive coalescing here — that requires GPU thread concepts they don’t have yet. The only goal today is: shape is a label on memory, not a rearrangement of it, and rows are the “straight walk.”

Reducing Along an Axis

grid = np.array([[1, 2, 3],
                  [4, 5, 6]], dtype=np.float32)   # shape (2, 3)

np.mean(grid, axis=0)   # [2.5, 3.5, 4.5]  — one value per COLUMN
np.mean(grid, axis=1)   # [2.0, 5.0]       — one value per ROW
np.mean(grid)           # 3.5              — one value, every element
  • axis=0 collapses rows together — you get one result per column
  • axis=1 collapses columns together — you get one result per row
  • Memory trick: the axis number you pass is the dimension that disappears from the shape after the reduction — (2, 3) with axis=0 leaves shape (3,)
  • np.sum, np.max, np.min, np.argmax all take this same axis parameter

~3 min. This is a notoriously confusing NumPy detail — most students initially guess axis=0 means “reduce along rows” (i.e. row-wise), when it actually means “collapse the row dimension,” producing one value per column. Have students predict np.mean(grid, axis=1) before revealing it. This exact skill is on Quiz 1 and gets hands-on practice in Lab 2’s last exercise.

Reducing Along an Axis, Visually

[DIAGRAM] — A 2×3 grid of numbered cells (values 1-6 as in the code above). Left panel: downward arrows through each column labeled “axis=0 — collapse rows,” converging into a single row of 3 output cells below the grid reading 2.5, 3.5, 4.5. Right panel: the same grid with rightward arrows through each row labeled “axis=1 — collapse columns,” converging into a single column of 2 output cells beside the grid reading 2.0, 5.0.

  • The arrows show which direction values get squashed together — not which direction you “read” the axis number
  • Same picture applies to np.sum, np.max, and every other axis-aware reduction

~2 min. Pair this directly with the mnemonic from the previous slide — seeing the arrows collapse in the opposite direction from what “axis=0” sounds like is what makes the rule stick.

Broadcasting Rules

a = np.ones((4, 6), dtype=np.float32)              # shape (4, 6)
b = np.array([1, 2, 3, 4, 5, 6], dtype=np.float32) # shape (6,)

c = a + b   # b is stretched across every row — result shape (4, 6)
  • NumPy compares shapes right to left. Here: 6 matches 6 — compatible
  • A dimension of size 1 (or a missing dimension) is automatically stretched to match the other array — no data is actually copied
  • If shapes don’t line up this way, NumPy raises a shape-mismatch error rather than guessing what you meant

~3 min. This is consistently the single most-tripped-over NumPy concept in labs. Have students predict the shape of a + b before revealing the comment, then try a deliberately mismatched pair (e.g. shape (6,) against shape (4, 5)) live to show the error message.

Broadcasting, Visually

[DIAGRAM] — A 4×6 grid of cells labeled a, all filled with the value 1. Beside it, a single row of 6 cells labeled b, with values 1 through 6. An animated-looking set of 4 faint copies of row b stacked to show it being “stretched” downward to align with each row of a, with a + symbol between the two stacks and a resulting 4×6 grid c where each row reads 2, 3, 4, 5, 6, 7.

  • The stretching in the diagram is conceptual — NumPy never actually duplicates b in memory; it just reuses the same 6 numbers for every row
  • This “reuse without copying” trick is why broadcasting is fast, not just convenient

~3 min. Emphasize the “no copy happens” point explicitly — it’s easy to walk away thinking broadcasting is expensive because the mental picture looks like duplication.

Boolean Masking

scores = np.array([0.9, 0.3, 0.7, 0.1, 0.8], dtype=np.float32)
mask   = scores > 0.5           # [True, False, True, False, True]
high   = scores[mask]           # [0.9, 0.7, 0.8]
  • scores > 0.5 doesn’t compare once — it compares every element, producing a full array of True/False
  • Using that Boolean array as an index selects only the True positions — no loop, no if
  • This exact pattern (compare, then select) is used in Lab 2 and reappears constantly for the rest of the course

~3 min. Live-demo: build the mask, print it separately from the selection, so students see the intermediate Boolean array rather than the two steps blurring together.

Why Loops Are Slow

[DIAGRAM] — Two side-by-side panels. Left panel, “Python loop”: a single translator sitting at a desk, translating a document one word at a time — read a word, look it up, write it down, repeat — with a stack of 2,000,000 words waiting. Right panel, “NumPy vectorized”: the same document fed into a printing press that stamps every word at once in a single pass, with a stopwatch showing a dramatically shorter time.

  • A Python for loop over an array processes one element at a time, and for every single element, Python re-checks the type, re-does bounds checking, and re-dispatches the operation — overhead paid 2,000,000 times for a 2,000,000-element array
  • NumPy’s vectorized operations hand the entire array to pre-compiled C code in one call — the type-checking and dispatch overhead is paid once, not once per element
  • Typical measured speedup on Colab: 50–200×, purely from removing per-element Python overhead — no algorithm changed, only how the same arithmetic gets executed

~4 min. This is the conceptual payoff of the whole module — connect it explicitly back to Session 2’s “why this matters for GPU programming” teaser slide. Note for later: Lab 3 / CK-3 (next module) has students measure this exact speedup themselves; today is intuition, next week is the number.

Not Everything Vectorizes

Vectorization works when every output element can be computed independently — NumPy doesn’t care what order it processes them in. Some computations don’t have that property.

# Fibonacci: each value depends on the two before it
fib = [0, 1]
for i in range(2, 10):
    fib.append(fib[i-1] + fib[i-2])   # MUST know fib[i-1] before computing fib[i]
  • There’s no single NumPy call that produces this — fib[i] cannot exist before fib[i-1] does
  • This is called a serial dependency: step i needs the result of step i-1, not just its position
  • Contrast with everything else today: x**2 + 1, boolean masks, dot products — every output element only needs the input values, never another output

~2 min. This is the one exception to “just vectorize it” that students need before Quiz 1 — ask them to spot the difference between this Fibonacci loop and the polynomial-evaluation loop from earlier: same syntax shape, but one has a dependency between iterations and one doesn’t. This same idea reappears in Module 1 as a reason GPUs specifically struggle with certain problems — today it’s just about NumPy.

The Dot Product

  • A dot product multiplies two same-length lists of numbers position by position, then adds up all the products
  • It shows up constantly: a weighted average is a dot product; a similarity score is a dot product; a full matrix multiply is just many dot products computed at once

\[\mathbf{u} \cdot \mathbf{v} = u_0 v_0 + u_1 v_1 + \cdots + u_{D-1} v_{D-1}\]

u = np.array([1.0, 2.0, 3.0], dtype=np.float32)
v = np.array([4.0, 5.0, 6.0], dtype=np.float32)
np.dot(u, v)     # 1*4 + 2*5 + 3*6 = 32.0

~3 min. Keep the geometric meaning (angle, projection) out of this slide entirely — that’s EL-01’s job (3Blue1Brown). Here we want only the mechanical pattern: multiply pairs, sum the results. Work the 3-element example on the board before revealing the code.

Similarity via Dot Product

song_a = np.array([0.6, 0.8, 0.0], dtype=np.float32)  # "fingerprint" vector
song_b = np.array([0.8, 0.6, 0.0], dtype=np.float32)  # similar mood/tempo to a
song_c = np.array([0.0, 0.0, 1.0], dtype=np.float32)  # totally different

print(np.dot(song_a, song_b))   # close to 1.0 — similar
print(np.dot(song_a, song_c))   # 0.0 — unrelated
  • When vectors are pre-normalized (length 1), their dot product lands between −1 and 1, and a value near 1 means “point in nearly the same direction” — which we’re using here as a stand-in for “sound similar”
  • This is the Session 1 capstone teaser, now with real, runnable code behind it

~3 min. Callback explicitly to the Session 1 “songs as numbers” slide — students should recognize this as the same example, now computable.

Matrix Multiply as Batch Dot Products

Q = np.random.randn(1000, 64).astype(np.float32)    # 1,000 query songs
D = np.random.randn(100_000, 64).astype(np.float32) # 100,000 database songs

sim = Q @ D.T   # sim[i, j] = dot product of query i with database song j
                # shape: (1000, 100_000)
  • One @ call computes 100 million individual multiply-and-add pairs — every query against every database song
  • NumPy hands this to a highly optimized library (BLAS) that’s already parallel across your CPU’s cores
  • We’ll do the same computation on a GPU’s thousands of cores in the capstone — same math, radically more parallelism

~3 min. Optional live-demo: time this cell on Colab CPU with %%time — it’s fast enough to look almost instant, which sets up the “and yet the GPU is still much faster” hook for later modules. If short on time, this slide can be trimmed to the code + first bullet only.

What NumPy Cannot Do

  • NumPy runs on the CPU. Q @ D.T above calls into parallel C code — but any Python for loop you write yourself still runs one instruction at a time on one core
  • A modern GPU has on the order of 10,000 arithmetic cores — NumPy alone has no way to address that many independent workers at once
  • The open question: if we want to run 100 billion dot products per second, how do we tell hardware to do all of them simultaneously? That question drives the next four modules
