Why Access Pattern Matters

[DIAGRAM] — 32 threads in a single warp, each about to read one float from global memory. Top scenario, “coalesced”: all 32 threads’ target addresses are drawn as 32 consecutive slots in one contiguous 128-byte memory block, with a single arrow labeled “1 memory transaction” pointing from the whole block to the warp. Bottom scenario, “strided”: the 32 threads’ target addresses are drawn scattered across a much wider span of memory (gaps between each), with 32 separate arrows each labeled “1 transaction,” captioned “32 transactions — 32× the bandwidth cost for the same 32 floats.”

  • The GPU doesn’t fetch memory one float at a time — it fetches in fixed-size blocks (transactions), and ideally serves an entire warp’s requests from as few transactions as possible
  • When 32 threads in a warp request 32 consecutive addresses, the hardware can often satisfy all of them with a single transaction — this is called coalesced access
  • When those same 32 threads request addresses scattered far apart, the hardware needs a separate transaction per address (or per small cluster) — up to 32× the memory traffic for the identical amount of useful data
  • This is the single most important hardware fact for writing fast kernels — every memory-access decision from here through the rest of the course traces back to this slide

~4 min. Worth pausing on: this isn’t about how much data a kernel reads — it’s purely about the pattern of addresses across threads in the same warp. Two kernels reading the identical set of bytes can differ by 32× in transaction count depending only on which thread reads which address.

Coalesced Access

@cuda.jit
def coalesced_kernel(arr, out):
    i = cuda.grid(1)
    if i < arr.shape[0]:
        out[i] = arr[i] * 2.0   # thread i reads element i
  • Thread 0 reads element 0, thread 1 reads element 1, …, thread 31 reads element 31 — 32 consecutive threads, 32 consecutive addresses
  • This falls into a single memory transaction (or a small, fixed number) covering one contiguous cache line
  • Every element-wise kernel you’ve written since Module 2 (arr[i] = arr[i] * scalar, out[i] = a[i] + b[i]) already has this property — you’ve been writing coalesced kernels without necessarily naming the pattern

~2 min. Reassuring framing: this isn’t a new skill to learn from scratch, it’s a name for something students have already been doing correctly since Lab 4. What’s new is recognizing when a kernel accidentally breaks this pattern (next slide).

Strided Access

STRIDE = 128

@cuda.jit
def strided_kernel(arr, out):
    i = cuda.grid(1)
    idx = i * STRIDE
    if idx < arr.shape[0]:
        out[i] = arr[idx] * 2.0   # thread i reads element i*128
  • Thread 0 reads element 0, thread 1 reads element 128, thread 2 reads element 256, … — 32 consecutive threads, but addresses spread across 4,096 bytes
  • Each of those 32 reads typically needs its own memory transaction — roughly 32× the memory traffic of the coalesced version, for the exact same 32 useful values
  • Lab 8 has you time both versions directly and measure this ratio empirically — the slowdown is a hardware specification, not a fluke of one run

~3 min. Lab 08 Exercise 1 sweeps a range of stride values and has students interpret the resulting time-vs-stride curve — this slide is the theory that curve is confirming.

2D Access Patterns

# Row access: consecutive in memory — coalesced ✓
@cuda.jit
def row_kernel(mat, out):
    row, col = cuda.grid(2)
    if row < mat.shape[0] and col < mat.shape[1]:
        out[row, col] = mat[row, col] * 2.0

# Column access: strided in memory — not coalesced ✗
@cuda.jit
def col_kernel(mat, out):
    row, col = cuda.grid(2)
    if row < mat.shape[0] and col < mat.shape[1]:
        out[col, row] = mat[row, col]   # transpose — watch the indices
  • NumPy (and Numba) arrays are row-major by default: element [r, c] sits at memory offset r * n_cols + c
  • Consecutive threads with the same row, increasing column → consecutive memory offsets → coalesced (the row_kernel above)
  • Consecutive threads with the same column, increasing row → offsets that jump by n_cols each time → strided, not coalesced (the transpose pattern in col_kernel)
  • Lab 8’s Exercise 3 has you measure exactly this row-vs-column contrast on a real matrix

~3 min. The row-major offset formula (r * n_cols + c) is worth writing out explicitly — it’s the concrete arithmetic reason “same row, varying column” is coalesced and “same column, varying row” isn’t, rather than something to take on faith.

Why This Sets Up Shared Memory

  • Coalescing helps every global-memory read be as cheap as possible — but it doesn’t reduce how many reads happen
  • The tiled matrix multiply later in this module attacks a different problem: the same global-memory element gets read by many different threads (Lab 5’s naive matmul reads each row of A and column of B repeatedly, once per output element that needs it)
  • Shared memory (next section) lets a block load each needed element from global memory once, then have every thread in the block reuse that one load — cutting the number of global reads, not just making each one cheaper
  • Coalescing and shared-memory reuse are complementary, not competing, techniques — a well-tuned kernel uses both

Why Coalescing Alone Isn’t Enough

  • Global memory delivers roughly 2 TB/s of bandwidth on a modern GPU — but a single float32 is only 4 bytes, so that’s “only” on the order of 500 billion individual float reads per second at peak
  • ALUs can execute billions of FLOPs per second — often far more than 500 billion, if each one only needed one memory read to do its job
  • Arithmetic intensity (FLOPs performed per byte moved, previewed back in Module 1) is what determines whether you can actually reach that ALU speed, or whether memory bandwidth caps you first
  • Oct 21’s coalescing makes each individual memory transaction as cheap as possible — but it does nothing to reduce how many transactions a kernel needs. That’s the gap shared memory closes

~3 min. Explicit framing: coalescing (last session) and shared-memory reuse (this session) are two different levers on the same memory-wall problem — one makes each access cheaper, the other reduces the number of accesses needed at all.

The Roofline Intuition

[DIAGRAM] — A roofline chart: x-axis “arithmetic intensity (FLOPs/byte),” log scale; y-axis “achieved performance (FLOPs/s),” log scale. Two “roof” lines meeting at a corner: a rising diagonal line on the left labeled “memory bandwidth roof,” which transitions into a flat horizontal line on the right labeled “compute (peak FLOPS) roof.” Two points are plotted underneath the roofline: one labeled “naive matmul,” sitting low and to the left, close to the diagonal memory roof; another labeled “tiled matmul,” sitting further right and higher, closer to the flat compute roof.

  • Any kernel’s achieved performance is capped by whichever roof it’s under: if arithmetic intensity is low, the diagonal memory-bandwidth roof caps you regardless of how fast your ALUs are; if arithmetic intensity is high enough, the flat compute roof becomes the real limit
  • Naive matmul (Lab 5/Module 2) sits on the memory-bound side — Oct 7’s bottleneck diagnosis already established this: lots of global reads, little reuse per read
  • Tiled matmul (Oct 28) doesn’t add any new arithmetic — it does the same multiplications — but by reusing data out of shared memory instead of re-reading global memory, it raises effective arithmetic intensity and moves the achieved performance point up and to the right, toward the compute roof
  • We won’t formally derive this model (that’s beyond this course’s scope) — the picture is what matters: tiling’s entire purpose is to move a kernel’s dot rightward on this chart

~3 min. Students will confirm this empirically in Lab 9 — comparing naive vs. tiled matmul timings is exactly measuring these two points’ relative height. Keep the derivation at “picture level” — no formulas needed here.

Declaring Shared Memory

from numba import cuda
import numba

@cuda.jit
def demo_shared(arr):
    # Declare shared memory — size known at compile time
    s = cuda.shared.array(shape=256, dtype=numba.float32)

    i  = cuda.grid(1)
    ti = cuda.threadIdx.x       # local index within the block

    if i < arr.shape[0]:
        s[ti] = arr[i]          # load from global → shared
        cuda.syncthreads()      # all threads in block must reach here

        # Now every thread can read any element of s[]
        arr[i] = s[ti] * 2.0
  • Three new pieces of syntax here: cuda.shared.array (the declaration), a compile-time-fixed shape=, and cuda.syncthreads() (the barrier) — each explained on the next few slides

~2 min. Walk through the three new concepts by name before the rules slide formalizes them — students should recognize each one in the code above before moving on.

Rules of Shared Memory

  1. Shared scope: visible to every thread in the same block — not visible to threads in other blocks, even ones running concurrently on the same SM
  2. Size fixed at compile time: the shape= argument must be a literal or a module-level constant, never a variable computed at runtime
  3. Lifetime: exists only for the block’s lifetime — allocated when the block starts, gone the moment the block finishes
  4. Synchronization required: cuda.syncthreads() is a barrier — every thread in the block must reach it before any thread is allowed to continue past it

~3 min. The most common bug this session sets up for Lab 9: forgetting syncthreads() after writing to shared memory, so one thread reads a value before another thread has finished writing it — a race condition producing a silent wrong answer, no crash. Foreshadow this explicitly; Oct 28’s tiled kernel has two separate places this can go wrong.

cuda.syncthreads() — The Barrier

[DIAGRAM] — Four threads in a block, each drawn as a vertical timeline. Threads 0 and 1 write to shared memory first (short colored bars near the top of their timelines), while threads 2 and 3 are still busy with unrelated work (their timelines show a gap). A horizontal dashed line labeled “syncthreads() barrier” crosses all four timelines at the same height. Below the barrier line, all four threads’ timelines resume together at the same point, now reading from shared memory. A second, smaller diagram to the right shows the without case: thread 2’s read (an arrow reaching into thread 0’s write) happens before thread 0’s write completes, crossing into thread 0’s timeline before its write bar — labeled “race: read arrives too early.”

  • syncthreads() is a rendezvous, not a delay — every thread in the block must physically arrive at that line of code before the fastest thread is allowed to proceed past it
  • Without it: whichever thread happens to reach the read first gets whatever was in shared memory at that moment — sometimes correct, sometimes stale garbage, with no error raised either way
  • A subtle trap: calling syncthreads() inside an if branch that not every thread in the block takes causes a deadlock — the threads that skipped the branch never arrive at the barrier, so the threads waiting there wait forever. Rare in this course’s labs, but worth knowing exists

~3 min. The deadlock case is worth a brief mention but not a deep dive — students won’t hit it in this course’s structured exercises, but it’s a real failure mode in general CUDA code and a satisfying “why does my program just hang” answer if they ever encounter it later.

A Worked Example: Block-Level Maximum

@cuda.jit
def block_max_kernel(arr, out):
    s = cuda.shared.array(shape=256, dtype=numba.float32)
    i  = cuda.grid(1)
    ti = cuda.threadIdx.x

    if i < arr.shape[0]:
        s[ti] = arr[i]
    else:
        s[ti] = -1e9            # identity element for max
    cuda.syncthreads()

    # Reduction to find block maximum — stride halving
    stride = 128
    while stride > 0:
        if ti < stride:
            if s[ti + stride] > s[ti]:
                s[ti] = s[ti + stride]
        cuda.syncthreads()
        stride //= 2

    if ti == 0:
        out[cuda.blockIdx.x] = s[0]

Shared Memory Banks

  • Shared memory isn’t one monolithic block of storage — physically, it’s divided into equally-sized banks (32 banks is the standard width, matching warp size), and consecutive 4-byte words are assigned to consecutive banks in a round-robin pattern
  • Each bank can service exactly one memory request per cycle — but different banks can all be accessed simultaneously
  • When all 32 threads in a warp read from 32 different banks in the same cycle, every read happens in parallel — this is the fast case, and it’s what you get by default with straightforward, consecutive access patterns

~3 min. This is the shared-memory analogue of coalescing (Oct 21) — same underlying idea (parallel hardware wants parallel, non-overlapping requests), one level closer to the compute units.

Bank Conflicts

[DIAGRAM] — 8 shared-memory banks drawn as 8 numbered vertical columns (simplified from 32 for readability). Left scenario, “no conflict”: 8 threads, each with an arrow pointing to a different bank (thread 0 → bank 0, thread 1 → bank 1, … thread 7 → bank 7) — all 8 arrows land in parallel, captioned “8 requests, 1 cycle.” Right scenario, “conflict”: 8 threads all arrow into the same single bank (bank 3), captioned “8 requests, but only 1 can be served per cycle → 8 cycles, serialized.” A third, small callout shows one exception: all 8 arrows pointing to the same address within the same bank, captioned “broadcast — free, not a conflict.”

  • A bank conflict happens when two or more threads in the same warp request different addresses that happen to land in the same bank — those requests can’t be served simultaneously, so the hardware serializes them, one at a time
  • In the worst case, all 32 threads hit the same bank with different addresses: a 32-way conflict, taking roughly 32× as long as the conflict-free case for that one access
  • Exception: if every thread in the warp requests the same address (not just the same bank), the hardware broadcasts that one value to all of them in a single cycle — that’s not a conflict, it’s the best case
  • This typically shows up with strided access into a 2D shared-memory array — e.g., every thread reading a different row of the same column, when the array’s row length happens to be a multiple of the bank count

~3 min. Conceptual/awareness-level content — this course doesn’t checkpoint or quiz bank conflicts directly (schedule.md commits to teaching it here, but no lab exercise currently isolates it). Still worth teaching properly: it’s genuinely useful GPU knowledge, and it’s exactly the kind of subtlety that explains “why is my shared-memory kernel not as fast as I expected” once students start experimenting beyond the assigned labs.

Avoiding Bank Conflicts: Padding

# Conflict-prone: TILE columns, stride exactly matches the bank pattern
tile = cuda.shared.array((TILE, TILE), numba.float32)

# Padded: one extra column shifts the stride, breaking the alignment
tile_padded = cuda.shared.array((TILE, TILE + 1), numba.float32)
  • The classic fix for a systematic, stride-caused bank conflict: allocate the shared array with one extra column than the problem actually needs
  • That single extra column shifts every subsequent row’s starting bank by one position — which is usually enough to break the alignment that was causing threads to repeatedly collide on the same bank
  • The padding column itself is never used for real data — it’s pure overhead, traded deliberately for avoiding serialized access
  • You won’t be required to apply this technique in this course’s labs or checkpoints — it’s here so the option is in your toolkit if you ever profile a shared-memory kernel and find bank conflicts are the bottleneck

~2 min. Keep this at “here’s the standard trick” level — don’t derive exactly which access patterns in this course’s own tiled-matmul kernel would or wouldn’t benefit from padding; that’s a level of hardware-specific detail beyond this course’s scope, and worth saying so if a curious student asks.

The Naive Approach

@cuda.jit
def matmul_naive(A, B, C):
    row, col = cuda.grid(2)
    if row < C.shape[0] and col < C.shape[1]:
        acc = 0.0
        for k in range(A.shape[1]):    # inner dimension
            acc += A[row, k] * B[k, col]
        C[row, col] = acc
  • Thread (row, col) reads all of row row from A and all of column col from B — recall from Oct 26’s roofline slide, this is exactly why naive matmul is memory-bound
  • A[row, :] is read once by every thread that shares that row — N_col different threads, so that same data is fetched from global memory N_col separate times
  • B[:, col] is read once by every thread that shares that column — fetched from global memory N_row separate times
  • Every element of A and B is loaded from global memory roughly O(N) times over the course of the whole computation, when a single load would suffice

[DIAGRAM] — A small 4×4 matrix multiply. Highlight element A[0,2] with a star. Draw four arrows from that single starred cell to the four threads in column 2 of the output matrix C (threads (0,2), (1,2), (2,2), (3,2)), each arrow labeled “reads A[0,2] independently from global memory.” Caption: “One element, read from global memory 4 separate times — for a 4×4 problem. At 512×512, this same element would be read 512 times.”

~3 min. The 4×4 example makes O(N) concrete — worth having students compute how many times a single element is re-read at the actual Lab 5/6 scale (512×512): 512 separate reads of the same 4 bytes, all landing in the exact same place. That number is the motivation for everything that follows.

The Tiling Idea

[DIAGRAM] — Matrices A and B split into TILE×TILE submatrices (shown as a coarse grid overlaid on each matrix). One thread block, block (bx, by), is highlighted — arrows show it responsible for computing exactly one TILE×TILE submatrix of the output C. A 4-step numbered sequence beneath: “1. Load one tile of A into shared memory” → “2. Load one tile of B into shared memory” → “3. syncthreads() — wait for the whole block to finish loading” → “4. Every thread in the block computes its partial dot product using only the shared tiles, no further global reads this round” → looping arrow back to step 1 labeled “repeat for the next tile along the shared dimension.”

  • The fix for the O(N) problem: instead of each thread independently re-reading global memory, have the whole block cooperate to load each needed tile from global memory exactly once, into shared memory
  • Every thread in the block then reads from that shared tile as many times as it needs — shared-memory reads are fast (Oct 26) and don’t touch global memory at all
  • Net effect: each element of A and B is loaded from global memory once per block that needs it, not once per thread — for a TILE×TILE block, that’s a TILE× reduction in global-memory traffic for that data

~3 min. This is the single most important idea in the module — the whole rest of this session is just implementing this four-step loop correctly in code. Make sure “the block loads once, every thread in it reuses that load” has fully landed before moving to code.

Tiled Kernel: Setup

TILE = 16

@cuda.jit
def matmul_tiled(A, B, C):
    # Shared memory tiles — size TILE×TILE each
    tile_A = cuda.shared.array((TILE, TILE), numba.float32)
    tile_B = cuda.shared.array((TILE, TILE), numba.float32)

    # Global position of this thread
    row = cuda.blockIdx.x * TILE + cuda.threadIdx.x
    col = cuda.blockIdx.y * TILE + cuda.threadIdx.y
    tx, ty = cuda.threadIdx.x, cuda.threadIdx.y

    acc = 0.0
  • TILE is declared as a Python constant, not a function parameter — Numba needs the shared-array shape fixed at compile time (Oct 26’s “Rules of Shared Memory”), so TILE must be a literal or a module-level constant
  • tile_A and tile_B are the block’s shared scratchpad — one TILE × TILE tile of each input matrix, reused by every thread in the block
  • row/col are this thread’s global position in the output (same formula as Module 2’s 2D indexing); tx/ty are its local position within the block — both are needed: global to know which output element this thread owns, local to know which shared-memory cell to read and write

~2 min. Point out explicitly: this setup code runs once per thread, before the tile loop — row, col, tx, ty, and acc are all computed a single time and then reused across every iteration of the loop that follows.

Tiled Kernel: Loop Over Tiles

    n_tiles = (A.shape[1] + TILE - 1) // TILE

    for t in range(n_tiles):
        # Load tile from global → shared
        if row < A.shape[0] and t * TILE + ty < A.shape[1]:
            tile_A[tx, ty] = A[row, t * TILE + ty]
        else:
            tile_A[tx, ty] = 0.0

        if t * TILE + tx < B.shape[0] and col < B.shape[1]:
            tile_B[tx, ty] = B[t * TILE + tx, col]
        else:
            tile_B[tx, ty] = 0.0

        cuda.syncthreads()              # wait for all loads

        for k in range(TILE):
            acc += tile_A[tx, k] * tile_B[k, ty]

        cuda.syncthreads()              # wait before overwriting shared

    if row < C.shape[0] and col < C.shape[1]:
        C[row, col] = acc
  • The two syncthreads() calls are the part almost everyone gets wrong the first time — the next slide explains exactly why both are required

~4 min. Walk through the loop body in order: bounds-checked load into tile_A/tile_B (zero-padding out-of-range entries so the accumulation stays correct even when the matrix size isn’t a multiple of TILE), first sync, the inner k loop accumulating from shared memory only, second sync. CK-14 (capstone) has two gaps in exactly this shape.

Why Two syncthreads()?

[DIAGRAM] — A timeline with 4 threads (thread 0-3), one horizontal row each, showing one iteration of the tile loop. Each timeline has a “load” segment, then a gap, then a “compute” segment, then a gap, then the start of the next iteration’s “load” segment. Two vertical dashed barrier lines cross all four timelines: the first labeled “sync 1” positioned right after the slowest thread’s “load” segment ends (before any “compute” segment begins); the second labeled “sync 2” positioned right after the slowest thread’s “compute” segment ends (before any next-iteration “load” segment begins). Thread 3 is drawn with a visibly longer “load” segment than threads 0-2, to show why the barrier matters — it’s the slow thread that the fast ones must wait for.

  • Without the first sync: a fast thread could start reading tile_A/tile_B in the k loop while a slower thread in the same block hasn’t finished writing its assigned entry yet — the fast thread reads stale (or uninitialized) shared-memory contents
  • Without the second sync: a fast thread could start overwriting tile_A/tile_B with the next tile’s data while a slower thread is still reading the current tile’s data during its k loop — the slow thread’s accumulation silently corrupts
  • Both bugs produce a wrong numeric answer with no crash and no error message — exactly the kind of silent failure Oct 5’s debugging session warned about
  • Understanding why both barriers are individually necessary — not just “more syncing is safer” — is the single most important idea in this module

~4 min. This is the module’s centerpiece slide. Consider asking students to predict, before you reveal it, what would go wrong with only one sync vs. the other — the two failure modes are different enough that guessing correctly requires actually understanding the loop, not just pattern-matching “GPU code needs syncthreads somewhere.”

TILE Size and Performance

TILE Shared memory per block Occupancy risk Expected outcome
8 2×8×8×4 B = 512 B Low Modest speedup — small tiles mean less reuse per global load
16 2×16×16×4 B = 2 KB Low Good speedup — a common default, balances reuse against overhead
32 2×32×32×4 B = 8 KB Higher Best reuse in principle, but larger per-block shared-memory and thread-count footprint can reduce how many blocks fit per SM at once
  • Larger tiles mean each global-memory load is reused more times before being discarded — more reuse should mean more speedup
  • But shared memory per SM is a fixed, limited budget (roughly 48-128 KB depending on the GPU) — a larger tile claims a bigger share of that budget per resident block, which can lower occupancy (Sep 30) and partially offset the reuse gain
  • The relationship between tile size and actual measured speedup is not always monotone — Lab 9 Exercise 3 has you sweep TILE ∈ {8, 16, 32} and find this out empirically, rather than trusting the “bigger tile = always faster” intuition

~3 min. Resist stating a winner in advance — the whole pedagogical point of Lab 9 Exercise 3 is that students discover the non-monotone relationship themselves by measuring it, the same “measure, don’t assume” lesson from Oct 5’s launch-configuration slide.

@cuda.jit
def sim_tiled(Q, D, sim):
