Why Access Pattern Matters

  • The GPU doesn’t fetch global memory one float at a time. It fetches in fixed-size chunks called transactions; one 128-byte cache line holds 32 float32 values
  • It serves a whole warp’s 32 requests together, using as few transactions as it can
  • 32 threads asking for 32 consecutive addresses: one transaction can serve them all. This is coalesced access
  • 32 threads asking for addresses scattered far apart: one transaction per address, up to 32 for the same 32 floats

Same 32 floats, same useful work. The only difference is which thread reads which address, and every memory decision for the rest of the course traces back to this picture.

~4 min across both sub-slides. Worth pausing on: this isn’t about how much data a kernel reads — it’s purely about the pattern of addresses across threads in the same warp. Two kernels reading the identical set of useful bytes can differ by up to 32× in transaction count depending only on which thread reads which address.

Coalesced Access

@cuda.jit
def coalesced_kernel(arr, out, n):
    i = cuda.grid(1)
    if i < n:
        out[i] = arr[i] * 2.0 + 1.0       # thread i reads element i
  • Thread 0 reads element 0, thread 1 reads element 1, … thread 31 reads element 31: consecutive threads, consecutive addresses
  • The whole warp is served by one 128-byte transaction
  • Every element-wise kernel since Lab 4 (out[i] = a[i] + b[i]) already has this property: you’ve been writing coalesced kernels all along

~2 min. Reassuring framing: this isn’t a new skill to learn from scratch, it’s a name for something students have already been doing correctly since Lab 4. What’s new is recognizing when a kernel accidentally breaks this pattern (next slide). The kernel matches Lab 08 Part 2 exactly, so students recognize it on Friday.

Strided Access

@cuda.jit
def strided_kernel(arr, out, n, stride):
    i = cuda.grid(1)
    if i < n:
        out[i] = arr[(i * stride) % n] * 2.0 + 1.0   # thread i reads element i*stride
  • With stride = 128: thread 0 reads element 0, thread 1 element 128, thread 2 element 256, … Neighbours are 512 bytes apart, and one warp’s reads spread over about 16 KB
  • The % n wraps around, so every thread still does one read: the same work as the coalesced kernel, only the pattern differs
  • Each read lands in its own cache line: up to 32 transactions instead of 1, and most of every fetched line is wasted
  • The measured slowdown is smaller than 32× (Lab 8 typically sees 4–8×). Lab 8 has you sweep the stride and explain the curve

~3 min. Lab 08 Part 2 times exactly these two kernels at N = 2^26; Exercise 1 sweeps stride ∈ {1, …, 128} and Exercise 2 asks students to interpret the curve (why stride 32 ≈ stride 128; what fraction of fetched bytes is used). Don’t pre-answer those questions here. The “less than 32×” point is honest: caches and the memory system’s own parallelism absorb part of the extra traffic.

2D Access Patterns

Two facts decide whether a 2D kernel is coalesced:

  1. Within a block, threadIdx.x varies fastest. A warp is (mostly) threads with consecutive x and the same y
  2. NumPy arrays are row-major: mat[r, c] sits at offset r * n_cols + c, so mat[r, c] and mat[r, c+1] are neighbours, while mat[r+1, c] is n_cols elements away

So a warp is coalesced when x walks along the last index (the columns).

~2 min. Write the row-major offset formula on the board — it’s the concrete arithmetic reason one direction is coalesced and the other isn’t, rather than something to take on faith.

The convention every 2D kernel has used so far:

@cuda.jit
def scale_rows_fast(mat, out, rows, cols):
    row, col = cuda.grid(2)              # cuda.grid(2) returns (x, y): x → row
    if row < rows and col < cols:
        out[row, col] = mat[row, col] * 2.0
  • cuda.grid(2) returns (x, y), so this puts the fast-varying x on row
  • Neighbouring threads in a warp have consecutive row and the same col: their addresses are n_cols elements apart. For a 1,000-column matrix that’s 4,000 bytes. This kernel is strided, not coalesced
  • The fix is to make x walk the columns instead. In Lab 8 Exercise 3 you write that kernel, time both, and check the outputs match

What about a transpose? out[c, r] = mat[r, c] reads along one direction and writes along the other.

  • Whichever way you map x, one side is coalesced and the other is strided: no choice of indices fixes both
  • The real fix is to stage a tile in shared memory: read it coalesced, then write it out coalesced. That is exactly the tool the rest of this module builds

~1 min. Students met transpose in Lab 05. This is a forward pointer only — we don’t build the shared-memory transpose in this course, but it’s the cleanest one-line motivation for why shared memory exists beyond matmul.

Why This Sets Up Shared Memory

  • Coalescing makes each global-memory read as cheap as possible, but it doesn’t reduce how many reads happen
  • Lab 5’s naive matmul has a different problem: the same element is read by many threads, once per output element that needs it
  • Shared memory (Oct 26) lets a block load each element from global memory once, then have every thread in the block reuse that one load
  • The two are complementary: coalescing makes each read cheaper, shared memory makes there be fewer reads. A well-tuned kernel uses both

~2 min. Bridge slide into the rest of the deck — makes explicit that “access pattern” (this session) and “reuse via shared memory” (rest of module) are two different levers on the same underlying memory-wall problem, not two separate topics.

Why Coalescing Alone Isn’t Enough

Colab’s T4, from Oct 7:

  • Global memory delivers 320 GB/s. At 4 bytes per float32, that’s about 80 billion floats per second
  • The ALUs can do 8,100 GFLOP/s: about 100 FLOPs for every float memory can deliver
  • Arithmetic intensity (FLOPs per byte moved, Oct 7) decides which limit you hit. Below the T4’s ridge point of 25.3 FLOP/byte, memory runs out first
  • Coalescing makes each transaction as cheap as possible, but does nothing to the number of bytes a kernel needs. That’s the gap shared memory closes

~3 min. Explicit framing: coalescing (last session) and shared-memory reuse (this session) are two different levers on the same memory-wall problem — one makes each access cheaper, the other reduces the number of accesses needed at all. Numbers deliberately match module03’s ridge-point slide.

The Roofline

Oct 7’s ridge point, drawn as a picture: a kernel’s ceiling is whichever roof is lower at its intensity.

~2 min. This is the roofline that module03 promised (“formalized as the roofline in Module 4”). Point at the corner: it’s exactly the ridge point students computed on Oct 7.

  • Naive matmul does 2 FLOPs (multiply, add) per 2 float32 reads (8 bytes): 0.25 FLOP/byte, a ceiling of 80 GFLOP/s if every read came from DRAM
  • Tiled matmul (Oct 28) does the same arithmetic, but each value loaded from global memory is reused by 16 threads (TILE = 16): 4 FLOP/byte, a ceiling 16× higher
  • Both still sit left of the ridge: tiling doesn’t make matmul compute-bound on a T4, it raises the memory ceiling
  • Real kernels beat these DRAM-only ceilings a little, because L1/L2 caches catch some reuse (Lab 6 Ex 2’s “impossible” bandwidth). Shared memory makes that reuse deliberate

~3 min. Students confirm the direction of this in Lab 9 — naive vs. tiled timings. Don’t promise 16× in measured time: caches already give naive matmul some reuse (module03 / Lab 06 notes), so the measured tiled-vs-naive speedup is much smaller (the lab key measured ~3× at 512³ on an RTX 4000 Ada). We don’t derive the model formally; the picture and the two intensity numbers are what matter.

Declaring Shared Memory

@cuda.jit
def offset_from_first(arr, out):
    # One shared slot per thread: launch with 256 threads per block
    s = cuda.shared.array(shape=256, dtype=numba.float32)

    i  = cuda.grid(1)
    ti = cuda.threadIdx.x           # local index within the block

    if i < arr.shape[0]:
        s[ti] = arr[i]              # load: global → shared
    cuda.syncthreads()              # every thread in the block waits here

    if i < arr.shape[0]:
        out[i] = s[ti] - s[0]       # s[0] was written by thread 0, not by me
  • Line 4: cuda.shared.array declares the block’s shared scratchpad, with a shape fixed at compile time
  • Line 10: each thread copies one value from global memory into its own slot
  • Line 11: cuda.syncthreads() is the barrier: no thread continues until all 256 have reached it. It sits outside the if so every thread reaches it
  • Line 14: each thread reads another thread’s slot (s[0]), which is only safe because of line 11

The new kernel reads a slot written by a different thread, which is what makes the barrier necessary. Verified in the CUDA simulator.

d_arr = cuda.to_device(np.arange(600, dtype=np.float32))   # [0, 1, ..., 599]
d_out = cuda.device_array(600, dtype=np.float32)
offset_from_first[3, 256](d_arr, d_out)
out = d_out.copy_to_host()
print(out[254:258])     # across the block 0 → block 1 boundary
print(out[-2:])         # the last two elements, in block 2
[254. 255.   0.   1.]
[86. 87.]
  • Each block has its own copy of s: block 1’s s[0] is arr[256], so the count starts over at 0
  • The last block is only partly full (indices 512–599). Its s[0] is arr[512], so arr[599] → 87

~2 min. Ask students to predict the two printed lines before revealing them. The “starts over” is the clearest possible demonstration that shared memory is per-block.

Rules of Shared Memory

  1. Shared scope: visible to every thread in the same block, and not to threads in other blocks, even ones running on the same SM
  2. Size fixed at compile time: shape= must be a literal or a constant (a module-level constant, or a variable captured from an enclosing function, as Lab 9’s make_tiled_matmul(TILE) does), never a value computed at runtime
  3. Lifetime: exists only while the block runs — allocated when the block starts, gone when it finishes
  4. Synchronization required: after writing shared memory, call cuda.syncthreads() before any thread reads another thread’s value

~3 min. The most common bug this session sets up for Lab 9: forgetting syncthreads() after writing to shared memory, so one thread reads a value before another thread has finished writing it — a race condition producing a silent wrong answer, no crash. Foreshadow this explicitly; Oct 28’s tiled kernel has two separate places this can go wrong.

cuda.syncthreads() — The Barrier

The barrier is a rendezvous, not a delay: the fastest thread waits for the slowest.

~2 min. Map this onto offset_from_first: thread 5 is any thread reading s[0]; thread 0 is the one writing it.

  • Without it, a thread gets whatever happens to be in shared memory when it reads: sometimes right, sometimes stale, no error either way
  • The trap: calling syncthreads() inside an if that not every thread in the block takes is undefined behaviour. The program may hang (threads wait for others that never arrive) or silently compute garbage
  • That’s why offset_from_first puts the barrier between its two if blocks, not inside one

~2 min. The divergent-barrier case is worth a clear mention: it’s a real failure mode in general CUDA code and a satisfying “why does my program just hang” answer. Older slides said it always deadlocks; on current GPUs it’s undefined — it may hang or may appear to work and corrupt results.

A Worked Example: Block-Level Maximum

@cuda.jit
def block_max_kernel(arr, out):
    s  = cuda.shared.array(shape=256, dtype=numba.float32)
    i  = cuda.grid(1)
    ti = cuda.threadIdx.x

    if i < arr.shape[0]:
        s[ti] = arr[i]
    else:
        s[ti] = numba.float32(-1e38)   # smaller than any real input
    cuda.syncthreads()

    stride = 128                       # half the block
    while stride > 0:
        if ti < stride:
            if s[ti + stride] > s[ti]:
                s[ti] = s[ti + stride]
        cuda.syncthreads()
        stride //= 2

    if ti == 0:
        out[cuda.blockIdx.x] = s[0]

~2 min for the code, ~3 min across the next two sub-slides. History: this slide used to be titled “Lab 08: Block Statistics”; Lab 8 is Memory Coalescing (no shared memory), so it’s kept purely as a worked illustration of the shared-memory + syncthreads pattern. The graded version of this stride-halving reduction is Module 5 (Nov 2, Lab 10 / CK-10); the graded double-syncthreads pattern is Lab 9’s tiled matmul.

  • Lines 7–11: every thread loads one value; threads past the end load -1e38, which can never win a max. Then a barrier
  • Lines 13–19: each round, the first half of the remaining threads keeps the larger of its value and the one stride away: 256 candidates → 128 → 64 → … → 1. That’s 8 rounds
  • Line 18: a barrier every round, because the next round reads values other threads just wrote
  • Line 18 again: this barrier is safe: the if ti < stride has closed before it, so all 256 threads reach it every round
  • Lines 21–22: after the last round, s[0] holds the block’s maximum; one thread writes it out

~2 min. The “line 18 is outside the if” point ties back directly to the divergent-barrier trap on the previous slide — worth asking the class “is this barrier legal?” before revealing that bullet.

1,000 values in descending order, 4 blocks × 256 threads:

d_out = cuda.device_array(4, dtype=np.float32)
block_max_kernel[4, 256](d_arr, d_out)
print(d_out.copy_to_host())
[999. 743. 487. 231.]
  • Each block’s max is its first element here, so a kernel that just kept the last one would fail
  • Block 3 holds only 232 real values (indices 768–999); the -1e38 padding never wins

Shared Memory Banks

  • Shared memory is split into 32 banks (one per warp lane). Consecutive 4-byte words go to consecutive banks, wrapping around: word k lives in bank k % 32
  • Each bank serves one request per cycle, but different banks work simultaneously
  • When a warp’s 32 threads hit 32 different banks, every read happens at once. Straightforward consecutive access gets this by default

~3 min. This is the shared-memory analogue of coalescing (Oct 21) — same underlying idea (parallel hardware wants parallel, non-overlapping requests), one level closer to the compute units.

Bank Conflicts

Drawn with 8 banks for readability; real hardware has 32.

  • A bank conflict: two or more threads in a warp ask for different addresses in the same bank. The hardware serializes them, one per cycle
  • Worst case: all 32 threads in one bank, 32-way conflict, about 32× slower for that access
  • Exception: if they all ask for the same address, it’s a broadcast: one cycle, no conflict
  • The usual cause: walking down a column of a 2D shared array whose row length is a multiple of 32. Every element of a column is then in the same bank

~3 min. Conceptual/awareness-level content — this course doesn’t checkpoint or quiz bank conflicts directly (schedule.md commits to teaching it here, but no lab exercise currently isolates it). Still worth teaching properly: it explains “why is my shared-memory kernel not as fast as I expected” once students start experimenting beyond the assigned labs.

Avoiding Bank Conflicts: Padding

TILE = 32

# Conflict-prone: each row is exactly 32 words, so column c is all in bank c
tile = cuda.shared.array((TILE, TILE), numba.float32)

# Padded: 33 words per row, so each row starts one bank later
tile_padded = cuda.shared.array((TILE, TILE + 1), numba.float32)
  • Allocate one extra column you never use. Each row then starts one bank later, so a column’s 32 elements land in 32 different banks
  • The padding is pure overhead: a few bytes traded for unserialized access
  • Oct 28’s tiled kernel doesn’t need it: a warp reads tile_A[ty, k] (one address, broadcast) and tile_B[k, tx] (consecutive, different banks)
  • Not required in labs or checkpoints. It’s in your toolkit for when a profiler points at bank conflicts

~2 min. The “today’s kernel doesn’t need it” bullet is true for TILE = 8, 16 and 32 with the x → col layout: within a warp, tile_A reads hit at most 4 distinct addresses in different banks (or broadcast), and tile_B reads are consecutive. Don’t go deeper than that.

The Naive Approach

@cuda.jit
def matmul_naive(A, B, C):
    row, col = cuda.grid(2)
    if row < C.shape[0] and col < C.shape[1]:
        acc = numba.float32(0.0)
        for k in range(A.shape[1]):    # inner dimension
            acc += A[row, k] * B[k, col]
        C[row, col] = acc
  • Thread (row, col) reads all of row row of A and all of column col of B
  • Row row of A is needed by every thread in that row of C: N_col threads, each fetching it separately. Column col of B: N_row times
  • Every element of A and B is fetched from global memory about N times, when once would do. That’s why it sits at 0.25 FLOP/byte on the roofline

~2 min. This is Lab 5’s kernel with the x → row layout, the same as Lab 9 Part 1 (kept on purpose as the baseline). Caches catch some of the repeat reads in practice (Lab 6), but nothing guarantees it.

At Lab 9’s 512×512 size, every element of A and B is fetched 512 times.

~2 min. Have students compute the 512 before revealing the caption. Note A[0,2] is needed by row 0 of C (every output in that row uses all of A’s row 0); B[2, j] is likewise needed by column j of C.

The Tiling Idea

  • Instead of each thread fetching from global memory on its own, the whole block loads each tile exactly once, into shared memory
  • Every thread then reads that tile as often as it needs. Shared-memory reads are fast and don’t touch global memory
  • Each element is fetched once per block that needs it, not once per thread: a TILE× cut in global traffic, which is the roofline’s 0.25 → 4 FLOP/byte at TILE = 16

~3 min across both sub-slides. This is the single most important idea in the module — the whole rest of this session is just implementing this four-step loop correctly in code. Make sure “the block loads once, every thread in it reuses that load” has fully landed before moving to code.

Tiled Kernel: Setup

TILE = 16

@cuda.jit
def matmul_tiled(A, B, C):
    # Shared memory tiles — size TILE×TILE each
    tile_A = cuda.shared.array((TILE, TILE), numba.float32)
    tile_B = cuda.shared.array((TILE, TILE), numba.float32)

    # x walks the columns (coalesced, Oct 21); y walks the rows
    tx, ty = cuda.threadIdx.x, cuda.threadIdx.y
    row = cuda.blockIdx.y * TILE + ty
    col = cuda.blockIdx.x * TILE + tx

    acc = numba.float32(0.0)
  • Line 1: TILE is a module-level constant, so Numba can fix the shared-array shape at compile time
  • Lines 6–7: the block’s shared scratchpad: one tile of A and one of B
  • Lines 10–12: x → column, as Oct 21 showed. row/col are the thread’s global output position; tx/ty its local position in the tile
  • Line 14: a float32 accumulator (a plain 0.0 would be float64, Lab 5’s trap)

~3 min. UPDATED 2026-10-21: the layout used to be x → row (blockIdx.x * TILE + threadIdx.x on row), which makes both global loads strided. Now matches Lab 09 Part 2, CK-09 and the lab key. The grid must match too: blocks = (ceil(N / TILE), ceil(M / TILE)) — x covers columns. Point out that this setup runs once per thread, before the tile loop.

Tiled Kernel: Loop Over Tiles

    n_tiles = (A.shape[1] + TILE - 1) // TILE

    for t in range(n_tiles):
        a_col = t * TILE + tx                    # this thread's column in A
        b_row = t * TILE + ty                    # this thread's row in B
        if row < A.shape[0] and a_col < A.shape[1]:
            tile_A[ty, tx] = A[row, a_col]       # load: global → shared
        else:
            tile_A[ty, tx] = 0.0                 # off the edge: pad with 0
        if b_row < B.shape[0] and col < B.shape[1]:
            tile_B[ty, tx] = B[b_row, col]
        else:
            tile_B[ty, tx] = 0.0

        cuda.syncthreads()                       # sync 1: tiles fully loaded

        for k in range(TILE):
            acc += tile_A[ty, k] * tile_B[k, tx]

        cuda.syncthreads()                       # sync 2: everyone done reading

    if row < C.shape[0] and col < C.shape[1]:
        C[row, col] = acc

~4 min across this and the next sub-slide. CK-09 (Friday) asks students to write the guarded loads and place the barriers on rectangular, non-multiple-of-TILE matrices — this slide is the walkthrough for that. Verified in the CUDA simulator on 40×30 @ 30×20.

  • Line 1: number of tiles along the shared dimension, rounded up so a partial last tile still counts
  • Lines 4–13: each thread loads one element of each tile. Consecutive tx read consecutive columns: coalesced
  • Lines 9, 13: anything off the edge becomes 0, so it adds nothing to the dot product. This is what makes sizes that aren’t multiples of TILE work
  • Lines 15, 20: the two barriers. The next slide shows why both are needed
  • Lines 17–18: the inner loop reads only shared memory: TILE multiply-adds per tile, no global reads
  • Lines 22–23: threads outside C still helped load tiles; they just don’t write

~2 min. The last bullet is the subtle one: out-of-range threads must not return early, because they still have to load their part of the tile and reach both barriers.

Why Two syncthreads()?

~2 min on the figure. Before revealing the next sub-slide, ask: what goes wrong with only sync 1? With only sync 2? The two failure modes are different enough that guessing correctly requires understanding the loop, not pattern-matching “GPU code needs syncthreads somewhere.”

  • Without sync 1: a fast thread starts the k loop while a slower thread hasn’t written its element yet: it reads a stale or uninitialized value
  • Without sync 2: a fast thread starts loading tile t + 1 while a slower thread is still reading tile t: the slow thread’s sum silently uses the wrong data
  • Both bugs give a wrong number with no crash and no error, and may only show up some runs (Oct 5’s debugging session)
  • Knowing why each barrier is there, not just “more syncing is safer”, is the key idea of this module

~3 min. This is the module’s centerpiece. The second bug is the one students rarely predict.

TILE Size and Performance

On a T4 (max 1,024 threads and 16 blocks per SM, 64 KB shared memory per SM):

TILE Threads / block Shared mem / block Blocks per SM Reuse per global load
8 64 2×8×8×4 B = 512 B 16 (block limit) 8×
16 256 2 KB 4 16×
32 1,024 8 KB 1 32×
  • All three fill the SM with 1,024 threads, and shared memory is nowhere near the 64 KB limit
  • What changes is reuse (bigger is better) and how many blocks the SM can switch between

~2 min. Same occupancy reasoning as module03’s “Why 16×16 Won Here”: on a T4 all three configs are at 100% theoretical occupancy. The old version of this slide said larger tiles lower occupancy via shared memory, which isn’t true at these sizes.

  • Bigger tiles: each global load is reused more times before it’s thrown away
  • But at TILE = 32, the SM has one block. When its warps all wait at a syncthreads(), the SM has nothing else to run. With 4 or 16 blocks, another block’s warps fill the gap
  • And at TILE = 8, reuse is low and there are more barriers per useful FLOP
  • So the fastest tile size is not always the biggest. Lab 9 Exercise 3 has you measure 8, 16 and 32 and explain what you see

~2 min. Resist stating a winner in advance — the point of Lab 9 Exercise 3 is that students discover the non-monotone relationship themselves by measuring it (the Lab 09 key wants “resident blocks per SM” in the answer, which these bullets set up without giving the ranking). The lab key measured 8 → 0.28 ms, 16 → 0.24 ms, 32 → 0.27 ms on an RTX 4000 Ada; T4 results vary.
