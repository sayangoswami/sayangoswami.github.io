Sketchy Math: Why Being Approximately Right takes approximately \(O(1)\)

HyperLogLog and the Count-Min Sketch

Counting the room without counting

A silly way to count people. But the same trick will count distinct visitors to a website.

~1.5 min. Each extra tail halves the chance: 1 tail is 1 in 2, 2 tails 1 in 4, 5 tails 1 in 32. The rarest outcome in the room tells you roughly how many people tried. Admit it’s silly: one lucky person decides everything. We’ll fix that later, and the fix is the same one you’d use here.

Two easy-sounding questions

  • How many different people visited Wikipedia today?
  • Which hashtags are trending right now?

Both are easy for a spreadsheet of 100 rows.

They are not easy for billions of events a day that never stop arriving.

~1 min. Ask the room how they’d answer each one. Most will say “keep a list”.

The obvious way: write everything down

~2 min. The usual next/previous keys step the animation; at its last step they move to the next slide. Point out the three numbers: memory grows with the distinct count. This same 7-IP stream comes back in every animation.

The deal we’ll make

We get to see each item once, as it flies past, and we may keep only a tiny notebook.

In exchange, we accept answers that are approximately right.

Exact table Sketch
Memory for 1 billion distinct IPs tens of GB 12 KB
Answer exact within ~1%

~1 min. “Sketch” = a tiny summary that answers one question approximately.

Our one tool: a hash function

  • Turns any item into a string of bits that looks random
  • The same item always gives the same bits

Think of it as a coin flip you can’t redo. In the room, if I counted you twice, you’d flip again and get a second chance to be lucky. A visitor seen twice gets the same bits.

~1 min. The 8-bit hashes here are toy values, picked by hand so the story is easy to follow. Real hashes are 64 bits.

Part 1: HyperLogLog

How many different items?

Hash bits are coin flips

Remember the room? Now every distinct item is a person flipping coins, and its leading zeros are its run of tails.

~1 min. Duplicates are free: they replay the same flips, so they can’t get lucky twice.

Version 0: remember one number

~2 min. This is exactly the room experiment: R is the longest run of tails. Memory is a single small number. Stop on 10.0.0.9: one lucky hash.

What went wrong?

  • One lucky item decides everything: 10.0.0.9 alone pushed us to 16
  • Only powers of 2: 1, 2, 4, 8, 16, … nothing in between

This is why counting the room was silly: one lucky person decided the answer.

Fix: run many small experiments and combine them, like asking each row of the room to run its own.

~0.5 min.

Split the hash into two jobs

Each bucket keeps its own longest run, in a small number called a register. Each bucket is one row of the room.

~1 min. With 2 bucket bits there are 4 buckets; real HLL uses 14 bits for 16,384 buckets.

HyperLogLog in action

~2 min. Emphasize: the lucky item is now contained in one register.

Each register is a mini estimate

Each register is “version 0” for its own bucket, so a longest run of M means about \(2^M\) items landed there.

~1 min. Same reasoning as the room, once per bucket. Adding the guesses gives 7: better than 16, but the one fluke still drags the total up. We need an average that the fluke can’t hijack.

A road-trip puzzle

You drive to town at 60 mph and come back at 20 mph.

What was your average speed?

Not 40. The slow leg takes three times as long, so it counts three times as much: the answer is 30 mph.

The trick: flip each speed into “hours per mile”, average those, then flip back. This is the harmonic mean. Small values win; one big value can’t take over.

~1 min. Let the room guess first; most say 40. 2 / (1/60 + 1/20) = 30.

An average that ignores flukes

1.06 is a fixed correction worked out mathematically: on average, steps 1–4 come out slightly too small with 4 registers. (With thousands of registers it’s 1.44.)

~1.5 min. Same flip-average-flip as the road trip. Here the corrected answer (5.2) is a bit further from 4 than step 4 (4.9): the correction is right on average, not in every example. For the curious, the full formula is E = 2 * alpha_m * m^2 / sum_j 2^(-M_j) with M_j = leading zeros: exactly these five steps. Textbook HLL stores zeros + 1 instead, which is why its constant alpha_m is half of ours. If asked: alpha is theoretical, not fitted. Flajolet et al. (2007) derive it from an integral that depends only on m: 0.532 for m=4, 0.673 for m=16, 0.709 for m=64, ~0.7213/(1+1.079/m) for large m (so 2 * alpha -> 1.44 = 1/ln 2). The empirical parts of HLL are elsewhere (switching to linear counting when registers are empty; HLL++’s bias tables). With only 4 registers and 4 items it’s rough; with thousands of registers it gets within 1%.

How good is it?

Error ≈ 1.04 / √m, where m = number of registers (6 bits each).

Registers m Memory Typical error
16 12 bytes 26%
256 192 bytes 6.5%
1,024 768 bytes 3.3%
16,384 12 KB 0.8%

And memory doesn’t grow with the stream: 12 KB for a thousand items or a trillion.

~1 min. 6 bits per register is enough because a run of zeros in a 64-bit hash can’t exceed 64.

Superpower: merging

~1 min. Each data center keeps its own sketch; combine them at the end. Works because max is the same no matter which server saw an item.

HyperLogLog in the wild

  • Redis: PFADD / PFCOUNT, 12 KB per counter
  • Google BigQuery, Snowflake: APPROX_COUNT_DISTINCT; Postgres via the hll extension
  • Reddit: post view counts
  • Network monitoring: how many distinct sources hit this server?

~0.5 min.

Part 2: Count-Min Sketch

How often does each item appear?

A different question

“How many times did 10.0.0.3 visit?” “How often did #worldcup appear?”

HyperLogLog can’t answer this. It never remembers which item caused what.

We need counters, but far fewer than one per item.

~0.5 min.

Attempt 1: one row of counters

~1.5 min. Key fact: a collision can only push a count up.

Fix: several rows, each with its own hash

~2 min. Insert: +1 in every row. Query: read every row, take the smallest.

Why take the minimum?

For the answer to be wrong, the item must collide in every row at once. With independent hashes, that’s unlikely.

~1 min. Like asking several witnesses who can only exaggerate: trust the most modest one.

How good is it?

With w columns and d rows, every answer is

  • never too small, and
  • too big by at most ε × (stream length), with probability 1 − δ

where w = e / ε and d = ln(1 / δ).

Example: 5 rows × 2,719 columns ≈ 54 KB.

Every count is within 0.1% of total traffic, 99% of the time, however many distinct items there are.

~1.5 min. Wider rows → smaller error. More rows → more confidence.

Count-Min in the wild

  • Trending topics: which hashtags are suddenly frequent?
  • Network security: which IPs are flooding us (DDoS)?
  • Caches: TinyLFU (Caffeine, Java) decides what’s worth keeping
  • Language models / NLP: approximate word and phrase counts

It also merges: add two grids cell by cell.

~0.5 min.

Takeaways

  1. You can’t remember everything, but you often don’t need to.
  2. A good hash turns data into fair coin flips.
  3. HyperLogLog: rare patterns reveal how many different items you’ve seen.
  4. Count-Min: overlapping counters, then trust the smallest.
