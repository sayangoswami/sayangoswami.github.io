Variables, Types, and type()

count = 42          # int
price = 3.14        # float
name = "Alice"      # str
ok = True           # bool
scores = [90, 85]   # list
ages = {"Al": 30}   # dict

print(type(price))  # <class 'float'>

= vs. ==, and Indentation Is Syntax

status = 200             # = assigns
if status == 200:        # == compares
    print("OK")          # indented: inside the if
    print("still OK")
print("always runs")     # not indented: outside the if

Output:

OK
still OK
always runs
  • = assigns; == compares. Writing if status = 200: is a syntax error in Python.
  • There are no braces. Indentation defines the block, and it’s required, not a style choice. Mixing up indentation changes what your program does, or stops it from running.
  • Every block-opening line (if, for, while, def) ends with a colon :.

Lists, len(), and range()

nums = [10, 20, 30, 40, 50]
len(nums)         # 5
nums.append(60)   # add to the end
nums[1]           # 20

for n in nums:    # loop over the items directly — no index needed
    print(n)      # 10, 20, 30, 40, 50, 60 (one per line)

for i in range(3):   # 0, 1, 2   (starts at 0, stops BEFORE 3)
    print(i)
  • len(x) works on lists, strings, dicts: anything with a size.
  • range(n) gives 0, 1, ..., n-1 — it stops before n. range(2, 5) gives 2, 3, 4.

Dictionaries

person = {"name": "Alice", "age": 30}   # curly braces, key: value
person["name"]          # 'Alice'
person["email"] = "a@x.com"             # add a key

counts = {}
for word in ["a", "b", "a"]:
    counts[word] = counts.get(word, 0) + 1
# counts == {'a': 2, 'b': 1}

for key, value in person.items():
    print(key, value)   # name Alice / age 30 / email a@x.com
  • Python’s HashMap: keys map to values. .get(key, default) avoids a crash (KeyError) on a missing key.
  • A dict looks exactly like a JSON object — that’s why REST APIs (Module 2), MongoDB documents (Module 5) and Flask’s jsonify (Module 6) all feel natural in Python.

List Comprehensions, lambda, and sorted

nums = [1, 2, 3, 4, 5]
squares = [n * n for n in nums]              # [1, 4, 9, 16, 25]
evens   = [n for n in nums if n % 2 == 0]    # [2, 4]

A list comprehension builds a new list in one line: [expression for item in list if condition].

It’s shorthand for a loop you already know how to write:

evens = []
for n in nums:
    if n % 2 == 0:
        evens.append(n)

Timing: 5 min across this slide and the next. Write the comprehension as the equivalent for loop first (the second block), then collapse it. Lab 6 Exercise 1 and Exercise 3 both use these directly.

pairs = [("bob", 70), ("alice", 85), ("carol", 92)]
sorted(pairs, key=lambda p: p[1], reverse=True)
# [('carol', 92), ('alice', 85), ('bob', 70)]
  • A lambda is a tiny unnamed function. lambda p: p[1] means “given p, return p[1].”
  • sorted(..., key=...) sorts by whatever the key function returns — here, the score. reverse=True puts the biggest first.
  • You’ll see both in Lab 6 and all over Python code. In PySpark, though, you’ll use Spark’s own filter/select instead of comprehensions (Session 2 shows why).

Reading a File

f = open("ratings.csv", "r")     # "r" = read mode
for line in f:
    print(line.strip())
f.close()

# The idiomatic version: the file closes itself when the block ends
with open("ratings.csv", "r") as f:
    header = f.readline()            # skip the header row
    for line in f:
        user, movie, rating, ts = line.strip().split(",")
  • open(path, "r") to read, "w" to write (overwrites the file).
  • with open(...) as f: is preferred: no forgotten close().
  • The unpacking needs one name per field: ratings.csv has four columns (userId,movieId,rating,timestamp), so three names would crash with a ValueError.

Recap: From Hadoop to Spark

Module 3 ended with MapReduce’s biggest weakness: every job writes its intermediate results to disk, even between steps of the same pipeline. For a job that only runs once, that’s fine. For anything iterative — trying 100 variations of a machine-learning model, or chaining ten transformations together — writing to disk every single step is slow.

Apache Spark was built to fix exactly this.

Timing: 3 min. Just re-anchor: MapReduce’s map→shuffle→reduce→disk cycle from Module 3 is the thing Spark is reacting against. Don’t re-teach MapReduce, just point at the pain point.

What Is Apache Spark?

Apache Spark is a distributed data-processing engine — the successor to Hadoop MapReduce for most large-scale data work today.

  • Key idea: keep intermediate data in memory across steps of a pipeline, instead of writing every step to disk the way MapReduce does.
  • Result: 10–100× faster for workloads that reuse the same data across multiple steps (iterative algorithms, interactive queries, multi-stage pipelines).
  • Written in Scala, but has full APIs in Python (PySpark — what we use), Java, R, and SQL.

One engine, several tools. Beyond the batch DataFrame work this course focuses on, Spark also has:

  • Spark SQL: write actual SQL queries against a DataFrame.
  • Structured Streaming: process data as it arrives, not just in batches.
  • MLlib: distributed machine learning.

All part of the same engine, not separate tools. We only use the batch/DataFrame piece this semester.

Not tied to HDFS. In our classroom cluster, Spark jobs happen to read from HDFS and get scheduled by YARN, both from Module 3 — but that’s a choice about our setup, not a requirement of Spark itself. Spark can just as easily read from S3, local files, a database, or a Kafka stream; it isn’t tied to HDFS the way MapReduce, in practice, always was.

Timing: 4 min. Emphasize continuity, not replacement: HDFS and YARN don’t go away in our setup. Spark is a new way to compute, sitting on the same storage and scheduling layer already taught — but say explicitly that this is our classroom’s configuration, not a general Spark requirement (Final Q17 tests this distinction directly: Spark is not tied to HDFS). The SQL/ streaming/MLlib bullet is Quiz 5 Q9’s multi-select — keep it to one sentence each, this course never touches any of the three.

Why Spark Improves on MapReduce

Picture a pipeline with three steps: filter, then group, then sort.

  • MapReduce: step 1 writes its full output to disk. Step 2 reads it back from disk, computes, writes its output to disk. Step 3 does the same. A disk round-trip between every pair of steps.
  • Spark: step 1’s output stays in memory. Step 2 reads it from memory, computes, keeps its result in memory. Step 3 does the same. Disk is only touched to read the input, save the result, or when data is too big to fit in memory.

Timing: 4 min (this slide and its two sub-slides). This is Quiz 5’s Q1 almost verbatim — spend real time here. The wrong-but-tempting answer is “Spark just has better algorithms”; the right answer is specifically about avoiding repeated disk I/O across steps.

Important

This matters most for iterative workloads — anything that reuses the same data repeatedly, like training a machine-learning model over many passes. A single MapReduce-style batch job that runs once and finishes isn’t dramatically slower in MapReduce; it’s repeated work over the same data where Spark’s in-memory model wins big.

RDDs vs. DataFrames

Spark actually has two ways to represent distributed data. You need to know both exist, even though we will work almost entirely with the second one.

RDD (Resilient Distributed Dataset) DataFrame
What it is A low-level, distributed collection of arbitrary Python objects A distributed table — named columns, with a schema
Structure None enforced — Spark doesn’t know what’s inside Spark knows every column’s name and type
Optimization None — you write exactly what runs Spark’s optimizer can rewrite your query to run faster
Feels like A distributed Python list A distributed spreadsheet
  • RDDs came first (Spark’s original data structure) and are still there underneath everything.
  • DataFrames were added later, and are what virtually everyone uses for tabular data today — including everything in this course, the labs, and the capstone.

Timing: 5 min (this slide and the next). This slide exists specifically because Quiz 5’s Q2 asks students to distinguish RDD from DataFrame directly — don’t let this be a one-line footnote. The callout’s answer is on the next sub-slide, after a pause.

Think about it

If Spark doesn’t know what’s inside an RDD, what can’t it do that it can do with a DataFrame? (Hint: think about what “optimizing a query” requires knowing about the data first.)

Answer: without column names and types, Spark can’t optimize. It can’t reorder operations, push a filter down to happen earlier, skip columns you never use, or pick an efficient join strategy. With an RDD it just runs your code exactly as written.

Spark Architecture

Timing: 4 min (this slide and the next). The payoff line: “you already learned what YARN does in Module 3 — Spark just hands YARN a different kind of job to schedule.” Don’t re-explain YARN from scratch. The figure deliberately reuses Module 3’s YARN figure layout (same violet ResourceManager, same NodeManager worker boxes).

  • Driver: coordinates the whole computation — your code runs here, and it decides what work to hand out. Plays the same role Module 3’s ApplicationMaster played for a MapReduce job: one coordinator, dispatched for this one application.
  • Executor: a worker process that actually runs tasks and holds a slice of the data in memory — the same role Module 3’s NodeManager-run tasks played, just for Spark tasks instead of Map/Reduce tasks.
  • Cluster manager: allocates machines/resources to your job — in our classroom cluster, that’s YARN, the exact same resource manager Module 3 used for MapReduce jobs. Spark doesn’t bring its own scheduler here; it asks YARN for workers, the same way a MapReduce job did.

DataFrames Are Immutable

Every PySpark DataFrame, once created, never changes. Every operation returns a brand-new DataFrame — the original is always left untouched.

filtered = df.filter(df["salary"] > 70000)

# df itself is completely unchanged here — still has all rows
# filtered is a NEW DataFrame with only the matching rows

Important

This trips up almost everyone coming from pandas or spreadsheets, where you’re used to modifying data in place. In PySpark, if you don’t assign the result of an operation to a variable, the result is thrown away and nothing changes. df.filter(...) on its own line, with no =, does nothing useful.

Timing: 3 min. Quiz 5’s Q6 asks this directly (true/false, “does filter() modify df in place?”). Say the rule out loud, plainly, more than once — it’s one of the most-missed ideas in this whole module.

Lazy Evaluation — The Core Idea

# These lines define a PLAN — nothing runs yet
filtered   = df.filter(df["salary"] > 70000)
selected   = filtered.select("name", "salary")
sorted_df  = selected.orderBy("salary", ascending=False)

# THIS triggers computation — Spark executes the whole plan at once
sorted_df.show()

Output (on the two-row df from before):

+-----+------+
| name|salary|
+-----+------+
|Alice| 95000|
+-----+------+
  • Nothing above sorted_df.show() actually touches the data. Spark just records each step as part of a plan — this is called lazy evaluation.
  • That recorded plan has a name: a DAG (Directed Acyclic Graph) — a chain of steps that only ever flows forward, never loops back on itself. Each transformation you chain adds one more step to the DAG.
  • Only when you call an action (show(), count(), …) does Spark look at the entire DAG you built, optimize it, and run it all at once.
  • Why bother? Because seeing the whole plan first lets Spark skip unnecessary work — for example, here only name and salary are ever used, so Spark can drop the department column straight away instead of carrying it through every step.

Timing: 5 min (this slide and its two sub-slides). Quiz 5’s Q8 tests this definition directly. The “why bother” bullet is the part students usually skip — don’t let this be just “Spark waits to run things,” make sure they leave with why waiting is useful. The DAG bullet is here specifically because Lab 7 Task 2 asks “What is a DAG in Spark? When does Spark build it and when does it execute it?” as a graded question — without this bullet, that question would be untaught.

Pause & Discuss: What Actually Ran?

Breather — think on your own (2 min), then we discuss

df has 10 billion rows of employee data.

high = df.filter(df["salary"] > 70000)      # line 1
df.filter(df["department"] == "Marketing")  # line 2
print(high.count())                         # line 3

Lines 1 and 2 return instantly. Why?

What does line 3 print: the number of high earners overall, or high earners in Marketing?

How many times does Spark actually go through the 10 billion rows?

Timing: 4 min (≈2 min silent thinking, ≈2 min discussion). Answers are on the next sub-slide so students reviewing later have them; reveal after the discussion.

This combines the two previous slides (immutable + lazy) and leads straight into the next one: count() is an action, filter() is a transformation.

Answers

  • Lines 1–2 are instant because transformations are lazy. They only add a step to the plan (the DAG), and no data is touched.
  • Line 3 counts high earners in all departments. Line 2 built a new DataFrame that was never assigned, so it was thrown away (immutability). high never knew about it.
  • One pass, at line 3, the only action. Line 2’s plan never runs at all, because nothing ever asked for its result.

Transformations vs. Actions

Transformations (lazy — build the plan) Actions (trigger execution)
filter() show()
select() count()
groupBy() collect()
orderBy() write.csv()
withColumn() first()
join() take(n)

Tip

If a line of PySpark code returns a DataFrame, it’s a transformation. If it returns data or writes a file, it’s an action.

(One wrinkle: groupBy() returns a GroupedData object, not a DataFrame. It’s still lazy, and the .agg() or .count() after it turns it back into a DataFrame.)

Recap: Transformations, Actions, Laziness

Three ideas from Monday, quickly:

  • Transformations (filter, select, …) build a plan but don’t run anything.
  • Actions (show, count, …) trigger Spark to actually execute that plan.
  • DataFrames are immutable — every transformation returns a new DataFrame; you must assign the result or it’s discarded.

Today: turning real files into DataFrames, and the two most common transformations you’ll use on almost every dataset — filtering rows and selecting columns.

Timing: 3 min. Fast recap only — the point is to have the vocabulary ready, not re-teach it.

Loading Data into Spark

# CSV with a header row
df = spark.read.csv("path/to/file.csv", header=True, inferSchema=True)

# TSV (tab-separated) with no header
df = spark.read.csv("path/to/file.tsv", sep="\t", header=False, inferSchema=True)

# JSON
df = spark.read.json("path/to/file.json")

# From HDFS — always your own username, never a shared placeholder
df = spark.read.csv("hdfs:///user/<your-username>/data.csv", header=True, inferSchema=True)
  • header=True tells Spark the first row is column names, not data.
  • inferSchema=True tells Spark to scan the file and guess each column’s type (integer, string, double, …) rather than treating every value as text.
  • Reading hdfs://... paths works exactly the same as reading a local path — Spark doesn’t care where the file lives, as long as it can reach it.

Timing: 4 min. Quiz 5 Q4 tests this exact syntax verbatim (spark.read.csv(..., header=True, inferSchema=True)) — make sure students see and can reproduce it, not just recognize it.

A Word on Schemas

  • Without inferSchema=True, Spark treats every column as a string — even columns that are clearly numbers.
  • That fails silently: orderBy("salary") sorts as text, so "100000" comes before "62000" (it starts with 1), and max("salary") returns the alphabetically last value. Comparing to a number, as in df["salary"] > 70000, happens to work only because Spark quietly converts the text for you.
  • inferSchema=True costs a little extra time (Spark has to scan the file first), but for anything you’ll sort, filter or aggregate numerically, it’s worth it.
  • df.printSchema() is your first move on any new dataset — confirm the types are what you expect before writing a single transformation.

Timing: 3 min (this slide and the next). Verified on Spark: a string salary column with "95000", "62000", "100000" sorts as 100000, 62000, 95000 and max returns 95000, while > 70000 correctly keeps 95000 and 100000. The callout’s answer is on the next sub-slide.

Think about it

You load a CSV and printSchema() shows a price column typed as string, not double. What’s the most likely cause — and what’s the first thing you’d check in the raw file?

Answer: either inferSchema was left off, or the column has some non-numeric values mixed in (e.g. "N/A" or "$12.50"), which forces Spark to fall back to string for the whole column. Check the raw file for those values.

Filtering Rows

from pyspark.sql.functions import col

# Filter rows — both forms below are equivalent
high_earners = df.filter(df["salary"] > 70000)
high_earners = df.filter(col("salary") > 70000)

# You can also pass a filter as a plain SQL-style string
high_earners = df.filter("salary > 70000")

# .where() is just another name for the same thing
high_earners = df.where(df["salary"] > 70000)
  • df["salary"] and col("salary") are two ways of referring to the same column — use whichever reads more clearly in context.
  • filter() and where() are exact synonyms — pick one and be consistent.
  • Remember: this returns a new DataFrame. high_earners is new; df still has every row.

Timing: 4 min. Quiz 6 Q10 lists several of these forms as “select all that apply” — students need to recognize all of them as valid, not just the one they memorize.

Selecting and Renaming Columns

# Select specific columns
result = df.select("name", "department", "salary")

# Add a new computed column
df = df.withColumn("salary_k", col("salary") / 1000)

# Rename a column
df = df.withColumnRenamed("salary", "annual_salary")
  • select() keeps only the columns you name, in the order you name them, dropping the rest.
  • withColumn(name, expression) adds a new computed column — or overwrites an existing column if you reuse its name.
  • withColumnRenamed(old, new) changes a column’s name without touching its values.

Timing: 4 min. Quiz 5 Q7 tests select() directly. Point out the parallel with the earlier filter-forms slide: these are all just “transformation in, new DataFrame out,” same pattern every time.

Adding a Computed Column

from pyspark.sql.functions import col

# Wrong — this is pandas syntax, and it doesn't work in Spark
df["new_col"] = df["col1"] * 2

# Right — Spark syntax
df = df.withColumn("new_col", col("col1") * 2)

The pandas-style line fails straight away with:

TypeError: 'DataFrame' object does not support item assignment

PySpark DataFrames are immutable, so there is nothing to assign into. withColumn (assigned back to df) is the only correct way to add or replace a column.

Timing: 3 min. This is worth its own slide (not folded into “common mistakes”) because it’s the single most common first bug students hit in Lab 7 — the error names the symptom (item assignment) but not the fix, so seeing the correct pattern before hitting the bug saves real debugging time. Tie it back to immutability.

Pause & Discuss: Find the Two Bugs

Breather — think on your own (2 min), then we discuss

Goal: names and salaries (in thousands) of everyone in Marketing.

from pyspark.sql.functions import col

df = spark.read.csv("hdfs:///user/alice/employees.csv", header=True, inferSchema=True)
df.withColumn("salary_k", col("salary") / 1000)
result = df.select("name", "salary_k")
result = result.filter(col("department") == "Marketing")
result.show()

This code fails. Find two separate bugs. Which line do you think Spark complains about first?

Timing: 4 min (≈2 min silent thinking, ≈2 min discussion). Answers are on the next sub-slide so students reviewing later have them; reveal after the discussion. Line numbers in the answers count from the df = spark.read... line, skipping the import. Verified on Spark: the select line raises AnalysisException: [UNRESOLVED_COLUMN.WITH_SUGGESTION] ... salary_k cannot be resolved.

Answers

  • Bug 1 (the withColumn line): its result is never assigned (immutability), so df has no salary_k column.
  • Bug 2 (the filter line): it filters on department after select has already dropped that column.
  • Spark complains first at the select line, with an AnalysisException saying it can’t resolve salary_k. Spark checks column names as you build the plan, even though it doesn’t touch any data until an action. Lazy execution doesn’t mean it skips checking names.

Fixed version:

df = df.withColumn("salary_k", col("salary") / 1000)
result = df.filter(col("department") == "Marketing").select("name", "salary_k")
result.show()

Avoiding Common PySpark Mistakes

Mistake 1: filtering in plain Python instead of in Spark

# ❌ Wrong — a list comprehension over collect()
result = [row for row in df.collect() if row["salary"] > 70000]

# ✅ Right — use Spark's own filter
result = df.filter(col("salary") > 70000)
  • The wrong version runs, but collect() pulls every row onto one machine (the driver) and filters them one at a time in plain Python — throwing away everything Spark is for. On big data it can crash the driver (more on collect() in Session 3).
  • Leaving out collect() doesn’t help: for row in df doesn’t loop over rows at all, and the comprehension fails with ValueError: Cannot convert column into bool.

Timing: 5 min (this slide and the next). Both mistakes are genuinely common — if time is short, prioritize the second one, since it’s the more frequent real bug in student code across every lab this module. Verified on Spark: [row for row in df if row["salary"] > 70000] raises CANNOT_CONVERT_COLUMN_INTO_BOOL, because iterating a DataFrame walks its columns by index.

Mistake 2: forgetting to assign the result

# ❌ Wrong — filter() doesn't modify df in place
df.filter(col("salary") > 70000)                 # result thrown away — df is unchanged

# ✅ Right — the result is captured
high_earners = df.filter(col("salary") > 70000)

This is the immutability rule from Session 1, showing up again in real code — if your DataFrame “isn’t changing,” check whether you forgot to assign the result.

Worked Example: Filter → Select

Given a DataFrame employees with columns name, department, salary:

# Goal: names and salaries of everyone in Marketing earning over $60,000

marketing_high_earners = employees \
    .filter(col("department") == "Marketing") \
    .filter(col("salary") > 60000) \
    .select("name", "salary")

marketing_high_earners.show()
  • Multiple .filter() calls chain naturally — each one narrows the DataFrame further.
  • Order between the two filters here doesn’t change the result, but select() must come after both filters — once you select() away a column, you can no longer filter on it.

GroupBy and Aggregation

from pyspark.sql.functions import avg, count, round as spark_round, desc

# Average salary and headcount by department
df.groupBy("department") \
  .agg(
      spark_round(avg("salary"), 2).alias("avg_salary"),
      count("name").alias("num_employees")
  ) \
  .orderBy(desc("avg_salary")) \
  .show()
  • groupBy("column") — a transformation; it doesn’t compute anything on its own, it just says *“gather rows into groups* by this column’s value.”
  • .agg(...) — applies one or more aggregation functions (avg, count, sum, …) to each group, producing one output row per group.
  • .alias("name") — renames the resulting column to something readable.

Aggregation Functions Reference

from pyspark.sql.functions import (
    avg, count, countDistinct,
    sum as spark_sum, min as spark_min, max as spark_max
)

df.groupBy("category").agg(
    count("*").alias("total_rows"),
    countDistinct("brand").alias("num_brands"),
    avg("price").alias("avg_price"),
    spark_sum("revenue").alias("total_revenue"),
    spark_min("price").alias("cheapest"),
    spark_max("price").alias("most_expensive")
)

Timing: 3 min (this slide and the table on the next). The import aliases are worth calling out explicitly. sum, min and max are also Python built-ins: importing Spark’s versions under the same names replaces the built-ins for the rest of the notebook, so a later plain sum([1, 2, 3]) breaks; not importing them means sum("revenue") calls Python’s built-in and fails. Aliasing avoids both. (round as spark_round on the previous slide is the same story.)

Function What it computes (per group)
count("*") Number of rows
count("col") Number of rows where col is not null
countDistinct("col") Number of unique values in col
avg() Mean of a numeric column
sum() Total of a numeric column
min() / max() Smallest / largest value

Why the aliases? sum, min and max are also Python built-ins. Importing Spark’s versions under the same names would replace the built-ins for the rest of your notebook, so as spark_sum (and friends) keeps both usable.

orderBy and the Top-N Pattern

# The "top N by some metric" pattern — you'll use this constantly
top_5 = df.groupBy("department") \
          .agg(spark_round(avg("salary"), 2).alias("avg_salary")) \
          .orderBy("avg_salary", ascending=False) \
          .limit(5)

top_5.show()
  • orderBy(column, ascending=False) sorts descending; ascending=True (or omitting it) sorts ascending.
  • .limit(n) keeps only the first n rows after sorting, as a new DataFrame — use it when you need the top N for something else (writing it out, joining it).
  • .show(n) just prints the first n rows of whatever it’s called on. It doesn’t sort; the orderBy before it does. Use it when you only want to look.

Tip

This pattern — groupBy → agg → orderBy → limit/show(n) — is the core of Lab 8’s “top 10 highest-rated movies” task. Checkpoint 5 uses the second half: sort descending, then show the top rows.

Actions, Revisited: The Risk of collect()

Session 1 introduced actions as “the things that trigger execution.” One of them deserves a warning of its own.

# ⚠️ Dangerous on a large DataFrame
all_rows = df.collect()   # pulls EVERY row to the driver machine, as a Python list

# ✅ Safer — limit first
sample = df.limit(100).collect()
  • collect() brings all matching rows back to the driver program, as a Python list of Row objects — not distributed anymore.
  • If the DataFrame is large, this can crash the driver — the driver has one machine’s worth of memory, not the whole cluster’s.
  • count() and show(n) don’t have this problem: count() returns a single number, and show(n) only ever brings back n rows.

Timing: 5 min. Quiz 6 Q7 tests this risk directly (“main risk of collect() on a very large DataFrame”) — this is a real, industry-relevant footgun, not a trivia fact, so it’s worth the full 5 minutes.

Pause & Discuss: Which One Crashes the Driver?

Breather — think on your own (2 min), then we discuss

ratings has 100 million rows but only about 50,000 distinct movies. Which of these are safe, and which could crash the driver?

ratings.count()                                          # (a)
ratings.groupBy("movieId").agg(avg("rating")).collect()  # (b)
ratings.collect()[:10]                                   # (c)
ratings.orderBy(desc("rating")).show(10)                 # (d)

Timing: 4 min (≈2 min silent thinking, ≈2 min discussion). Answers are on the next sub-slide so students reviewing later have them; reveal after the discussion.

Answers

  • (a) Safe. It returns a single number.
  • (b) Safe. It collects the result: one small row per movie, about 50,000 rows, not 100 million. What makes collect() risky is the size of what you collect, not the size of the input.
  • (c) Dangerous. collect() runs first and pulls all 100M rows onto the driver. The [:10] happens afterward in plain Python, which is too late. Fix: ratings.limit(10).collect() or ratings.take(10).
  • (d) Safe. Only 10 rows come back to the driver. The sort itself runs on the executors.

The rule to leave with: ask “how many rows will land on the driver?”, not “how big is the DataFrame?”

Every Action Re-Runs the Plan — Unless You Cache

Lazy evaluation has a consequence: Spark doesn’t remember results between actions. Each action re-runs the whole plan from the source data.

top = ratings.filter(col("rating") >= 4.0).groupBy("movieId").count()

top.count()   # runs the full plan: read → filter → groupBy
top.show(5)   # runs the full plan AGAIN from scratch

top.cache()   # keep `top` in executor memory once it's computed
top.count()   # computes it one more time, and stores it
top.show(5)   # reads the stored copy, no recomputation
  • cache() (or persist()) is neither a transformation nor an action. It marks the DataFrame to be kept in memory the next time an action computes it.
  • Use it when you’ll run several actions on the same intermediate result. This is the in-memory reuse that makes Spark faster than MapReduce (Session 1, and EL4’s Zaharia talk).

Timing: 2 min. Quiz 6 Q9’s last option (“calling multiple actions re-executes the computation each time, unless the DataFrame is cached”) hinges on this slide. EL4 covers persist() in more depth, but EL4 is due the same day as Quiz 6, so say it here too.

Writing DataFrame Output

# Write as CSV — creates a folder, not a single file
df.write.csv("output/path", header=True, mode="overwrite")

# Write as JSON
df.write.json("output/path", mode="overwrite")
  • df.write.csv(...) is an action — like show() or count(), it triggers Spark to execute the full pending plan, this time saving the result instead of printing it.
  • The output is a folder of part-... files, one per partition, because each executor writes its own slice in parallel.
  • mode="overwrite" replaces existing data at that path; mode="error" (the default) fails if the path already exists, to prevent accidentally destroying previous output.
  • The capstone’s spark_job.py uses this same write pattern — except writing to MongoDB instead of a CSV folder, which Module 5 covers.

Timing: 3 min. Quiz 6 Q8 and Q9 both test that write.csv() is an action, not a transformation — reinforce that classification explicitly, since “write” sounds like it should just be setup, not execution.

Joins in PySpark

# Inner join: only rows with matching keys in both DataFrames
result = ratings.join(movies, on="movieId")

# Left join: all rows from the left DataFrame, matched rows (or nulls) from the right
result = ratings.join(movies, on="movieId", how="left")

# Joining on differently-named columns
result = df1.join(df2, df1["user_id"] == df2["id"])
  • A join combines two DataFrames into one, matching rows where a key column agrees.
  • Inner join (the default): keep only rows that have a match in both DataFrames — rows with no match on either side are dropped.
  • Left join: keep every row from the left DataFrame; unmatched rows get null for the right DataFrame’s columns instead of being dropped.

Timing: 5 min (this slide and its two sub-slides). The worked example on the next sub-slide was run on Spark; the output tables are real. Lab 8’s Task 2 and Task 5 both join ratings with movies on movieId.

Think about it

ratings has a movieId for every rating. movies has a movieId and title for every film. If you inner-join them, could you ever end up with fewer rows than ratings had originally? What would that mean about the data?

Worked Example: A Full Multi-Step Query

from pyspark.sql.functions import col, avg, count, round as spark_round, desc

top_movies = ratings \
    .groupBy("movieId") \
    .agg(spark_round(avg("rating"), 2).alias("avg_rating"),
         count("rating").alias("num_ratings")) \
    .filter(col("num_ratings") >= 50) \
    .join(movies, on="movieId") \
    .select("title", "avg_rating", "num_ratings") \
    .orderBy(desc("avg_rating"))

top_movies.show(10, truncate=False)

Timing: 4 min (this slide and the next). This is deliberately close to Lab 8 Task 2’s actual solution shape — click through the line highlights one step at a time rather than all at once, since chaining six operations together is a lot to take in as a single block the first time. The written walkthrough is on the next sub-slide for students reviewing later.

Reading it top to bottom:

  1. Group ratings by film (groupBy("movieId")).
  2. Compute each film’s average and count (agg).
  3. Keep only films with ≥ 50 ratings, so a film with a single 5-star rating can’t top the list.
  4. Join in the title from movies.
  5. Keep just the columns we want (select).
  6. Sort by average rating, highest first (orderBy(desc(...))).
  7. Show the top 10, without cutting off long titles (truncate=False).

Concept Key idea
