Recap: Why One Machine Isn’t Enough

Week 1 already did this arithmetic once — the StreamBase manager’s ask was 80 billion events. Quick replay:

  • A laptop with 16 GB of RAM holds roughly 200 million integers in memory at once.
  • 80 billion rows is 400× that — you’d need on the order of 400 machines just to store it, before any processing starts.
  • Processing 80 billion rows sequentially, one machine, one core, at a generous 1 million rows/second, takes over 22 hours — for one pass over the data, one time.

That arithmetic is the entire justification for everything in this module: storage has to spread across machines (HDFS), and so does the processing (MapReduce).

Timing: 3 min. This is a recap, not a new derivation — if a student asks “wait, why 200 million integers,” that’s a Week 1 detail (4 bytes/int, 16 GB ÷ 4 bytes), not worth re-deriving here. Move on.

Batch Processing: Meal-Prep, Not À La Carte

Once data is big in one of these ways, there are two general strategies for processing it: handle each new piece of data the instant it arrives (streaming — out of scope this course), or collect a pile of it and process the whole pile at once (batch processing — this module and Module 4).

  • Kitchen picture: a meal-prep Sunday, where a kitchen cooks a whole week’s worth of a dish in one big batch, versus a restaurant cooking one dish fresh the instant each order comes in. Batch processing is the meal-prep Sunday: collect first, process the whole pile together.
  • Classic real example: process yesterday’s entire log file overnight, have results ready by morning — nobody needs the answer in the next 10 milliseconds, so batching the whole day’s data together is simpler and more efficient than reacting to each log line individually.
  • MapReduce (Google, 2004 — the paper from Week 1’s Google vignette) is the framework that made batch processing on thousands of machines practical and programmable. You’re about to invent a version of it yourself.

Timing: 3 min. Keep this brief — it exists to set up “batch” as the vocabulary word for what the activity is about to do, not to teach streaming as a topic (it isn’t covered this course).

Today: Become the Cluster

For the rest of this session, no more slides about big data — you’re going to become a small distributed system and solve a real batch-processing problem with your own bodies, before any formal vocabulary shows up.

  • You’ll work in clusters of 3 — each of you is a separate “machine,” sitting at a separate desk, not next to each other.
  • Each of you gets a slice of a dataset — nobody sees the whole thing.
  • Your cluster’s job: combine your three slices into one correct answer, in as little time as possible, with your teammates spending as little time standing around waiting as possible.

Timing: 3 min. Say explicitly: “I’m not going to tell you the algorithm. Figure one out, then we’ll name what you did.” The entire value of the activity depends on not front-loading the strategy.

Activity Setup

  • Desks for each cluster of 3 are spread apart — corners of the room, not adjacent. Leaving your desk to check in with a teammate costs a real walk, not a whisper.
  • Each cluster gets its own shuffled deck (or set of order strips) split three ways — one pile per student. Nobody’s pile is sorted; your slice is a random mix of everything.
  • The rule that makes this interesting: every trip you make to a teammate’s desk costs time, and whoever you leave behind is sitting idle until you’re back. A good cluster finishes fast and keeps everyone busy — not just one person doing all the walking while two people watch.

Meet Map, Shuffle, Reduce

MapReduce is a programming pattern for processing a big dataset by splitting it into pieces, processing each piece independently, then combining the results — exactly what your cluster did Monday, generalized to any number of “machines” and any counting problem, not just suits or menu items.

Input data (split across N machines/files)
         ↓
    Map    — each machine processes only its own piece, in parallel
         ↓
  Shuffle/Sort — the framework groups everyone's output by key
         ↓
   Reduce — one machine per key combines that key's values into a final answer
         ↓
      Output

Diagram to add later (Excalidraw / pyxcd / draw.io)

Reuse Monday’s kitchen-branch icon language. Three small “branch” icons on the left, each with its own input pile, feeding downward arrows into a “Map” band where each branch is shown tallying its own pile independently (no arrows between branches at this stage). Below that, a “Shuffle” band where arrows converge from all three branches toward per-key collection points (e.g., one arrow bundle labeled “♠” converging on one point, another labeled “♥” converging elsewhere) — these are the only diagonal/crossing arrows in the whole diagram, visually marking this as the one phase that costs movement. Below that, a “Reduce” band where each collection point emits one final summed value. Caption: “Same shape as Monday — just relabeled.”

The Map Phase: One Record In, Zero or More Pairs Out

A map function takes one input record and emits (key, value) pairs — nothing more.

map(record):
    ... extract whatever matters from this one record ...
    emit(key, value)

Two examples of the same pattern, different data:

Problem What map() emits
Count words in a line of text emit(word, 1) for every word in the line
Total sales per region, given region, productID, saleAmount records emit(region, saleAmount)

Notice what’s the same in both: one input record in, one small (key, value) pair out — the mapper never looks at any other record, and never talks to any other machine. Exactly like your cluster tallying your own pile alone, Monday.

Think about it

A log file has one line per web request: timestamp, userID, status_code. You want to count how many requests resulted in each status code (200, 404, 500, …). What should map() emit?

Timing: 5 min. Callout answer: emit(status_code, 1) — structurally identical to word count and the sales example, just a different field extracted. The point of showing three problems with the same shape is pattern transfer, since Lab 4 and CP3 both hand students a new extraction problem (email domains) they need to recognize as this same pattern.

The Shuffle/Sort Phase: The Framework’s Job

After every machine finishes its map phase, all the emitted (key, value) pairs need to end up grouped by key — every value for "gmail.com" in one place, every value for "yahoo.com" in another — regardless of which machine originally emitted them.

  • This is exactly Monday’s “carry your tally to whoever owns that key” step — except now it’s the framework doing the carrying, across a real network, not a student walking across a room.
  • You never write this step yourself. Hadoop and Spark both do shuffle/sort automatically — it’s the one phase of MapReduce with no function you implement.
  • It’s also the one phase that costs real network transfer — same as Monday, where trips were the only real cost. Map and Reduce, like your cluster’s own tallying and summing, happen locally.

Timing: 4 min. Emphasize “you never write this step” explicitly — CP3 only asks students to write map-phase output precisely because shuffle and reduce’s mechanics are the framework’s job, not something to hand-code.

The Reduce Phase: Combine Each Group Into One Answer

A reduce function receives one key and the full list of values shuffled to it, and produces one final result for that key.

reduce(key, values):
    total = sum(values)
    emit(key, total)
  • This runs once per key, on whichever machine the shuffle phase sent that key’s values to — the same role as the one teammate on Monday who “owned” a suit or menu item and summed everything handed to them.
  • Reduce doesn’t have to mean “sum” — it could compute a maximum, an average, a count of distinct values, anything that combines a list into one answer. Summing is just today’s example.

Timing: 3 min. Keep this brief — it’s the shortest of the three phase slides because it’s the most intuitive once Map and Shuffle are solid.

Pause & Discuss: Average, Not Count

Breather — think on your own (2 min), then we discuss

The capstone’s ratings data has one line per rating:

userId,movieId,rating
1,31,2.5
1,1029,3.0
7,31,4.0

You want the average rating for each movie. What should map() emit? What does reduce() do with each movie’s list of values?

Harder follow-up: to cut shuffle traffic, a teammate suggests that each machine first computes a local average per movie, and then the reducer averages those averages. Does that give the right answer?

Timing: 4 min (≈2 min silent thinking, ≈2 min discussion). Answer:

  • map: emit(movieId, rating). Same shape as word count and sales-per-region.
  • reduce: emit(movieId, sum(values) / len(values)). In the example, movie 31 gets [2.5, 4.0] → 3.25.
  • Follow-up: no. Averaging averages is wrong whenever the groups are different sizes. Say machine 1 has movie 31’s ratings [5, 5, 5, 5] (average 5) and machine 2 has [1] (average 1). The average of averages is 3, but the true average is 16 / 5 = 3.2. Fix: each machine sends a (sum, count) pair per movie, and the reducer adds up the sums and counts and divides once at the end. Sums and counts can be combined early; averages can’t. Spark’s avg() (Module 4) does exactly this for you.

This sets up the next slide: the teammate’s instinct (shrink what crosses the network) is right. Only the math was wrong.

Why This Scales

Module 2 put it this way: “a distributed system grows by adding more machines, not by buying an impossibly bigger one.” That’s called scaling out (add more machines) as opposed to scaling up (buy one bigger machine) — MapReduce is the mechanism that makes scaling out actually work for processing, not just storage.

  • Map tasks run in parallel, one per input chunk — on a real cluster, ideally on the same machine that already holds that chunk of data. This is called data locality: compute goes to the data, not data to the compute. Kitchen picture: send the recipe to the branch that already has the ingredients, don’t ship the ingredients to one central kitchen.
  • Reduce tasks also run in parallel, one per key (or range of keys).
  • Only shuffle moves data across the network — exactly the one phase that cost a trip on Monday. Everything else happens locally, at the same time, on every machine.
  • Adding a 21st machine to a MapReduce cluster doesn’t require rewriting map() or reduce() — it just means one more machine’s worth of chunks processed in parallel. That’s what “scaling out” buys you: capacity grows by adding machines, with the same code.

Important

This is the same instinct your best cluster found in Round 2: move the small thing (a tally), not the big thing (the raw pile). Data locality is that same idea, one level up — don’t move the raw data to the computation, move the (tiny, by comparison) computation to the data.

Timing: 4 min. The callout is the payoff of the whole activity — say explicitly that “data locality” is the formal name for the exact efficiency idea their best Round 2 strategy already discovered. The scale-up/scale-out distinction isn’t tested by any checkpoint, quiz, or exam — it’s here only so the slide’s own title (“scales”) is earned by a definition rather than assumed. Don’t spend more than a sentence on it.

What the Framework Handles For You

Beyond running Map, Shuffle, and Reduce, Hadoop and Spark both handle a list of things you never have to code yourself:

  • Task scheduling — deciding which machine runs which chunk
  • Fault tolerance — if a machine dies mid-job, its work gets reassigned and re-run elsewhere
  • Retries — a failed task is retried automatically, not left broken
  • Progress tracking — reporting how much of the job is done

You write map() and reduce(). The framework does everything else — a big part of why MapReduce was such a breakthrough in 2004.

Timing: 2 min. Keep brief — this is context for why the abstraction is valuable, not testable detail.

Why Not Just a Regular File System?

A regular file system — the one on your laptop — lives on one machine’s one disk.

  • Its size is capped by that one disk, no matter how the rest of the data grows.
  • If that one disk fails, everything on it is gone — no backup, nothing to fall back on.
  • Only one machine can read it at a time — no way to spread the reading work across many machines.

HDFS (Hadoop Distributed File System) splits a file into pieces and spreads those pieces — plus duplicate copies — across many machines’ disks. The file can now be bigger than any single disk, survives a disk failure, and can be read by many machines at once, in parallel. This is the same scaling out idea from Wednesday — now applied to storage, not computation.

Timing: 4 min. One-sentence callback to Wednesday’s scale-up/scale-out beat is enough — don’t re-derive it, just point at it: “same idea, different resource.”

HDFS Blocks + Replication

  • HDFS splits a file into fixed-size blocks (default 128 MB) — a large file becomes many blocks, scattered across many machines.
  • Each block is stored on 3 machines, not one (replication factor = 3).
  • Kitchen picture: like stocking the same popular ingredient at 3 different branches, so one branch’s fridge breaking down doesn’t mean the whole company runs out of it.
  • This is a first, simpler taste of the replication idea — Module 5 covers the full version, including why 3 copies, consistency between them, and what happens when one goes stale. For now: 3 copies, automatic, so no single block is a single point of failure.
ratings.csv (say, 500 MB) → split into 4 blocks of ~128 MB each
  Block 1 → stored on Machine A, Machine C, Machine E
  Block 2 → stored on Machine B, Machine D, Machine A
  Block 3 → stored on Machine C, Machine E, Machine B
  Block 4 → stored on Machine D, Machine A, Machine C

Timing: 4 min. The block-placement example is illustrative, not something to test — the point is “different blocks can land on different machines, and each one is triplicated,” not the exact placement algorithm.

HDFS Architecture: The Address Book, Again

Module 2 gave you DNS: the internet’s address book, translating a human-readable name into a numeric address before your browser could even connect. HDFS has the exact same shape of problem — given a filename, which machines actually hold its blocks?

  • The NameNode is HDFS’s version of that address book — it tracks which blocks belong to which file, and which machines hold each block. It does not store any of the actual file data itself.
  • DataNodes are the machines that store the real block data.
  • To read a file: the client asks the NameNode “where are this file’s blocks?”, the NameNode replies with a list of DataNode locations, and the client then reads the blocks directly from those DataNodes — the NameNode itself never touches the actual data.

HDFS Commands Demo

hdfs dfs -put ratings.csv /user/alice/    # upload: local file → HDFS
hdfs dfs -ls /user/alice/                 # list files in an HDFS directory
hdfs dfs -cat /user/alice/ratings.csv     # read a file's contents
hdfs dfs -get /user/alice/ratings.csv .   # download: HDFS → local file
  • -put and -get are opposites: local-to-HDFS, and HDFS-to-local.
  • -ls and -cat mirror the everyday Unix commands you already know, just pointed at HDFS instead of your local disk.
  • This -put command is not a hypothetical — it’s the literal first step of Week 1’s Pipeline diagram, and the exact command Lab 10 has you run on ratings.csv and movies.csv for the capstone.

Timing: 5 min. Actually run these four commands live against the classroom cluster if possible, on a small throwaway file — seeing real output (a real file listing, real file contents) lands better than reading the commands off a slide.

HDFS Design Principles

  • Write once, read many — files aren’t modified after writing; you write a file once, then only ever read it (or replace it entirely) afterward.
  • Data locality — the same idea from Wednesday: MapReduce runs map tasks on the same machine that already holds the data block being processed.
  • Fault tolerance — if a DataNode fails, its blocks are automatically re-replicated elsewhere from the remaining copies, restoring the replication factor of 3.
  • Not good for: small files (overhead per file is high), low-latency access (built for throughput, not speed-of-single-lookup), or random writes (write-once-read-many, remember).

Timing: 3 min. HDFS was designed for exactly the workload MapReduce produces — large, sequential reads of immutable files. It’s a poor choice for transactional workloads (that’s what Module 5’s databases are for) — worth saying explicitly, since students may otherwise wonder why the capstone uses both HDFS and MongoDB instead of just one.

Pause & Discuss: What Happens When a Machine Dies?

Breather — think on your own (2 min), then we discuss

You -put a 1 GB file into HDFS (128 MB blocks, replication factor 3) on a cluster with 10 DataNodes.

(a) How many blocks is the file split into? How much total disk space does it take up across the cluster?

(b) One DataNode’s disk dies. Is any part of the file lost? What does HDFS do next?

(c) Instead, the NameNode dies, and every DataNode is fine. Can you still read the file?

Timing: 4 min (≈2 min silent thinking, ≈2 min discussion). Answer:

  • (a) 1024 / 128 = 8 blocks. With 3 copies each, that’s 24 block copies, about 3 GB of raw disk.
  • (b) Nothing is lost. Every block on the dead node still has 2 copies elsewhere. HDFS notices the node has gone silent and re-replicates its blocks from the surviving copies until each block is back to 3 (the Design Principles slide). Data is only lost if all 3 holders of the same block die before re-replication finishes.
  • (c) No. Every byte is still on the DataNodes, but nothing knows which blocks make up which file, or where they are. The address book is gone. In a basic setup that makes the NameNode a single point of failure, and production clusters run a standby NameNode to take over. Compare DNS: when DNS is down, every website still exists, but you can’t find any of them.

Part (c) sets up Module 5 Session 1’s single-point-of-failure slide.

YARN: Who Actually Runs the Job?

HDFS answers “where does the data live.” YARN (Yet Another Resource Negotiator) answers “which machine actually runs each Map or Reduce task, and who’s keeping track?”

  • ResourceManager — the whole branch network’s dispatcher: one per cluster, deciding which worker machine handles a newly submitted job.
  • NodeManager — each branch’s own on-site manager: one per worker machine, actually running whatever tasks get assigned to that machine.
  • ApplicationMaster — a coordinator dispatched specifically for one job: tracks that job’s progress across whichever workers are running its tasks. One ApplicationMaster per job, not one for the whole cluster.

A MapReduce Job in Practice

The output directory of a completed Hadoop MapReduce job:

/output/
  _SUCCESS          ← empty file, signals the job completed successfully
  part-r-00000      ← actual output (one file per reducer)
  part-r-00001      ← (if 2 reducers were used)
  • Never overwrite an existing output directory — Hadoop refuses, specifically to prevent accidental data loss. You’ll see this exact error in Lab 5 if you forget to clean up first.
  • Delete it yourself before re-running: hdfs dfs -rm -r /output

Timing: 3 min. This is a direct preview of Lab 5’s Task 3, Question 3 — say plainly that they’ll hit this refusal-to-overwrite behavior themselves on Friday, so it isn’t a surprise.

From MapReduce to Spark

MapReduce already gets you scaling out for processing — but it has real limitations:

  • Every job writes its intermediate results to disk, even between steps of the same pipeline — slow for anything iterative.
  • The Mapper/Reducer API is low-level and verbose — hard to express a multi-step pipeline cleanly.
  • No support for interactive, ask-a-question-and-wait-seconds-for-an-answer queries.

Spark (2009, Berkeley AMPLab) keeps intermediate data in memory instead of writing it to disk between steps — 10–100× faster for iterative workloads. Same scaling-out idea as MapReduce; Module 4 is about doing it faster.

Timing: 3 min. Keep the framing “same idea, faster mechanism” rather than “MapReduce is obsolete” — Hadoop/HDFS is still the storage layer under Spark in this course’s own pipeline.
