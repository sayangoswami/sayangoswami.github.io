Recap: You’ve Already Used the Cloud

Before defining anything: you’ve already relied on a cloud provider without thinking of it that way. MongoDB Atlas, since Lab 9 — you never installed a database server, never provisioned a machine. You made an account, clicked a button, and had a running, replicated MongoDB cluster within minutes.

That’s cloud computing. Today: precise vocabulary for what you were actually doing.

Timing: 3 min. Anchor immediately in something concrete and already-experienced, rather than opening with an abstract definition.

What Is Cloud Computing?

Cloud computing means renting computing resources — servers, storage, databases, machine learning services — over the internet, on demand, paying only for what you actually use.

  • You never own or physically touch the hardware; the provider does, somewhere in one of their data centers.
  • Before cloud: a startup had to buy and rack physical servers — real upfront cost, real lead time — before writing a single line of application code.
  • With cloud: you can start with $0, write code today, and scale to millions of users later, on the same code, just by renting more.

Timing: 5 min. The “same code, just renting more” line is worth landing explicitly — it’s Week 1’s “the code doesn’t change, only the scale does” idea, now applied to infrastructure instead of data volume.

The Apartment Analogy: IaaS, PaaS, SaaS

Cloud providers offer different amounts of “already done for you”:

  • IaaS (Infrastructure as a Service): renting an empty apartment. Four walls, plumbing, electricity — no furniture. You install your own operating system and runtime, everything above the bare hardware.
  • PaaS (Platform as a Service): renting a furnished apartment. Utilities and maintenance are handled — you just move in your own belongings (your code and data). The provider manages the OS, the runtime, the scaling.
  • SaaS (Software as a Service): a hotel room. Everything is provided and maintained for you — you just use it. You never think about plumbing or furniture at all.

Concretely: Google Colab is PaaS-like (you write code, Google manages the runtime underneath it). MongoDB Atlas is SaaS-like (you never configure a database server at all — you just use the database).

Think about it

A startup wants to deploy a Python web app without managing servers, operating systems, or runtime environments — just write code and deploy it. Which of the three fits?

Timing: 5 min. Callout answer: PaaS — this is close to Quiz 8 Q3’s own scenario shape (Heroku/App Engine), so it’s good rehearsal without spoiling the quiz’s exact wording.

The Three Service Models, Named

Model You manage Provider manages Examples
IaaS OS, runtime, apps Hardware, networking AWS EC2, Google Compute Engine
PaaS Your code and data OS, runtime, scaling Heroku, Google App Engine, Colab
SaaS Nothing — just use it Everything Gmail, Dropbox, Salesforce, MongoDB Atlas

Important

The more “as a service,” the less you manage — but also the less control you have. IaaS gives you the most control and the most responsibility; SaaS gives you the least of both.

Scaling Out, Someone Else’s Problem

  • Module 3 gave you scaling out — add more machines instead of buying one bigger one — as the mechanism behind MapReduce and HDFS.
  • Cloud computing takes that same idea and hands the “adding machines” part to the provider: click a button (or, as Nov 30 covers, let it happen automatically) and more capacity appears, without you racking a single physical server yourself.
  • Same vocabulary, same idea — now something you rent, not something you build.

EL5 Preview: When the Cloud Breaks

(EL5 — assigned today, due Nov 30): read a real cloud outage post-mortem and reflect on which distributed-systems concepts explain the failure.

Recall Module 2 Session 3’s GitHub case study — a network partition lasting seconds caused an outage lasting a day. Real cloud outages follow the same pattern:

  • Single-region risk — many services quietly depend on the same one region; if it goes down, everything built on it goes down together.
  • Cascading failures — one service slows down, its queues fill up, callers time out, and the failure spreads to services that were never directly affected.
  • The “retry storm” — the moment a recovering service comes back online, every client that was failing retries at once, instantly overwhelming it again.

Timing: 4 min. This slide anchors EL5, it doesn’t teach new content in depth — point back to Module 2 Session 3’s GitHub incident explicitly as the model students should apply to whatever outage post-mortem they choose to read.

Recap: From Renting to Running Efficiently

Nov 23 gave you the vocabulary for renting cloud resources. Today: two patterns for using them efficiently (autoscaling, serverless), then a design question for how to structure the application running on them (monolith vs. microservices) — plus Checkpoint 8.

Timing: 3 min. Fast bridge only.

Autoscaling: Extra Cooks During the Dinner Rush

Autoscaling means a cloud service automatically adds capacity when demand rises, and removes it again when demand falls — with no human deciding when.

  • Kitchen picture: a branch calls in extra cooks the moment a dinner rush starts, and sends them home once things quiet down — not a fixed staff sized for the busiest night of the year, sitting idle every other night.
  • Concretely: a web service might normally run on 2 machines, automatically scale to 20 during a traffic spike (a product launch, a viral post), then scale back down to 2 once traffic drops.
  • This is scaling out from Module 3 — but automatic, and elastic in both directions, scaling out and back in, based on real-time demand rather than a human’s decision.

Important

Without autoscaling, you face two bad choices: provision for peak load and pay for idle capacity almost all the time, or provision for average load and fall over during a spike. Autoscaling is the industry’s answer to not having to choose.

Timing: 4 min. Keep this brief but don’t skip it — it’s promised syllabus content for today even though it isn’t separately quiz-tested.

Serverless: You Never See a Machine at All

Serverless computing goes one step further than renting a machine — you don’t manage a machine at all, not even a rented one.

  • You write a single function. The provider runs it only when triggered — an HTTP request, a file upload, a scheduled time — on infrastructure you never provision, see, or manage.
  • You pay only for the time your function actually runs, not for an idle server waiting for the next request.
  • Recall Nov 23’s Cloud-Native Data Services table: “Our Flask API → AWS Lambda + API Gateway, Cloud Run” was left unexplained on purpose. That’s exactly this — a serverless Flask deployment doesn’t run on a machine you provisioned; it runs only when a request actually arrives.

Think about it

Our classroom Flask API (Wed Dec 2) runs on one machine the whole time class is happening, whether or not anyone is hitting it. What would change, in cost and in behavior, if it ran serverless instead?

Timing: 4 min. Closes the loop on the deliberate plant from Nov 23 — say explicitly “this is the answer to the row I left unexplained last session.”

Bridge: One Kitchen vs. Many Kitchen Branches

Since Module 1, one running picture has covered how work gets organized: one kitchen, many cooks (a single program); many kitchen branches, coordinating over the phone (distributed machines). Today’s last topic asks the same question one level up: should your application itself be built as one kitchen doing everything, or as many specialized branches?

Timing: 3 min. Explicit bridge slide — make the “one level up” framing clear before the next two slides apply it.

Monolith: One Big Kitchen

Monolith: the entire application — every function — is built and deployed as a single unit.

┌──────────────────────────────────┐
│           Monolith               │
│  ┌────────┐ ┌───────┐ ┌───────┐ │
│  │  Auth  │ │Orders │ │Payment│ │  ← all in one kitchen
│  └────────┘ └───────┘ └───────┘ │
│              Database            │
└──────────────────────────────────┘
  • Kitchen picture: one kitchen, one staff, cooking the auth dish, the orders dish, and the payment dish, all in the same space — deployed (opened for business) as one unit.
  • ✅ Simple to develop and test — everything lives in one codebase, one process.
  • ✅ Easy deployment — one thing to build, one thing to deploy.
  • ❌ One bug anywhere can crash the entire kitchen, not just the dish it was in.
  • ❌ Fixing a typo in the payment logic means rebuilding and redeploying the entire application — auth and orders included, even though neither changed.

Timing: 4 min. Checkpoint 8’s key distinguishing question is “can you update one part without redeploying everything” — the last bullet here is the direct answer for a monolith: no.

Microservices: Separate Kitchen Branches

Microservices: each function is built and deployed as an independent service, communicating with the others the same way Module 2 taught you any two machines communicate — over REST APIs.

Client
  ↓
API Gateway
  ├── Auth Branch         (own DB, own deployment)
  ├── Order Branch        (own DB, own deployment)
  ├── Payment Branch      (own DB, own deployment)
  └── Notification Branch (own DB, own deployment)
  • Kitchen picture: an Auth branch, an Order branch, a Payment branch — each its own kitchen, its own staff, its own inventory — calling each other on the phone (a REST request) whenever one needs something from another.
  • ✅ Each branch scales independently — today’s autoscaling can add capacity to just the Payment branch during a sale, without touching the others.
  • ✅ Different teams can deploy their own branch independently — no coordinating one giant release.
  • ❌ Every call between branches is now a network call — Module 2’s entire catalogue of failure modes (lost messages, timeouts, partial failures) applies to every one of these calls, where a monolith’s internal function calls never fail that way.
  • ❌ Distributed tracing, service discovery, keeping data consistent across many separate databases — all genuinely new problems a monolith never had.

Timing: 5 min. The “every call is now a network call” bullet is worth dwelling on — it’s the direct payoff of Module 2 Session 1’s entire catalogue (lost/delayed/reordered messages, partial failures, the timeout problem), now shown to apply inside a single application’s own architecture, not just between two different companies’ servers.

When to Use Which

Situation Prefer
New product, small team, fast iteration Monolith
High scale, different services have different load patterns Microservices
Different teams owning different features Microservices
Strong consistency requirements Monolith (simpler transactions)

Note

Many companies start with a monolith and break it into microservices as they scale. Netflix, Uber, and Amazon all did this — it’s a normal evolution, not a sign the monolith was a mistake.

Timing: 3 min. Resist framing microservices as strictly “better” — Checkpoint 8’s own sample solution credits the monolith with real, legitimate advantages for its scenario.

Flask: Module 2’s REST Vocabulary, in Code

Everything Flask does is Module 2’s REST anatomy, written as code instead of read off the wire:

Module 2 concept Flask’s version
A URL identifies a resource @app.route("/users/<id>")
An HTTP verb says what to do methods=["GET"], methods=["POST"], …
A response has a status code return jsonify(...), 201
A JSON body jsonify({...}) builds one for you

Flask is a lightweight Python web framework — small enough that a full REST API is often under 50 lines of code.

Timing: 4 min. Walk this table before showing any code — the goal is “you already know all of this conceptually, Flask is just the syntax,” not introducing REST as new material.

Your First Flask Route

from flask import Flask, jsonify
app = Flask(__name__)

@app.route("/hello")
def hello():
    return jsonify({"message": "Hello, World!"})

@app.route("/users/<int:user_id>")
def get_user(user_id):
    return jsonify({"id": user_id, "name": "Alice"})

if __name__ == "__main__":
    app.run(debug=True, port=5000)
  • @app.route("/hello") is a decorator — it wraps the function written right below it. Read it as: “whenever an HTTP request arrives at /hello, call this function and send back whatever it returns.”
  • <int:user_id> in the URL captures part of the path as an argument — a request to /users/42 calls get_user(42).
  • jsonify(...) takes a Python dict and turns it into a proper JSON HTTP response.
  • Run with python app.py, then visit http://localhost:5000/hello in a browser.

Timing: 5 min. The decorator explanation is genuinely new depth for this audience — don’t assume “decorator” is a familiar Python concept, spell it out plainly as “wraps the function below it,” since it’s one of the more abstract syntax ideas in the whole course.

Flask Route Patterns

# Query parameters: GET /search?q=python&limit=10
from flask import request

@app.route("/search")
def search():
    q     = request.args.get("q", "")
    limit = int(request.args.get("limit", 10))
    return jsonify({"query": q, "results": []})

# POST with a JSON body
@app.route("/users", methods=["POST"])
def create_user():
    data = request.get_json()
    name = data["name"]
    return jsonify({"created": name}), 201
  • request.args.get(...) reads a query parameter — the part of the URL after ?.
  • methods=["POST"] is Module 2’s POST verb, named explicitly — without it, this route only accepts GET by default.
  • request.get_json() reads the request’s JSON body — the counterpart to jsonify() on the way out.
  • , 201 returns HTTP status 201 (“Created”) — Module 2’s status-code vocabulary, chosen deliberately instead of the default 200.

Timing: 4 min. Point at each line and name which Module 2 concept it’s implementing — the whole point of this slide is “no new ideas, just syntax for old ones.”

Connecting Flask to MongoDB

from flask import Flask, jsonify
from pymongo import MongoClient

app    = Flask(__name__)
client = MongoClient("mongodb+srv://...")
db     = client["mydb"]

@app.route("/employees")
def get_employees():
    docs = list(db["employees"].find({}, {"_id": 0}))
    return jsonify(docs)

@app.route("/employees/<dept>")
def get_by_dept(dept):
    docs = list(db["employees"].find({"dept": dept}, {"_id": 0}))
    return jsonify(docs)
  • Same MongoClient and .find() syntax from Module 5’s Lab 9 — nothing new there.
  • list(...) around .find() is necessary because jsonify() needs an actual list, not MongoDB’s lazy cursor object.
  • This is exactly the pattern your capstone’s flask_app.py uses for its five JSON API endpoints.

Timing: 4 min. Say plainly: “this slide is the shape of five of your capstone’s endpoints, just with different collection names and filters.”
