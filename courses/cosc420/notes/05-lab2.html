Lab 2: Java Threading Exercises

Module 1: Concurrency

Published

September 4, 2026

Date: September 11
Duration: 50 minutes
Points: 10
Competency: C1.2 — Apply synchronized and locks to prevent race conditions

Background

Last week (Lab 1) you observed a race condition and made it safe with synchronized. Today you write your own threaded programs — first using raw Thread objects, then using an ExecutorService thread pool, which is closer to how real applications manage concurrency.

Getting ahead of lecture, on purpose: thread pools aren’t covered in depth until Sep 16 (Session 5), and you’ll get a short intro at the end of Session 4 (Sep 14). Today you use one hands-on first — the same way you used synchronized in Lab 1 before Session 4 explains it. The pool API you need for Task 2 is spelled out below; you’re not expected to know it cold.

Setup

Open the IDE of your choice. Create a new file for each task (or use separate classes in one file).

Task 1 — Write a Runnable (15 min)

Create a class called PrintTask that implements Runnable. When run, it should: - Print "Thread <name> starting" (use a name passed in via the constructor) - Loop 5 times, printing "Thread <name>: step <i>" - Print "Thread <name> done"

In main, create three PrintTask instances with names "A", "B", and "C". Start all three threads and call join() on each so main waits for them to finish.

Expected output (order of steps will vary between runs — that is normal):

Thread A starting
Thread B starting
Thread C starting
Thread A: step 1
Thread B: step 1
...
Thread C done

Task 2 — Use an ExecutorService (20 min)

Rewrite Task 1 using ExecutorService with a fixed thread pool of 2 threads instead of creating threads manually. Submit the same three PrintTask instances to the pool.

An ExecutorService is a ready-made pool of worker threads. Instead of new Thread(task).start(), you hand tasks to the pool with submit(...) and it runs them on whichever worker is free. The four calls you need:

Call What it does
Executors.newFixedThreadPool(n) create a pool with n reusable worker threads
pool.submit(task) hand one Runnable to the pool’s queue; a free worker picks it up
pool.shutdown() stop accepting new tasks; let the ones already submitted finish
pool.awaitTermination(t, unit) block here until all tasks finish (or the timeout elapses) — the pool’s equivalent of join() 
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

ExecutorService pool = Executors.newFixedThreadPool(2);

pool.submit(new PrintTask("A"));
pool.submit(new PrintTask("B"));
pool.submit(new PrintTask("C"));

pool.shutdown();                              // no more tasks after this
pool.awaitTermination(10, TimeUnit.SECONDS);  // wait for A, B, C to finish

Don’t worry about how the pool reuses threads or manages its queue — that’s the Sep 16 lecture. Today you just need to see that 3 tasks and 2 workers means one task waits its turn.

Questions:

  1. With 3 tasks and a pool of 2 threads, what do you observe about the order tasks start? Can all three run at the exact same time?
  2. What does pool.shutdown() do? What happens if you forget it?
  3. Change the pool size to 1. What changes about the output? Why?

Task 3 — Shared Counter with a Thread Pool (15 min)

Using an ExecutorService (same four calls as Task 2), submit 5 tasks that each increment a shared counter 1000 times, then print the final counter value.

ExecutorService pool = Executors.newFixedThreadPool(3);
for (int i = 0; i < 5; i++) {
    pool.submit(() -> {
        for (int j = 0; j < 1000; j++) {
            // increment the shared counter here
        }
    });
}
pool.shutdown();
pool.awaitTermination(10, TimeUnit.SECONDS);
System.out.println("Final counter: " + counter);

You’ll see the same race condition from Lab 1. Fix it with synchronized, the same way you did there.

Expected final counter: 5000 (always, after the fix).
