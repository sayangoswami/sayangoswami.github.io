Module 1: Concurrency

Module 1 Summary

Concept Key idea
Process / Thread A process has its own memory; threads inside it share the heap, each with a private stack
Race condition The result depends on unpredictable thread timing; non-atomic read-modify-write is the classic cause
synchronized Mutual exclusion on one specific object’s lock
Deadlock Circular wait: each thread holds a lock the other needs. Frozen.
Livelock Threads keep reacting to each other and retrying. Busy, no progress.
Starvation One runnable thread never gets its turn while others make progress
Thread pool A fixed set of reused worker threads pulling tasks from a queue
Future Returned immediately by submit(); .get() blocks until the result is ready

Timing: 3 min. Students already saw the long version of this table in the Quiz 1 review — don’t re-teach it, just ask the room to define two or three rows from memory before showing them.

Practice 1: The Bank Transfer

void transfer(Account from, Account to, int amount) {
    synchronized (from) {
        synchronized (to) {
            from.balance -= amount;
            to.balance   += amount;
        }
    }
}

// Thread A:  transfer(alice, bob, 10);
// Thread B:  transfer(bob, alice, 20);   // at the same time

Both balances are protected by locks, so there’s no race condition on them.

With a partner (2–3 min): can this program get stuck forever? If so, trace the steps that cause it, name the failure, and fix transfer() so it can’t happen.

Timing: 4 min including pair discussion. Most pairs will spot the problem; push them on the fix. “Synchronize the whole method” doesn’t fix it here, because the method locks two different objects each call.

Practice 1: Solution

Yes, this can deadlock. One interleaving that does it:

  1. Thread A locks alice (its from).
  2. Thread B locks bob (its from).
  3. Thread A tries to lock bob, which B holds, so A waits.
  4. Thread B tries to lock alice, which A holds, so B waits.

Each thread holds what the other needs: a circular wait. Neither ever lets go.

The fix: acquire the two locks in the same order everywhere, no matter which account is from. For example, always lock the account with the smaller id first:

Account first  = (from.id < to.id) ? from : to;
Account second = (from.id < to.id) ? to   : from;
synchronized (first) {
    synchronized (second) {
        from.balance -= amount;
        to.balance   += amount;
    }
}

Now both threads try to lock alice first (or both bob first). Whoever gets it also gets the second lock. The other thread just waits its turn.

Timing: 4 min. This is the Session 4 knife-and-cutting-board picture with real objects. Point out that the deadlock depends on the arguments: two transfers in the same direction never deadlock, which is why bugs like this survive testing.

Practice 2: Name That Failure

Each scenario describes a program that misbehaves. Match it to race condition, deadlock, livelock, or starvation.

(a) A server hangs. CPU usage drops to 0%. A thread dump shows two threads, each BLOCKED waiting on a lock the other one holds.

(b) CPU usage is pinned at 100%. The log fills with “conflict detected, backing off, retrying” from two threads, millions of times. No work ever finishes.

(c) A ticket-sale program sells seat 14C to two different customers about once a week. When a developer steps through it in a debugger, it never happens.

(d) A low-priority “nightly report” thread has been waiting for three days. The server is busy handling a steady flood of high-priority requests, and all of those are completing normally.

With a partner (2–3 min): name each one, and say which clue gave it away.

Timing: 4 min including pair discussion. The clue is the point, not just the label. Ask pairs to report the clue first.

Practice 2: Solution

  • (a) Deadlock. The clue: 0% CPU and each waits on a lock the other holds. Frozen threads use no CPU.
  • (b) Livelock. The clue: 100% CPU but no progress. The threads are busy reacting to each other, like two people stepping aside in a doorway forever.
  • (c) Race condition. The clue: only sometimes, and it disappears under the debugger, which changes the timing. That’s a Heisenbug. Two threads both read “14C is free” before either wrote “sold.”
  • (d) Starvation. The clue: the system overall is making progress; only one thread never gets a turn.

Tip

Quick rule: frozen → deadlock. Busy but stuck → livelock. Everyone else fine → starvation. Wrong sometimes → race condition.

Timing: 4 min. If a pair said (c) was a deadlock, ask: “Did anything get stuck?” A race condition produces wrong results. The other three produce no results.

Practice 3: Trace the Thread Pool

// main is declared "throws Exception"
ExecutorService pool = Executors.newFixedThreadPool(2);
List<Future<Integer>> results = new ArrayList<>();

for (int i = 1; i <= 4; i++) {
    final int n = i;
    results.add(pool.submit(() -> {
        Thread.sleep(1000);      // each task takes ~1 second
        return n * 10;
    }));
}
System.out.println("all submitted");

for (Future<Integer> f : results) {
    System.out.println(f.get());
}
pool.shutdown();

With a partner (2–3 min):

(a) Does "all submitted" print right away, or after the tasks finish?

(b) Roughly how long until the last number prints?

(c) What if the pool had 4 threads instead? What about 1?

(d) In what order do the numbers print?

Timing: 4 min including pair discussion. Draw the 2-worker queue on the board if pairs are stuck on (b): the same picture as the Session 5 queue trace.

Practice 3: Solution

  • (a) Right away. submit() doesn’t wait for the task. It puts the task in the queue and hands back a Future (an order ticket) immediately.
  • (b) About 2 seconds. Two workers, four 1-second tasks: tasks 1 and 2 run together, then tasks 3 and 4 run together. That’s two rounds.
  • (c) 4 threads: about 1 second (all four run at once). 1 thread: about 4 seconds (one at a time). The pool size caps how many tasks run at once. Extra tasks wait in the queue.
  • (d) 10, 20, 30, 40, in that order, every time. The loop calls .get() on the futures in the order they were submitted, and .get() blocks until that particular result is ready. Even if task 2 finished a moment before task 1, its value isn’t printed until task 1’s .get() returns.

Timing: 4 min. Part (d) is the subtle one. The tasks may finish in any order, but the printing order is set by the order of the .get() calls.

Module 2: Distributed Systems Concepts

Module 2 Summary

Concept Key idea
Partial failure Some machines fail while others keep running; the system can be up for some users and down for others
Dead or slow? From outside, a crashed node and a slow node look the same; a timeout is only a guess
No global clock Each machine’s clock drifts, so timestamps from different machines can’t be trusted to order events
Failure types Crash (stops), omission (drops some messages), timing (too slow), Byzantine (wrong answers)
8 fallacies Network reliable, zero latency, infinite bandwidth, secure, fixed topology, one admin, free transport, homogeneous: all false
CAP During a partition, choose consistency (latest data or an error) or availability (always a response, maybe stale)
HTTP / REST Verb says what to do, URL says to what; status code says how it went; REST is stateless
Status codes 2xx success · 3xx redirect · 4xx your request is wrong · 5xx their server broke

Timing: 3 min. The Availability definition is still the most-missed idea in this module: “always responds” is not “always responds correctly.” Say it once more here.

Practice 4: Diagnose the Distributed Bug

For each scenario, name the failure type (crash, omission, timing, Byzantine) or the fallacy of distributed computing the developer believed.

(a) A phone app makes 40 API calls, one after another, to draw a single screen. On campus Wi-Fi it feels instant. On a train it takes 12 seconds.

(b) A service has its database server’s IP address hard-coded. The ops team moves the database to a new machine, and the service breaks.

(c) One replica in a cluster has a faulty memory chip. It answers every request promptly and normally, but some of the account balances it returns are garbage.

(d) A node receives “are you alive?” heartbeat messages, but only replies to about half of them.

With a partner (2–3 min): name each one, and say how you’d tell it apart from the others.

Timing: 4 min including pair discussion. (a) and (b) are fallacies; (c) and (d) are failure types. Don’t tell pairs that split up front — let them figure out which list each belongs to.

Practice 4: Solution

  • (a) Fallacy 2: “latency is zero.” Each call’s round trip is tiny on fast Wi-Fi, but 40 of them in a row add up. A design that assumed network calls are free breaks as soon as latency is real.
  • (b) Fallacy 5: “topology doesn’t change.” Machines move, get replaced, and change addresses. Hard-coding where things are assumes they never will. (This is part of why DNS exists: look the address up by name instead.)
  • (c) Byzantine failure. The node looks healthy (prompt, normal responses) but returns wrong data. That’s why it’s the hardest type to defend against: nothing looks broken.
  • (d) Omission failure. The node is alive and working, but it drops some messages. Compare crash, where it would answer none of them.

Timing: 4 min. For (c), ask “how would you even notice?” A crashed node goes silent. A Byzantine node keeps talking, so you need some way to cross-check its answers.

Practice 5: Make the CAP Call

The network between two datacenters has just split: a partition. For each system, would you favor consistency or availability? Describe what a user on the cut-off side actually sees.

(a) A university course-registration system. Each section has a hard seat cap.

(b) A ride-share app’s map showing the positions of nearby drivers.

(c) A coordination service that tells every server in a cluster which one is the current “leader” allowed to accept writes.

(d) The customer-review section under each product on a shopping site.

With a partner (2–3 min): decide each one, and justify it with the cost of being wrong vs. the cost of not answering.

Timing: 4 min including pair discussion. Reasonable people can argue (a) either way. If a pair argues availability for (a), ask what happens to the 31st student in a 30-seat section. The reasoning matters more than the label.

Practice 5: Solution

  • (a) Favor consistency. Two sides of the split could each give away the last seat, so the section ends up over its cap. User sees: “Registration is temporarily unavailable, try again shortly.”
  • (b) Favor availability. A car icon a few seconds out of date is harmless; a blank map is useless. User sees: the map loads, but some cars may be slightly out of place.
  • (c) Favor consistency. If both sides each pick their own leader, you get split-brain: two leaders accepting conflicting writes. That’s the case study from Session 3. User sees: some servers refuse writes until the partition heals.
  • (d) Favor availability. If a new review doesn’t show up for a minute, nobody is harmed. User sees: the page loads; the newest reviews may be missing for a while.

Tip

The choice only matters during a partition. When the network is healthy, a well-built system gives you both. The real design question is: when the split happens, which is worse, wrong or silent?

Timing: 4 min. Connect (c) back to the case study by name. It’s the clearest example in the module of a wrong answer being far worse than no answer.

Practice 6: Pick the Verb, Predict the Status

A campus library has a REST API at https://api.campuslib.edu.

# - What the client wants to do (or what happens)

a - Sign up a brand-new library patron

b - Change only patron 88’s email address, leaving everything else alone

c - Cancel hold #301

d - Patron 88’s app sends a valid request, but its login token expired yesterday

e - A valid request arrives, but the library’s database server has crashed

With a partner (2–3 min): for (a)–(c), give the HTTP verb, a sensible URL path, and the success status code. For (d)–(e), give the status code you’d expect back. Then: for (d) and (e), should the client just retry the same request?

Timing: 4 min including pair discussion. (b) is the one to listen for: PATCH vs. PUT. Ask pairs what PUT would do to the patron’s other fields.

Practice 6: Solution

# Verb + path Status
a POST /patrons (patron details in the request body) 201 Created
b PATCH /patrons/88 (body: just the new email) 200 OK
c DELETE /holds/301 200 OK
d (any) 401 Unauthorized
e (any) 500 Internal Server Error (or 503 Service Unavailable)
  • (b): PUT would replace the whole patron record with what you send, so any field you left out could be wiped. PATCH changes only what you send.
  • Retry (d)? No. A 4xx means your request is the problem. Sending the same expired token again fails again. Log in again for a new token, then retry.
  • Retry (e)? Maybe, yes, after a short wait. A 5xx means the server broke, and that’s often temporary.

Timing: 4 min. The 4xx/5xx retry rule is the practical payoff of the status-code ranges. It’s how real client code decides what to do next.

Module 3: Big Data & MapReduce

Module 3 Summary

Concept Key idea
The 3 Vs Volume (too much), velocity (too fast), variety (too messy) for one machine
Map One record in → zero or more (key, value) pairs out; never sees other records
Shuffle/Sort The framework groups every value with the same key together; you don’t write it
Reduce Runs once per key on that key’s list of values → one result per key
Data locality Move the computation to the machine that already holds the data, not the other way
HDFS Files split into 128 MB blocks, each replicated on 3 machines
NameNode / DataNode NameNode = the address book (which blocks are where); DataNodes hold the actual bytes
YARN Decides where tasks run (ResourceManager, NodeManagers, one ApplicationMaster per job)

Timing: 3 min. The most useful single question for this module: “What decides which reducer a value goes to?” Answer: its key. Choosing the key is choosing the grouping.

Practice 7: Build a Search Index

A search engine needs to know, for every word, which documents contain it: an inverted index.

d1:  big data big ideas
d2:  data moves
d3:  ideas move data
map(docId, text):
    for each word in text:
        emit(word, docId)

reduce(word, docIds):
    emit(word, sorted list of distinct docIds)

With a partner (2–3 min): write out (1) the map output for each document, (2) the groups after shuffle/sort, and (3) the final reduce output.

Timing: 4 min including pair discussion. Same three-step trace as the word-count walkthrough, but the value is a document ID instead of a 1. Students who only memorized word count will need to think here, and that’s the point.

Practice 7: Solution

(1) Map: one mapper per document:

d1 → (big,d1) (data,d1) (big,d1) (ideas,d1)
d2 → (data,d2) (moves,d2)
d3 → (ideas,d3) (move,d3) (data,d3)

(2) Shuffle/Sort: grouped by key:

(big,[d1,d1])  (data,[d1,d2,d3])  (ideas,[d1,d3])  (move,[d3])  (moves,[d2])

(3) Reduce: distinct docs per word:

big → [d1]   data → [d1,d2,d3]   ideas → [d1,d3]   move → [d3]   moves → [d2]
  • big appears twice in d1, so its list has d1 twice. That’s why reduce keeps only distinct IDs.
  • move and moves are different keys. Shuffle matches keys exactly. It doesn’t know they’re related words.

Timing: 4 min. The move/moves point is worth a sentence: real search engines normalize words in the map step (lowercasing, stemming) for exactly this reason. Any cleanup you want has to happen before the key is emitted.

Practice 8: Find the Bug

A web server log has one line per page view: time, userId, page. The goal is the number of different users who visited each page.

09:01,u7,/home
09:02,u7,/home
09:05,u3,/home
09:06,u7,/about

A teammate writes:

map(line):            emit(page, 1)
reduce(page, values): emit(page, sum(values))

With a partner (2–3 min): what does the teammate’s job output for this data, and what should it output? Fix map and reduce. Then: would emitting (userId, page) from map work instead?

Timing: 4 min including pair discussion. Let pairs actually run the four lines by hand. The bug only shows up because u7 visited /home twice.

Practice 8: Solution

Teammate’s output: /home → 3, /about → 1. Correct: /home → 2 (u7 and u3), /about → 1. The job counts visits, not visitors: u7’s two visits count twice.

Fix: keep who visited, then count distinct values in reduce:

map(line):            emit(page, userId)
reduce(page, values): emit(page, number of distinct values)

/home receives [u7, u7, u3] → 2 distinct users.

Emitting (userId, page)? No. The key decides the grouping. Keying on userId puts each user’s pages together, which answers a different question: “how many pages did each user visit?”

Tip

Designing a MapReduce job starts with one question: “What am I grouping by?” That’s your key. Then ask: “What does reduce need to see to compute the answer?” That’s your value.

Timing: 4 min. Like the Session 2 average-of-averages problem: reduce isn’t always a sum. Here it’s “count distinct.”

Practice 9: HDFS by the Numbers

A 300 MB file is uploaded to an HDFS cluster with 5 DataNodes, the default 128 MB block size, and replication factor 3.

With a partner (2–3 min):

(a) How many blocks is the file split into? How much raw disk does it use across the cluster?

(b) Two DataNodes die at the same moment. Can any part of the file be lost? What does HDFS do next?

(c) A client reads the whole file. Do the file’s bytes pass through the NameNode?

(d) On our classroom server, hdfs dfs -ls shows a 1 where a real cluster shows 3. Why?

Timing: 4 min including pair discussion. Different numbers from the 1 GB example in the Session 3 lecture. For (a), watch for pairs who say “3 × 128 MB = 384 MB per copy.” The last block is smaller.

Practice 9: Solution

  • (a) 3 blocks: 128 MB + 128 MB + 44 MB. Each is stored 3 times, so 9 block copies, about 900 MB of raw disk. The last block only uses the 44 MB it needs, not a full 128 MB.
  • (b) Nothing is lost. Each block’s 3 copies are on 3 different machines, so losing 2 machines leaves at least one copy of every block. HDFS notices the dead nodes and re-replicates the affected blocks from the surviving copies until each is back to 3. (If 3 machines died at once, a block whose 3 copies were all on those 3 could be lost.)
  • (c) No. The client asks the NameNode where the blocks are, then reads them directly from the DataNodes. The NameNode is the address book, not a relay.
  • (d) The classroom cluster is one machine, so it’s configured with replication factor 1. There’s nowhere to put a second copy.

Timing: 4 min. (c) is the one students most often get backwards. If time allows, ask the follow-up from the lecture: what if the NameNode dies instead? (Data intact but unfindable: a single point of failure.)
