Methods with Parameters

COSC120: Introduction to Computer Science I

Learning Outcomes

By the end of this lecture, you’ll be able to:

  • Explain what a parameter is and why methods need them
  • Define methods that accept one or more parameters of specified types
  • Distinguish between a parameter (in the definition) and an argument (in the call)
  • Explain that argument order matters and that parameters are local to the method
  • Trace a method call and show how argument values flow into parameters

The Problem with Last Lecture’s Methods

Before introducing anything new, return to the methods from last lecture and expose their limitation. Those methods were useful but rigid — every call produced identical output. The printSeparator example was fine because you always want the same separator. But what about greeting different people? Printing different scores? Those methods would need to be rewritten for every new value. The repetition problem from last lecture hasn’t gone away — it has just moved: instead of repeating code inside main, now we’d repeat nearly-identical method definitions. The solution is to let the method accept input. On the second sub-slide, the highlighted lines are the only lines that differ between the three methods.

Last lecture, every method you wrote produced the same output every time it ran:

void printSeparator() {
    IO.println("--------------------");    // always this, forever
}

void printWelcome() {
    IO.println("Welcome to COSC 120!");   // always this text, forever
}

That is fine when the output really is always the same.

But what if you want to greet different people?

void greetAlice() {
    IO.println("Hello, Alice!");
}

void greetBob() {
    IO.println("Hello, Bob!");
}

void greetCharlie() {
    IO.println("Hello, Charlie!");
}

Three methods, one difference: the name inside IO.println. You are right back to the repetition problem, now with nearly-identical method definitions instead of nearly-identical code blocks.

There has to be a better way.

The Spell Needs a Target

Consider a the spell: Reparo — it fixes broken things.

But which broken thing? That depends on what you point your wand at:

  • Point at Harry’s cracked glasses → the glasses are fixed
  • Point at a shattered vase → the vase is fixed
  • Point at a broken wand → the wand is fixed

The spell is the same every time. What changes is the target.

The spell name tells Java what to do. The target tells Java what to do it to.

That target is what we are about to call a parameter.

The Coffee Machine

A third analogy that makes the parameter/argument distinction extremely concrete, and additionally explains type enforcement. The coffee machine has three containers — milk, beans, water (listed in the same order as the parameters of makeCappuccino, so the code later lines up with the picture). Each container is a parameter. What you pour into each container is the argument. You can vary the contents: soy milk, almond milk, oat milk all work in the milk container. Dark roast, medium roast, decaf all work in the beans container. But you cannot put beans in the water container — wrong type. The machine won’t run. This maps perfectly to Java: the method defines named slots (parameters) of specific types; what you provide at call time (arguments) must match those types; and within a type, you have freedom to vary the value. The “press the button” moment is calling the method. Take time on this slide — the tactile nature of containers and contents lands differently from the spell analogy and the blank-form analogy coming next, and together they reinforce the same idea from three angles.

Imagine a single-serve coffee machine with three labeled containers:

  • A milk container — holds milk
  • A beans container — holds coffee beans
  • A water container — holds water

You fill each container, press the button, and the machine makes your coffee using whatever you put in.

The containers are the parameters — named slots that hold the inputs.

What you pour in is the argument — the actual value you provide each time.

The containers give you flexibility:

  • Milk container → soy milk, almond milk, oat milk, whole milk all work
  • Beans container → dark roast, medium roast, decaf all work
  • Water container → water. Just water.

But you cannot put beans in the water container — wrong type. The machine won’t run.

In Java, each container is a parameter with a type:

void makeCappuccino(String milkType, String roastType, int waterMl) {
    IO.println("Brewing with " + roastType + " beans");
    IO.println("Adding " + waterMl + "ml of water");
    IO.println("Steaming " + milkType);
    IO.println("☕ Your cappuccino is ready.");
}
makeCappuccino("oat milk", "dark roast", 200);   // ✓ types match
makeCappuccino(200, "dark roast", "oat milk");   // ✗ won't compile

Output of the ✓ call:

Brewing with dark roast beans
Adding 200ml of water
Steaming oat milk
☕ Your cappuccino is ready.

The ✗ call puts a number in the milk slot and text in the water slot. Java refuses to compile it.

The containers stay the same. The contents change with each cup — but they must be the right type.

What Is a Parameter?

Now the vocabulary arrives — AFTER two analogies have established the intuition. A parameter is the named slot (the container) in the method definition. An argument is what you pour into the slot at call time. The blank-form analogy is a third reinforcement: the parameter is the label on the blank (“Name:”); the argument is what you write in the blank (“Alice”). Students who connect with the magic analogy, the coffee machine, or the form — at least one of the three will stick. Present all three briefly and let students find their own anchor.

A parameter is a named placeholder in a method definition. It represents a value that will be provided each time the method is called.

Think of it like a blank in a form:

Hello, _______!
         ↑
      parameter: "name"
      (blank to be filled in)

The form is written once. Each time someone fills it in, they provide a different name.

In Java, the parameter goes inside the parentheses of the method definition:

void greet(String name) {
    IO.println("Hello, " + name + "!");
}

The word name is the parameter. Inside the method body, name stands in for whatever value will be provided at call time.

One definition. Works for any name.

Note

A parameter has two parts: a type (String) and a name (name). The type tells Java what kind of value to expect. The name is how you refer to the value inside the method body.

Defining a Method with a Parameter

The syntax is a direct extension of what they already know. void + name + () becomes void + name + (type paramName). Everything else is the same. Walk through the anatomy carefully. The parameter lives inside the parentheses — that is why the parentheses were always required, even when empty, in deck 08. Now they are no longer empty. Show two or three examples so the pattern is clear before moving on to calling.

Adding a parameter is a small change to the method definition — just add type name inside the parentheses:

//  Without parameter:        With parameter:
void printSeparator()         void greet(String name)

The full structure:

void methodName(type parameterName) {
    // the parameter is available here, as a variable
}

Examples:

void greet(String name) {
    IO.println("Hello, " + name + "!");
}

void printScore(int score) {
    IO.println("Your score is: " + score);
}

void reparo(String target) {
    IO.println("*fixes the " + target + "*");
}

Inside the body, the parameter behaves exactly like a variable: use it in expressions, pass it to IO.println, put it in conditions.

The only difference: its value comes from whoever calls the method.

Declare the parameter once in the parentheses; use it anywhere in the body.

What Is an Argument?

Now the second vocabulary word: argument. The distinction between parameter and argument is one of the most commonly confused pairs in intro CS. The mnemonic on the slide: Parameter is in the definition (Planning), Argument is in the call (Actual value). Or just: parameter is what you name it in the definition; argument is what you put there when you call it. The blank-form analogy extends naturally: the parameter is the label on the blank (“Name:”); the argument is what you write in the blank (“Alice”).

When you call a method that has a parameter, you provide a value inside the parentheses. That value is called an argument.

greet("Alice");   // "Alice" is the argument
greet("Bob");     // "Bob" is the argument

Two new words — one for each side of the exchange:

Word Where it appears What it is
parameter in the method definition the placeholder
argument in the method call the actual value

Think of the blank-form analogy:

  • The blank labeled “Name:” is the parameter — it’s in the form definition
  • “Alice” written in the blank is the argument — it’s what you fill in

The form (method) is defined once with a blank. Each time you fill it in (call it), you provide a different argument.

Tip

An easy way to remember: Parameter is in the definition (think: Planning). Argument is in the call (think: Actual value).

Calling a Method with an Argument

Now the full picture: define the method with a parameter, call it with an argument. Show the connection between the two. For each call, show which argument fills which parameter — the figure on the second sub-slide does exactly this. The reparo example ties back to the Harry Potter analogy, making this feel like a payoff of the earlier slide. Multiple calls with different arguments demonstrates the whole point: one method, many uses. Ask students to predict the output before revealing it.

void reparo(String target) {
    IO.println("*fixes the " + target + "*");
}

void main() {
    reparo("glasses");   // argument: "glasses"
    reparo("vase");      // argument: "vase"
    reparo("wand");      // argument: "wand"

Output:

*fixes the glasses*
*fixes the vase*
*fixes the wand*

One method. Three calls. Three different results — because three different arguments.

Back to the duel — this time, every spell has a target:

Tracing: How the Argument Flows

This is the most important mechanical slide of the lecture. Students need to see exactly what Java does when it hits a method call with an argument: it takes the argument value, copies it into the parameter, and then runs the method body with the parameter holding that value. Click through the highlighted lines: greet(“Alice”) in main, then the parameter line, then the body, then back to main for greet(“Bob”), and through the method again. The numbered steps on the next sub-slide spell out what happened. The “as if Java wrote” framing is useful: calling greet(“Alice”) is as if Java wrote String name = “Alice”; at the top of the method body, then ran the body. The figure after that shows the parameter as a variable box that is filled fresh on each call.

When you call greet("Alice"), here is exactly what Java does. Step through it:

void greet(String name) {
    IO.println("Hello, " + name + "!");
}

void main() {
    greet("Alice");
    greet("Bob");
}

Step by step:

  1. greet("Alice") — Java sees a method call with argument "Alice"
  2. Java copies "Alice" into the parameter name
  3. The method body runs — everywhere name appears, it holds "Alice"
  4. The method finishes. Then greet("Bob") starts the same process with "Bob"

It is as if Java wrote String name = "Alice"; at the very top of the method body, ran everything, then came back and did it again with String name = "Bob";.

Output:

Hello, Alice!
Hello, Bob!

The parameter is a variable box that gets filled fresh on every call.

Multiple Parameters

A method can take more than one parameter — just separate them with commas inside the parentheses. The critical rule: argument order matters. The first argument is copied into the first parameter, the second into the second. If you swap them and the types still match, Java will not complain — but the output will be wrong. The swap-bug is one of the most common mistakes with multiple parameters. Show both the correct call and the swapped call to make the risk concrete.

A method can accept more than one input — just list the parameters separated by commas:

void printScore(String player, int score) {
    IO.println(player + ": " + score);
}

Each parameter has its own type and name. When calling, give one argument per parameter:

void main() {
    printScore("Alice", 95);
    printScore("Bob", 87);
    printScore("Charlie", 91);
}

Output:

Alice: 95
Bob: 87
Charlie: 91

Order matters. The first argument goes to the first parameter, the second to the second — in order, left to right.

void introduce(String first, String last) {
    IO.println("My name is " + first + " " + last + ".");
}

void main() {
    introduce("James", "Bond");   // first="James", last="Bond"
    introduce("Bond", "James");   // first="Bond", last="James" ← wrong!
}

Output:

My name is James Bond.
My name is Bond James.

Java does not know which order you intended — it just fills positions left to right. If you swap the arguments, you get wrong output with no error message.

Parameters Are Local

A parameter only exists inside the method where it is defined. Outside that method, it does not exist at all. This is a preview of scope, which gets its full treatment in deck 10. For now, just plant the rule: parameters are local. Students who try to use a parameter after the method ends, or try to use one method’s parameter inside a different method, will hit a compile error. This is a good thing — it means methods are self-contained and cannot accidentally interfere with each other.

A parameter only exists inside the method where it is defined. It cannot be seen or used anywhere else.

void greet(String name) {
    IO.println("Hello, " + name + "!");   // ✓ — name exists here
}

void main() {
    greet("Alice");
    IO.println(name);    // ✗ — ERROR: name does not exist here
}

This is intentional. Each method is a self-contained unit. Its parameters are its own private variables — they come into existence when the method is called and disappear when the method finishes.

This is called scope — where a variable exists. Scope gets its full treatment in the next lecture.

Note

The same parameter name can appear in multiple different methods with no conflict, because each method’s parameters are completely independent of every other method’s.

Common Mistakes

Four mistakes, each tied to a specific concept in this lecture. Wrong argument count and wrong argument type are compile errors — caught early. Wrong argument order may compile (if types match or can be converted) but produces wrong output — the sneakiest kind of bug. Using a parameter outside its method is a compile error. For each one, show the code, ask students to identify the problem, then click to reveal it.

1. Wrong number of arguments

void greet(String name) { ... }

greet();
greet("Alice", "B");
greet("Alice");
  • greet(); — missing argument; won’t compile
  • greet("Alice", "B"); — too many arguments; won’t compile
  • greet("Alice"); — ✓ exactly one argument for one parameter

2. Wrong argument type

void printScore(String player, int score) { ... }

printScore(95, "Alice");
printScore("Alice", 95);
  • printScore(95, "Alice"); — 95 is not a String and "Alice" is not an int; won’t compile
  • printScore("Alice", 95); — ✓ types match, in order

3. Arguments in the wrong order

void introduce(String first, String last) { ... }

introduce("Bond", "James");

It compiles — but prints My name is Bond James. instead of My name is James Bond.

Java fills positions left to right. It doesn’t know which value is the first name.

4. Trying to use a parameter outside its method

void greet(String name) {
    IO.println("Hello, " + name + "!");
}

void main() {
    greet("Alice");
    IO.println(name);
}

IO.println(name); won’t compile: name does not exist in main. Parameters are local to their method.

Key Takeaways

A one-slide recap students can come back to when studying. There is no textbook, so this is the page they will revisit before the test. Read each line aloud and ask the class for an example of each.

  • A parameter is a named, typed placeholder in a method definition: void greet(String name).
  • An argument is the actual value you pass in the call: greet("Alice").
  • On a call, Java copies each argument into its parameter, then runs the body.
  • Separate multiple parameters (and arguments) with commas. Arguments fill parameters left to right.
  • The number and types of arguments must match the parameters, or the program won’t compile.
  • Swapping two arguments of the same type compiles but gives wrong output.
  • Parameters are local: they exist only inside their own method.
