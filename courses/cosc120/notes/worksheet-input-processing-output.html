Learning Outcomes

  • Identify the input, processing, and output stages in a program’s description before writing any code
  • Read one or more values with IO.readln, convert numeric input with Integer.parseInt
  • Compute a result using arithmetic operators (+, -, *, /, %)
  • Print a labeled result using IO.println and String concatenation
  • Explain, for a program that fails, which of the three stages is broken

Why New Programmers Hit a Wall Here

This deck is a remediation/consolidation session, not new content — everything here uses only what lecture 2 (variables, IO.readln, IO.println) and lecture 3 (arithmetic, Integer.parseInt) already covered. The wall students hit is usually not syntax, it’s not having a plan before they start typing. They stare at a word problem and don’t know where to begin because they’re trying to write the whole program in one motion. The fix is a habit: before touching the keyboard, name the three stages out loud (or in a comment). Use this slide to diagnose that out loud with the class — ask “when a program you wrote doesn’t work, do you know if the input is wrong, the math is wrong, or the print statement is wrong?” Most say no. That’s the gap this worksheet closes.

You already know IO.readln, IO.println, variables, and arithmetic.

You must have a plan before you start typing.

Every program you’ve written so far, no matter how small, does the same three things:

  1. Get some data in
  2. Do something with it
  3. Show a result

The Pattern: Input → Processing → Output

Name the pattern explicitly and give it an acronym (IPO) so students have a label to reach for. Map each stage directly onto the Java constructs they already know — this is not new material, it’s a lens for organizing material they have. Emphasize that not every program has all three (a program can print a fixed message with zero input or processing), but almost every interesting program does.

Stage Question to ask Java tools you already know
Input What data does the program need, and where does it come from? IO.readln(), IO.readln("prompt: ")
Processing What computation turns that data into the answer? + - * / %, Integer.parseInt(...)
Output What exactly should be printed, and in what format? IO.println(...), + for concatenation

Note

Not every program needs all three. A program that just prints a message has output only — zero input, zero processing. But most real programs use all three, in that order.

Worked Example — Labeling the Stages

Walk through this once, slowly, before turning students loose. The point of the //INPUT, //PROCESSING, //OUTPUT comments is not that real programs need these comments forever — it’s training wheels. Have students write these three comments in their code for every problem on this worksheet, in order, before writing any other code. It forces them to plan the shape of the program before worrying about syntax. Trace through the example with a concrete input (say, 45 minutes studied) before running it.

Problem: Ask the user how many minutes they studied. Print how many full hours that is, and how many minutes are left over.

void main() {
    // INPUT
    int minutes = Integer.parseInt(IO.readln("Minutes studied: "));

    // PROCESSING
    int hours = minutes / 60;
    int leftover = minutes % 60;

    // OUTPUT
    IO.println("Hours: " + hours);
    IO.println("Leftover minutes: " + leftover);
}

Notice the shape: one block to get data, one block to compute, one block to print. That order almost never changes.

Tip

Before you write any code on this worksheet, write the three comments //INPUT, //PROCESSING, //OUTPUT in your file first. Then fill in each block one at a time.

Note

This worked example uses IO.readln("Minutes studied: ") — a prompt built right into the read. The worksheet below builds up to that style in stages; you’ll see why it’s the one worth defaulting to.

Prompts: Three Ways to Ask

This is the second confusion point layered on top of IPO, and it deserves its own slide before students hit the worksheet. A silent IO.readln() is technically correct Java but a terrible user experience — the cursor just blinks and the student (or grader) doesn’t know the program is waiting for anything. Walk through all three versions live: run the silent one first and let the awkward silence land, then show the two fixes. The IO.println + IO.readln() version matters because it’s the one students reach for instinctively once they realize they need to say something before reading — but it puts the prompt on its own line, and the input the user types appears on the next line, which looks different from the inline-prompt version. Point that out explicitly: same information reaches the program either way, but the on-screen layout differs. IO.readln("prompt: ") is the idiomatic one-line version and should become the default once it’s introduced.

IO.readln doesn’t require a prompt — but leaving one out makes the program confusing to use.

No prompt

String name = IO.readln();

The program just waits. The user has no idea what to type.

Separate print, then read

IO.println("Enter your name:");
String name = IO.readln();

The prompt appears on its own line; the user’s answer appears on the next line.

Prompt built into readln

String name =
    IO.readln("Enter your name: ");

Prompt and answer share one line — the style you should default to from here on.

Worksheet

Reserve the last 20-30 minutes, or use as a standalone remediation session. Require the // INPUT / // PROCESSING / // OUTPUT comment scaffold on every problem, even the trivial ones — the habit is the point, not the code. Problem 1 is intentionally degenerate (missing a stage) so students see that the pattern is a lens, not a rigid template. On top of the IPO progression, prompts are layered in gradually: Problems 2-4 read with no prompt at all (let them feel the confusion), Problems 5-7 print a prompt separately with IO.println/IO.print before calling IO.readln(), and Problems 8-10 fold the prompt into IO.readln("..."), which should become the default from here on. Problems 7-9 also require two or more processing steps in sequence, and Problem 10 is the synthesis problem. Common failure: students try to read all inputs, then do all processing, then print — which is actually correct and is exactly the pattern; the more common bug is interleaving a println into the middle of processing and getting confused about what’s been computed yet. Watch for forgotten Integer.parseInt, and for / vs % confusion.

For every problem below, start by writing // INPUT, // PROCESSING, and // OUTPUT as comments in your file, in that order. Then fill in the code under each one. If a problem has no input or no processing, leave that comment in place with nothing under it — that’s fine, and worth noticing.
