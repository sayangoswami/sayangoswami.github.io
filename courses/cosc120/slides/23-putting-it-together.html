The Big Picture

You now have a full toolkit:

Tool What it’s for
Variables & types Storing and naming individual values
if / else Making decisions
while / for Repeating
Methods (decks 08–10) Naming and reusing a block of work
Arrays (decks 15–17) Storing many values of the same type

Today’s lecture: using all of them together.

Step back and let students see the whole map before the deep dive. Each tool solves a specific problem; combining them is what real programming looks like. The goal of this lecture is not to teach new syntax — it’s to teach design: given a problem, how do you decide which tools to reach for and in what order?

A Design Process

When given a problem, ask these questions in order:

  1. What are the “things” in this problem? → Make a class for each
  2. What data does each thing carry? → Those are the fields
  3. What can each thing do? → Those are the instance methods
  4. What work spans many things? → Arrays of objects, loops
  5. What utility calculations don’t belong to any one thing? → Static methods
  6. How does everything start? → main orchestrates it all

This is a design checklist, not a rigid recipe. Walk through it with students: “What are the things in a grade book? Students. What data does a student carry? Name, grade, maybe ID. What can a student do? Report their grade, say whether they’re passing, compute their letter grade. What spans many students? The roster — an array of Student objects with a loop. What utility? Maybe a static letter-grade converter. Main creates the roster, fills it, and calls a print method.” This makes OOP feel natural rather than arbitrary.

Case Study: A Grade Book

Problem: Build a simple grade book. Store students (name + grade), compute class statistics, and print a report.

Step 1 — Identify the “things”: Students.

Step 2 — The Student class:

class Student {
    String name;
    int grade;

    Student(String name, int grade) {
        this.name  = name;
        this.grade = grade;
    }

    boolean isPassing() { return grade >= 60; }

    String letterGrade() {
        if (grade >= 90) { return "A"; }
        if (grade >= 80) { return "B"; }
        if (grade >= 70) { return "C"; }
        if (grade >= 60) { return "D"; }
        return "F";
    }

    void print() {
        IO.println(name + ": " + grade + " (" + letterGrade() + ")");
    }
}

Start with the class — the building block. isPassing() and letterGrade() are clean predicate/query methods. print() composes letterGrade() inside it. Nothing new syntactically; the emphasis is on the design decision: these behaviors belong WITH the student, not in a standalone method, because they always need a specific student’s grade.

Case Study: Roster + Statistics

Step 3 — An array of Student objects + loops:

void printRoster(Student[] roster) {
    IO.println("=== Grade Book ===");
    for (int i = 0; i < roster.length; i++) {
        roster[i].print();
    }
}

double classAverage(Student[] roster) {
    int sum = 0;
    for (int i = 0; i < roster.length; i++) {
        sum += roster[i].grade;
    }
    return (double) sum / roster.length;
}

int countPassing(Student[] roster) {
    int count = 0;
    for (int i = 0; i < roster.length; i++) {
        if (roster[i].isPassing()) { count++; }
    }
    return count;
}

These are standalone methods (not inside Student) because they work on the whole roster, not one student. The loop structure is identical to array algorithms from decks 15–16, but now the elements are Student objects instead of ints. roster[i].grade accesses the field; roster[i].isPassing() calls the instance method.

Case Study: main Orchestrates

Step 4 — main creates and connects everything:

void main() {
    Student[] roster = {
        new Student("Alice",  88),
        new Student("Bob",    54),
        new Student("Carol",  91),
        new Student("Dave",   72),
        new Student("Eve",    63)
    };

    printRoster(roster);
    IO.println("Class average: " + classAverage(roster));
    IO.println("Passing: " + countPassing(roster) + "/" + roster.length);
}

Output:

=== Grade Book ===
Alice: 88 (B)
Bob: 54 (F)
Carol: 91 (A)
Dave: 72 (C)
Eve: 63 (D)
Class average: 73.6
Passing: 4/5

Main is the conductor: it creates the orchestra (the roster) and tells each section when to play (calls the methods). Main itself does almost no calculation — it delegates everything. This is good design: main is a readable script of what happens; the details live in the methods and class. Ask students: if we add a sixth student, what changes? Only the roster array — everything else adjusts automatically.

Practice tracing with object arrays, not just int arrays. The table structure is the same as deck 13 (loop patterns); only the “action” column is different. Each iteration calls roster[i].isPassing() — an instance method call on the object at that index. Trace this table aloud with students. Then ask: “What would countPassing return if Bob’s grade were 62?” They should be able to answer immediately.

Another Design: A Simple Inventory

class Item {
    String name;
    double price;
    int quantity;

    Item(String name, double price, int quantity) {
        this.name     = name;
        this.price    = price;
        this.quantity = quantity;
    }

    double totalValue() { return price * quantity; }

    boolean isInStock()  { return quantity > 0; }

    void sell(int n) {
        if (n <= quantity) { quantity -= n; }
        else { IO.println("Not enough stock!"); }
    }
}

A second mini-design to show the pattern generalizes. Item has three fields; totalValue() and isInStock() are query methods; sell() is a void modifier method. Ask: “What would a static method on Item look like?” Maybe a static price formatter, or a static factory method — but most Item behavior needs a specific item, so most methods here are instance.

Choosing the Right Tool

When you see a problem description, map its language to tools:

Phrase in the problem Tool
“store many ___ of the same type” array
“for each ___” for loop
“keep asking until ___” while loop
“a ___ has properties: X, Y, Z” class with fields
“a ___ can ___” instance method
“a calculation that doesn’t belong to any one object” static method
“the same value for all objects” static field
“might not exist / not found” null check

Putting this table up invites students to use it as a design vocabulary. “For each student in the roster” → for loop over an array. “A student has a name and grade” → class with fields. “Might not find the student” → return null, check null. This is the language-to-tool translation skill that separates programmers who can read problems from those who blank out.

Common Design Mistakes

Warning

Putting everything in main main should orchestrate, not compute. If main has 50 lines of calculation, refactor: extract methods and classes.

Warning

Making every field public and every method static If you never use new, you’re not doing OOP. Objects bundle state and behavior together.

Warning

Parallel arrays instead of an array of objects String[] names; int[] grades; that must stay in sync → replace with Student[] roster.

Warning

Writing all code before testing anything Write the class, test it. Write one method, test it. Don’t write 100 lines and then debug all at once.

The last point is software engineering practice, not just syntax. Encourage students to test incrementally: write the Student class and immediately write a main that creates one student and prints its name. Add letterGrade(), test it. Add isPassing(), test it. Only then build the roster and statistics.

Worksheet

Build the following program:

You are managing a library’s book collection.

  1. Write a class Book with fields String title, String author, and boolean checkedOut (initially false). Add a constructor, and methods:

    • void checkOut() — marks the book as checked out
    • void returnBook() — marks it as available
    • boolean isAvailable() — returns !checkedOut
    • void printStatus() — prints title, author, and “Available” or “Checked Out”

  2. In main, create an array of 4 Book objects.

  3. Write a method int countAvailable(Book[] books) that counts available books.

  4. Write a method Book findByTitle(Book[] books, String title) that returns the first matching book, or null if not found. Guard against null in main.

  5. Check out two books, then print the full inventory using a loop and printStatus(). Print how many books are still available.
