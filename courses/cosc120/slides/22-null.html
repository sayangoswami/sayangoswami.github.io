null and Object References

COSC120: Introduction to Computer Science I

Learning Outcomes

  • Explain what null means for an object reference variable
  • Recognize a NullPointerException and identify the line that caused it
  • Guard against null using an if (obj != null) check before calling a method
  • Distinguish an uninitialized reference (null) from an initialized object
  • Explain that null is not the same as 0, false, or "" — it means “no object at all”

What Is null?

When you declare an object variable without assigning it:

String name;        // uninitialized — holds null
Dog rex;            // uninitialized — holds null
Student alice;      // uninitialized — holds null

The variable holds null — a special value meaning “this variable currently points to nothing.”

null is not a string, not a number, not an empty object. It means no object exists here.

The pointer/arrow mental model is essential here. An object variable is an arrow (reference) pointing to an object. null means the arrow leads nowhere. Dereferencing null (following an arrow that leads nowhere) causes a NullPointerException — the program crashes because there’s nothing there to access. This is one of the most common runtime errors in Java.

Default Values for Object Fields

When an object is created and its fields aren’t set in the constructor, they get default values:

Field type Default value
int, double, etc. 0 / 0.0
boolean false
String null
Any object type null 
class Person {
    String name;    // defaults to null
    int age;        // defaults to 0
}

Person p = new Person();
IO.println(p.name);    // null
IO.println(p.age);     // 0

Students are often surprised that p.name prints the word “null” — Java converts null to the string “null” for IO.println. But calling a method on p.name (like p.name.length()) would crash with a NullPointerException because p.name has no object behind it. The printing behavior can mask the bug. Always check whether a String field was properly set before using it.

NullPointerException

Calling a method on a null reference crashes the program:

Dog rex = null;
rex.bark();       // NullPointerException!
Exception in thread "main" java.lang.NullPointerException

This is one of the most common errors in Java. The message says: you tried to follow an arrow that leads nowhere.

When does it happen? - Calling a method on a variable that was never assigned - Calling a method on a field that was never set in the constructor - A method returned null and you called a method on the result

NullPointerException (NPE) is so common it’s almost a rite of passage in Java. The error tells you a line number — that’s the line where you dereferenced null. Find that line, find the variable, trace back to where it was supposed to be assigned. Was it assigned? If not, that’s the bug. A newer Java will also tell you which variable was null in the message.

Guarding Against null

Always check before calling a method on a reference that might be null:

String name = IO.readln("Enter a name (or leave blank): ");

if (name != null) {
    IO.println(name.toUpperCase());
} else {
    IO.println("No name given.");
}

Or for an object:

Dog dog = findDog("Rex");    // might return null if not found

if (dog != null) {
    dog.bark();
} else {
    IO.println("Dog not found.");
}

The pattern “check before use” is the universal null-safety technique. Before calling any method on an object reference that might be null, check: if (obj != null). This is especially important for: return values from search methods (linear search returns -1 for arrays; methods often return null for objects), fields that aren’t always set, and user input.

null in Linear Search

When searching for an object and not finding it, return null as the “not found” signal (just as index searches return -1):

Student findByName(Student[] roster, String name) {
    for (int i = 0; i < roster.length; i++) {
        if (roster[i].name.equals(name)) {
            return roster[i];    // found — return the object
        }
    }
    return null;                 // not found
}

Usage:

Student found = findByName(roster, "Carol");

if (found != null) {
    IO.println("Found: " + found.grade);
} else {
    IO.println("Not found.");
}

Returning null from a search method is the object counterpart to returning -1 from an index search. The caller is responsible for checking: if the result is null, the search failed. This pattern appears everywhere in real Java code. Note: we use .equals() to compare Strings (from deck 07), not == , even inside a class.

null Is Not the Same As…

Value Meaning
null No object at all — the reference points nowhere
0 The integer zero — a valid int value
false The boolean false — a valid boolean value
"" An empty String — a real String object with length 0 
String a = null;   // no String object exists
String b = "";     // a String object exists, but it has no characters

IO.println(a.length());   // NullPointerException!
IO.println(b.length());   // 0  — perfectly fine

This is a common confusion. An empty string (““) IS an object — you can call .length() on it and get 0. null is NOT an object — you can’t call any method on it. The distinction matters in every conditional check: if (name == null) and if (name.equals(”“)) are two different questions.

Common Mistakes

Warning

Calling a method without checking for null If a variable might be null, always guard with if (obj != null) before the dot.

Warning

Using == to compare String content name == "Alice" compares references (are they the same object?), not content. Use name.equals("Alice") — but check name != null first!

Warning

Forgetting that unset fields default to null A field of type String that isn’t set in the constructor holds null — calling .length() on it will crash.

Warning

Printing null and thinking it’s fine IO.println(name) will print the word null if name is null — no crash. But IO.println(name.toUpperCase()) will crash. Printing without crashing doesn’t mean the variable is safe to use.

The fourth mistake is the sneakiest: IO.println(null) works because Java converts null to the string “null” for display. Students think “it printed something, so name must be set.” Wrong — name is still null, and any method call on it will crash. Always verify that a field was actually assigned, not just that println survived.
