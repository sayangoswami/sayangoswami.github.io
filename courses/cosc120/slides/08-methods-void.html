Methods: void Methods

COSC120: Introduction to Computer Science I

Learning Outcomes

  • Explain what a method is and describe how methods reduce repetition and improve readability
  • Define a void method with no parameters
  • Call a method from main, including calling the same method multiple times
  • Write a method that calls other methods to build a structured program

What Is a Method?

Before doing anything else, plant two vocabulary words the students will hear for the rest of the course: “method” and “call.” Don’t define them formally — just give them enough meaning to follow what comes next. The table is intentionally minimal. Two words. That’s the whole slide. Students should leave this slide knowing what to listen for, not feeling like they learned something hard. The aha moments and the examples come on the slides that follow.

You have written dozens of programs. Every instruction lived inside main.

But what if a group of instructions belongs together and you want to use it in multiple places?

Java lets you package a group of instructions, give that package a name, and run it anywhere — just by writing the name.

Word Meaning
method a named group of instructions
call to make a method run by writing its name

These two words are the most important new ideas in this lecture. By the end, both will feel completely natural.

This is the big callback moment. Now that “method” and “call” have been introduced as vocabulary, show students that the words describe something they have been doing all semester. The list is intentionally long to make the point land — every single item has the same pattern: a name followed by parentheses. Pause and let that sink in. Then: “Today, you learn how to write your own.” This reframes a scary-sounding topic as a natural next step.

IO.println("Hello, world!")         // Lecture 1

You have been calling methods since Day 1. Today, you learn how to write your own.

The Duel

This is the central analogy for the whole lecture. The goal is maximum drama before any code appears. Harry and Voldemort are mid-duel — spells flying, stakes high. Neither wizard stops to describe what the spell does. They just shout the name. The audience doesn’t need to know the magical mechanics of Avada Kedavra — they just see the result. The key idea to land: a name that, when said, triggers a complete sequence of actions. Students who don’t know Harry Potter can substitute any battle magic from any fiction — the structure is universal. Let this slide breathe. No code. Just the analogy.

Picture the final duel. Harry faces Voldemort.

Spells are flying back and forth.

Harry does not shout:

“I am gathering magical energy in a protective dome shape around myself, calibrating the resonant frequency to deflect incoming dark magic, initializing the shield at full power…”

He shouts:

“Protego!”

Voldemort does not announce:

“I am directing a focused stream of lethal dark energy toward you at approximately 45 degrees, initiating the killing curse sequence…”

He shouts:

“Avada Kedavra!”

Each spell is a name for a complex sequence of actions. In the heat of battle, nobody cares about the steps — they call the spell, and the spell knows what to do.

The Duel in Java

Now translate the analogy into code. The structure is identical: a name that triggers a sequence of steps. The only difference from real magic: you write the spell yourself. Walk through the Java duel line by line in main() — it reads almost exactly like the battle narration. Point out that main reads like a story: first Voldemort attacks, then Harry defends, then again. The details of each spell are hidden inside the method definition. The duel is legible without knowing the magical mechanics. This is the exact same benefit methods provide in any real program.

In Java, a spell looks like this — you write the steps once, under a name:

void avadaKedavra() {
    IO.println("*a jet of green light flies*");
    IO.println("*the killing curse is cast*");
}

void protego() {
    IO.println("*a shimmering shield materializes*");
    IO.println("*the curse is deflected*");
}

And the duel itself:

void main() {
    avadaKedavra();    // Voldemort attacks
    protego();          // Harry defends
    avadaKedavra();    // again
    protego();          // again
    IO.println("Harry wins.");
}

main reads like the battle. The details of each spell are tucked away inside their own block. You don’t need to know the magical mechanics to follow the story.

The only difference from real magic: you write the spells yourself.

And once you have — calling them is exactly that simple.

Note

In the next two lectures you will learn how to make spells that take input (“cast at this target”) and produce a result (“and tell me if it worked”). For now, every method just does its thing.

Methods Are Mini-Recipes

The recipe analogy complements the spell analogy: where the spell emphasizes simplicity of invocation, the recipe emphasizes how a large task is decomposed into smaller named tasks. A Thanksgiving dinner recipe does not copy the gravy recipe inline — it says “make the gravy” and points elsewhere. This is exactly how a well-structured program works: main reads like a table of contents, and each method is a self-contained sub-recipe. The visual hierarchy (big card at top, smaller cards below) should make the structure feel natural and obvious.

Imagine writing a recipe for a full Thanksgiving dinner.

At one point it says: “Step 4: Make the gravy.”

It does not paste the entire gravy recipe into the middle of the Thanksgiving recipe. It just says the name. The gravy recipe exists separately, and you look it up when you need it.

Your program works the same way:

void main()         ←  "Cook Thanksgiving Dinner"
    roastTurkey()   ←  Step 1 — see turkey recipe
    makeSides()     ←  Step 2 — see sides recipe
    makeGravy()     ←  Step 3 — see gravy recipe
    serveDinner()   ←  Step 4 — see service recipe

main is the head chef — it coordinates everything but delegates the actual work. Each method is a focused, self-contained task. The head chef doesn’t need to know how to make gravy — they just need to know when to call for it.

void main() — You Already Wrote a Method

This is the biggest aha moment of the lecture. Every student has been staring at “void main() { }” since the first day of class and now they learn that it is itself a method. Take time to annotate each part. The word “void” has been there the whole time — now it gets an explanation (doesn’t produce a value; all their methods will start with void for now). The key emotional beat: “You have been writing methods since Lecture 1. Now you will write more of them — with names you choose.”

Look at every program you have written this semester:

void main() {
    IO.println("Hello, world!");
    // ... all your code ...
}

That void main() { ... } — that is a method.

You have been writing a method since Lecture 1 without knowing it.

main is a special method: Java looks for it when your program starts and runs it automatically. Everything inside its braces is the body of the main method.

The word void means “this method does not produce a value.” All the methods you write in this lecture will start with void — more on this in a future lecture.

You already know how to write a method. Now you will write them with names you choose.

main Is Special

Students now know that main is a method — but they need to understand why it is different from every other method they will write. Three rules, stated plainly: every program must have one, there must be exactly one, and Java starts there. The “no main” and “two mains” error cases are worth spending a moment on — students will hit both of these at some point this semester. The analogy: every story has a first page. main is Java’s first page. All other methods are chapters that only get read when the story calls for them.

main is a method — but it is a special one. Three rules set it apart from every other method you will write:

1. Every program must have a main method. When you run a program, Java looks for main to know where to start. No main — no starting point — Java stops with an error.

2. There must be exactly one main. If you write two methods both named main, Java doesn’t know which one to start from. That is also an error.

3. Java always starts at main — and only at main. Every other method you write sits quietly until something calls it. main is the only method that runs automatically.

void main() {
    // Java starts here — always
}

void printBanner() {
    // this only runs if something calls printBanner()
}

Warning

If your program produces no output and you are not sure why — check that you have a main method, and that your code is inside it.

Think of main as the opening scene. Every story has to start somewhere. In a Java program, it always starts at main.

Why Write Your Own Methods?

Three reasons, stated plainly before any code. Keep this slide short — the code examples on the next two slides will make the argument concrete. Students often get the “avoid repetition” point immediately; the “change in one place” and “better names” points need the code examples to land properly. Plant the ideas here, let the code make them real.

There are three reasons to write your own methods:

1. Avoid repetition. Write a group of instructions once. Call it as many times as you need. Never copy-paste the same lines again.

2. Give things names. printHeader() tells the reader exactly what is about to happen. Three raw IO.println lines tell them nothing until they’ve read all three.

3. Change in one place. Need to update the steps? Update the method body — not every place you used it.

These three benefits compound as programs get longer. Let’s see them in action.

The Problem: Without Methods

Show the code that everyone writes before they know about methods. The repeated header block is highlighted — three copies of the exact same three lines. Ask students how they would change the header from “=” to “*“. They would have to find and change three places. What if it appeared twenty times? This sets up the next slide’s fix perfectly. Don’t solve the problem yet — just make students feel the pain.

void main() {
    IO.println("====================");
    IO.println("=  SCORE BOARD     =");
    IO.println("====================");
    IO.println("Alice: 95");
    IO.println("Bob:   87");
    IO.println("====================");
    IO.println("=  SCORE BOARD     =");
    IO.println("====================");
    IO.println("Charlie: 91");
    IO.println("Diana:   78");
    IO.println("====================");
    IO.println("=  SCORE BOARD     =");
    IO.println("====================");
}

The header appears three times — three identical copies of three lines.

Now imagine: you want to change the header style. You must find and edit all three copies — and hope you don’t miss one.

If the header appeared twenty times, you would need to edit sixty lines.

There has to be a better way.

The Fix: With a Method

Now the payoff. The method is defined once. Calling it three times is three short lines. If you want to change the header, you change the method body — one place, done. Ask the class: how many lines long is main now? How many would it be if there were twenty calls? The version with a method actually gets shorter relative to the without-method version as repetition increases — methods scale. End with: “main reads like a table of contents. Each method does one thing.”

void printHeader() {
    IO.println("====================");
    IO.println("=  SCORE BOARD     =");
    IO.println("====================");
}

void main() {
    printHeader();
    IO.println("Alice: 95");
    IO.println("Bob:   87");
    printHeader();
    IO.println("Charlie: 91");
    IO.println("Diana:   78");
    printHeader();
}

The header is defined once. To change it, change one place. main is shorter and reads clearly.

Three calls. One definition. If the header appears twenty times, you write printHeader() twenty times — not sixty lines of IO.println. And to update the style, you still change just one place.

Defining a void Method

Walk through the anatomy one piece at a time. Students have seen every one of these elements before: “void” is in main; the name follows the same naming rules as variables; the parentheses have been in every method call they have ever written; and the braces are the same as in if-statements. Nothing here is truly new — this is just putting a name to something they already know. The anatomy figure with labeled arrows is the most important visual on this slide.

A void method has this structure:

void methodName() {
    // the body — steps that happen when this method is called
}

Every part has a job:

  • void — this method does not produce a value
  • methodName — the name you choose (write it like a short command)
  • () — parentheses, always required
  • { } — the body: the steps that run when the method is called

Nothing here is new. You have seen every one of these pieces before — in main, in if statements, in every method you have already been calling.

Method Examples

Three examples, each with a clear purpose. Students should be able to read each method name and immediately know what it does — that’s the whole point of the naming principle. Ask students to predict what each method prints before revealing or running it. The examples are short by design: the body of each method is one or two lines. This is intentional — students often think a method has to be long. Even a method that prints a single line is worth having if it has a good name and might be called more than once.

Here are three methods, each doing one clear thing:

void printSeparator() {
    IO.println("--------------------");
}

void printWelcome() {
    IO.println("Welcome to COSC 120!");
    IO.println("Let's write some Java.");
}

void printGoodbye() {
    IO.println("Thanks for learning with us.");
    IO.println("See you next class!");
}

You can read each name and know exactly what it does — before reading the body. That is what a good method name does.

You can call all three from main:

void main() {
    printWelcome();
    printSeparator();
    printGoodbye();
}

Naming Your Methods

The naming rules are the same as for variables, with one important addition: method names should be verb phrases — they describe an action, not a thing. A variable stores a value (a noun: “score”, “name”). A method does something (a verb phrase: “printScore”, “readName”). The good/bad examples are important — students often default to meaningless names when they are not sure what a method does. If a student cannot name a method well, that is a sign the method is trying to do too many things. Good naming is a design skill, not just a style preference.

Method names follow the same rules as variable names — with one key addition: use a verb phrase, because a method does something.

// ✓ Good names — describe an action clearly
void printHeader() { ... }
void showMenu() { ... }
void drawLine() { ... }
void displayScore() { ... }
void printEventSchedule() { ... }

// ✗ Poor names — say nothing about what the method does
void stuff() { ... }
void doThings() { ... }
void method1() { ... }
void myMethod() { ... }

Rules:

  • camelCase: printHeader, not PrintHeader or print_header
  • Start with a verb: print, show, draw, display, compute, check
  • Be specific: printEventSchedule() beats printStuff()

Tip

If you cannot name a method clearly, it might be trying to do too many things. Split it into smaller methods, each with one job and one clear name.

Calling a Method

The mechanics are simple: name followed by parentheses and a semicolon. Two points to stress: (1) defining a method does not run it — you must call it; and (2) you can call it as many times as you want, and the method body runs fresh each time. The note about definition order is useful: in Java, unlike some other languages, the order of method definitions doesn’t matter. Java reads all definitions before running anything. Students who have internalized “Java reads top to bottom” will be surprised, so flag it explicitly.

Once a method is defined, you call it — write its name, parentheses, semicolon:

void main() {
    printWelcome();       // the lines inside printWelcome run now
    printSeparator();     // then the lines inside printSeparator
    printGoodbye();       // then the lines inside printGoodbye
}

That is the whole spell. One line. The details are inside the method.

You can call the same method as many times as you want:

void main() {
    printSeparator();
    IO.println("First section");
    printSeparator();
    IO.println("Second section");
    printSeparator();
}

Each call runs the method body fresh from top to bottom. One definition. Unlimited calls.

Note

In Java, the order of method definitions does not matter. You can write printWelcome below main and Java will still find it. Java reads all the definitions before running anything.

The Flow of Execution

The most important mechanical concept of the lecture. Students need a clear mental model: the computer is executing line by line in main, hits a method call, leaves main, jumps to the method body, executes every line top to bottom, reaches the closing brace, and returns to main at exactly the next line. “Exactly where it left off” is the key phrase. Walk through the numbered comments one by one, waiting after each step. Then show the output. The figure — two vertical timelines connected by forward and return arrows — is what makes this concrete. Call stack mechanics are intentionally omitted.

When your program hits a method call, here is exactly what happens:

void main() {                       // 1. Java starts here
    IO.println("Before");           // 2. prints "Before"
    printBanner();                  // 3. JUMP to printBanner
    IO.println("After");            // 6. back here — continues
}

void printBanner() {                // 4. runs from top to bottom
    IO.println("=========");        //    prints "========="
    IO.println("  Hello!  ");       //    prints "  Hello!  "
    IO.println("=========");        //    prints "========="
}                                   // 5. closing brace — COME BACK

Output:

Before
=========
  Hello!
=========
After

The program jumps into the method, runs it completely, then comes back to the next line in main. “After” prints after the banner, not before it.

What happens when you call the same method twice?

void main() {
    IO.println("Round 1:");
    printBanner();            // jump in, run, come back
    IO.println("Round 2:");
    printBanner();            // jump in again, run again, come back
    IO.println("Done.");
}
Round 1:
=========
  Hello!
=========
Round 2:
=========
  Hello!
=========
Done.

Two separate trips. Each time, the method runs from top to bottom, then execution returns to main.

Methods That Call Other Methods

A method can call other methods inside its body. This is the payoff of the whole recipe hierarchy analogy — now it’s code. Main calls printTicket, which calls three helpers. Reading main tells you everything that happens at the highest level; reading printTicket tells you the structure; reading each helper tells you the actual output lines. You never have to hold the whole program in your head at once. Walk through the execution flow verbally: main → printTicket → printHeader (runs, comes back) → printDetails (runs, comes back) → printFooter (runs, comes back) → back to printTicket → back to main.

A method can call other methods inside its body — this is how large programs are built:

void printHeader() {
    IO.println("============================");
    IO.println("        MOVIE TICKET        ");
    IO.println("============================");
}

void printDetails() {
    IO.println("Movie:  The Matrix");
    IO.println("Date:   Saturday, Aug 22");
    IO.println("Time:   7:30 PM");
    IO.println("Seat:   Row C, Seat 12");
}

void printFooter() {
    IO.println("============================");
    IO.println("      Enjoy the show!       ");
    IO.println("============================");
}

void printTicket() {
    printHeader();
    printDetails();
    printFooter();
}

void main() {
    printTicket();    // one line. that's it.
}

Three levels of detail, each at the right level:

  • Read main → prints a ticket
  • Read printTicket → header, then details, then footer
  • Read each helper → the actual lines of output

You never have to hold the whole program in your head at once. You zoom in only as far as you need to.

Common Mistakes

Four mistakes that appear in almost every student’s code the first week. The most dangerous is defining without calling — the program compiles and runs, just silently does less than expected. Missing parentheses and code outside a method are compile errors, so at least they are caught early. Poor naming compiles fine but creates invisible technical debt. Go through each one slowly, asking students to identify what is wrong before revealing the answer.

1. Defining a method but never calling it

void printBanner() {       // defined...
    IO.println("=====");
}

void main() {
    IO.println("Hello!");  // ...but never called — banner never prints
}

Java does not warn you. The method simply never runs.

2. Forgetting () when calling

printBanner;     // ✗ — not a method call; won't compile
printBanner();   // ✓

3. Writing code outside any method

IO.println("Hello");   // ✗ — not inside any method; won't compile

void main() {
    IO.println("Hello");   // ✓
}

Every executable line must live inside the { } of some method.

4. Naming a method something vague

void stuff() { ... }           // ✗ — what does "stuff" do?
void doIt() { ... }            // ✗ — do what, exactly?
void printEventSchedule() { }  // ✓ — says exactly what it does

A method name is a promise to whoever reads the code. Keep it.
